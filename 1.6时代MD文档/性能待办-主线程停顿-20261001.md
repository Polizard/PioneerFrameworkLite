## 0. 一句话

物理步的偶发尖峰里，**"等"（线程被挡）占 2–4 ms/次**，位置**全都落在"我们正在打日志"的主线程路径上**
（燃烧诊断 / 终端律"修正烧起步" / 阶梯）；那条 **108 ms** 最可能是同一机制的最坏一次。
**算法层面无账可查**（那些步的本线程 CPU 只涨了 0.4 ms）。

## 2. 已排除

- **GC**：相关步的 `GC 本步=0/0/0`（三代都没触发）。
- **等自家并行工作线程**：三条"等"走的都是**单线程路径**（终端律计算、燃烧诊断）——没有派发并行体。
  ⚠ 口径提醒：**并行阶段**（组物理、阶梯并行搜索）天然表现为"低 CPU + 高墙钟"，**与"停顿"不同源**
  —— 本仪器的 CPU 栏只测**主线程**，读的时候别把两者混了。
- **算法慢**：CPU 没涨，没有计算量可优化。

## 3. 头号假设 + 尚未排除的

- **头号假设**：`Verse.Log.Message` → **同步写 `Player.log`** 的偶发 I/O 停顿
  （磁盘忙 / Windows Defender 实时扫描 / 缓冲刷新）。I/O 延迟是**重尾分布**——
  这正好解释"平时 ~20 µs、偶尔 2–4 ms、极偶尔 100 ms"的形状。
  **证据**：三条"等"与"我们在打日志"的位置一一对应（终端律烧起步那一行、燃烧诊断那 3–4 行）。
  **未证实**：还没有直接测到"某一次 Log.Message 花了 N ms"（见 §5.2 的仪器）。
- **未排除**：页错误（工作集被换出后读回）、别的进程占盘、时间片被别的线程抢走。

## 4. 问题的本质：现在"看见"和"代价"是绑在一起的

- **免费的观测**（内存累加，纳秒级）——已经在用：
  `[步耗时]` **窗口行**（每 300 步一行）· **尖峰行**（只在 >2 ms 时打、事件驱动）· **普查计数**（>2ms 步数/合计）。
  ⇒ "能力有没有变化 / 哪一步出事 / 一个窗口里出过几次"这三问**都不贵**。
- **贵的那一半**：**逐屏诊断流**（每行 = 主线程一次同步写盘）：
  `[燃烧·诊断]` / `[燃烧·对账]` / `[燃烧·头步]`（上一轮 3,700+ 行；这一轮 950 行）· `[终端律]`（每 10 s 一行）·
  已挂开关的 `[预对准·诊断]`（不挂之前 4,570 行 = 日志 38%）。
- 日志构成实测：上一轮 11,903 行里诊断类 **≈87%**；这一轮（`[预对准·诊断]` 关掉后）2,905 行里燃烧两族 **33%**。

## 5. 待办（按性价比排序，**都未做**）

1. **给诊断族挂开关**：`[燃烧·诊断]` / `[燃烧·对账]` / `[燃烧·头步]` 挂到既有的 `DebugDetailedThrust` 家族
   （照 `[预对准·诊断]` 挂 `DebugDetailedSteering` 的先例，一行的事）⇒ 常态不打 = 不付 I/O；查燃烧账时打开。
2. **尖峰行加"本步日志行数 / 写盘耗时"**：包裹层**只在内存累加**（~50 ns/行，可忽略），**只在尖峰时印**
   ⇒ **平时零成本、出事正好有账**——这一刀直接破掉"想看见就得付钱"的两难，也是 §3 头号假设的**直接判据**。
3. **（可选、较大）内存环缓冲 + 按需 dump**：逐屏诊断攒在内存里（最近 N 千行），按键导出 / 窗口末 / 退出时落盘
   ⇒ 逐屏细节一行不少，而主线程几乎零 I/O。
4. **（仅当 1+2 之后仍要追）换页/内核时间读数**：`GetThreadTimes` 的**内核**部分（1 ms 粒度即可）+
   `PageFaultCount` 增量，用来分开"I/O 停顿"与"换页停顿"。
