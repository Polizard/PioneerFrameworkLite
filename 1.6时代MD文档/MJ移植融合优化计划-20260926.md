## §0 一页入口

### 0.1 现场一句话

**移植进来的 MJ 库本体不是成本中心——接缝才是。** 走游戏运行路径的 MJ 代码全是纯结构体纯函数、零分配；
真正花钱的是三件事：①一个**本可以关掉的观测仪器**（燃烧诊断块，台账 P28 已登记"长期应可关"）常驻生产；
②规划尖峰（`MakePlan` ≤4320 次 Lambert 求解，含"每次不可行都抛/接异常"）；
③宿主适配层**把已有的东西算第二遍**（每次调用重建 `OrbitView`、每次调用问一遍 `GetComponent`、同一帧两次传播）。

⇒ 本批的目标一句话：**把"身体"改到不再对移植进来的器官做重复功，器官本身一个字不动。**

> 📌 **另有两块不在本批内**：
> ①**表示层一致性**（类型 / 坐标系 / 换系点的混乱）——**手性那一半已结清、不是问题**；
> 但"一个类型扛多个系、同一对换算多份实现"确实存在**并已造成事故**，且本次核查**新抓到一处疑似活缺陷**。
> 见 **§8**（与性能批严格分开，唯一交集是 N2 并进 P26）。
> ②**转换最小化**（用户 2026-09-26 裁定"**必要时可以改移植过来的 MJ**，让 MJ 与 PFL 之间尽可能少转换"）——
> 结论是：**最贵的那个转换（极轴 +Y↔+z）不值得消**（消它要放弃 6179 条上游验收），
> 该做的是"让那一次转换不可能漏" + 消掉三个便宜的。见 **§9**。

### 0.2 移植面规则（**2026-09-26 用户裁定后重写：可以改，但要分档**）

**用户原话**："**必要时可以修改我们移植过来的 MJ 部分，使得移植的 MJ 和我们的 PFL 之间尽可能少转换。**"
⇒ 原先"逐字不变式 = 一个字不许动"**已作废**。（该不变式原是我们自己写进 `ThirdParty/MechJebLib/README.md` 的护栏，
不是上游要求；它的**真实价值**是——**上游那 6179 条用例是我们最强的验证资产**。所以新规则按"改一下要付多少验证成本"分档。）

| 档 | 允许的改动形态 | 上游用例 | 判据 |
|---|---|---|---|
| **T-A ✅ 鼓励** | **语句级重写，公式与求值序都不变**：提循环不变量、提局部变量、同一个子表达式只算一次、加 `[MethodImpl(AggressiveInlining)]` | **仍全绿** ⇒ **验证资产完好** | 逐位差分（§4.1）+ 移植用例数不减 |
| **T-B ⚠ 逐条裁定** | **加可选参数、默认值 = 上游行为**（例：把"极轴"参数化，默认 `+z`） | 仍全绿，但**宿主走的那条路不被上游覆盖** | 需**自建**差分：宿主路径 vs 上游路径（默认参数）逐位比 |
| **T-C ❌ 不做** | **改公式 / 改约定 / 改默认容差 / 改迭代上限**（例：把 MJ 的 `+z` 极轴改成 `+Y`） | **红** ⇒ **资产作废** | 必须自建整套替代验证。**不值得**——见 §9.2 |

**另两条不变**（与本次裁定不冲突，它们是**架构**裁定不是"保护上游"）：
- **K1**：`ODE/` 是验收层的数值参照、**不许接进物理步或规划路径**；生产传播权威仍是 `NBodyIntegrator.ThirdOrderTaylorStep`。
  本批**不新增第二条传播链**。
- **K2**：移植面**只能在 net48 编译**（`Angles.cs` 靠 net48 没有 `Math.Asinh` 才通得过）；不许链进 net8 工程。

> ⚠ **T-A 的边界要说清**：`Math.Pow(x,2.0) → x*x` **不算 T-A**——`pow` 是否特判 `y=2.0` 不是 CLR/CRT 保证，
> 而目标运行时是 Unity/Mono 的 libm ⇒ 属**待实测**（§3-F）。`x*x*x` 替 `Pow(x,3.0)` 同理。
> **可证的只有 `Statics.Powi(x,3)`**（平方-乘序 = `(x*x)*x`，与 C# 同结合序）。


> ⚠ **台账 P26 的既有裁定同样有效**（`性能优化待办2026-09-09.md` 末段，原话）：
> "**P26 是为正确性买的时间**（方向量化会吃掉不变量 1%、e 数倍），**不要为了省它把节拍改回去** ✗ ——
> 真要省，应改成『**只在方向变化超过阈值时重算**』（保正确性、降频次），而不是退回固定节拍。"
> ⇒ 本批次对 P26 的处置**只许做"让每次调用更便宜"，不许动刷新节拍**；"按阈值重算"是台账指定的形态，要做必须单独一条、且不带第二机制。

### 0.3 三类改动（本批唯一的分类轴；照 `先照 MJ、创新放最后` + `别让能用的基干丢在对小处的打磨里` 两条既有裁定）

| **偏离** | 会改变数值（哪怕只是末位）、或改变结构选择的 | **不做** | 要做必须有**实测数字 + 回撤点 + 就地标注**；出现"以前能、现在不能"⇒ **先撤偏离、还原基干** |

**本批 90% 是「修」。** 偏离项集中在 §3-F，**默认全部不做**，登记只为让下一个会话不必重新发现它们。

> ⚠ **尖峰不跨轮复现**（均值可复现、峰值不可）：比较只能用**同场景同机器**，且要带 `最慢 / 第N步 / t=`。

## §8 另一条线：表示层一致性（**不是性能批**）

> 起因：用户 2026-09-26 问"各种变量类型和左右手系转来转去也可能造成管理混乱，我们有这种情况吗"。
> 结论：**有，但混乱不在"手性"上**——手性那一半已被实测结清（§8.1）。真正的混乱是
> **一个类型扛多个系、同一个系有多个名字、同一对换算有多份实现**（§8.2），且**已经付过账**（§8.3）。
> **本条线与性能批严格分开**（`不夹带第二机制`）：唯一交集是 N2（见 §8.5）。

### 8.1 先结清：手性不是问题（省得以后再去查一遍）

- **`V3` 与 `DVector3` 同为右手系 XYZ 双精度、纯字段、无 swizzle**（逐字段比对，`P-1适配层决策-20260917.md:234`）。
  R1 原名登记为"手性/轴约定"，实测把它拆开了：**向量表示这一半不成立**；剩下的只是"参考系旋转方向"，
  而它被互证台钉住（`MechJebLibPortTests.R1_RotationSense_IsRightHanded_ForPortedCode`，含反向对照 + 上游 `DP5` 独立复核）。
- **`GameWorldToAdapter` 是正常旋转，det = +1，不翻手**：`x→x, y→z, z→-y`（`OrbitView.cs:202`）——
  它做的是"游戏 +Y 极轴 → 适配层 +z 极轴"。**真正的"换手"在上游的 `MechJebLibBindings/` 里（`vector.xzy.ToV3()`，det = −1），而我们故意没移植它**（`MechJeb参考大修计划-20260917.md:68`）。
- ⚠ **登记一条口头债**：R1 的**名字**（"手性"）与实测结论（"只是极轴不同"）已经不一致 ⇒ **谁按名字去查会查错方向**。
  建议在 R1 登记处就地加一行更正（属文档修，不属本批）。

### 8.2 真正的混乱：五个"名字说了谎"的结构

| 形态 | 实例 | 为什么危险 |
|---|---|---|
| **一个类型扛三个系** | `DVector3` 同时是：系统系（`CurrentOrbit.position`）· 天体局部系（`localPosition`）· **适配层系**（`Gooding.Solve` 的入参与返回、`OrbitAdapter.ToD`） | 编译器帮不上忙。`Gooding.Solve(double mu, DVector3 r1, DVector3 r2, …)`（`Gooding.cs:40`）**签名里没有系**，而类型名暗示"这是通用向量"⇒ 新调用点传游戏系值会静默拿到错的 Lambert 解 |
| **同一规则写多份** | "非行星 → `GetBodyLocalPosition`；行星 → 零"这条规则 + `GetComponent`→`GetBodyById`→`bodyType` 那串查询，在 `SpaceEntityGroup.GetCentralBodyOffset/Velocity`（`SEG:1304-1333`）与 `SpaceGameComp.GetBodyWorldOffset/GetBodyWorldVelOffset`（`SGC:4700-4717`）**各写一遍**（另有 `CelestialBodyManager.AccumulateToRoot` 疑似第三份，未核） | 改一处漏一处 ⇒ 静默不一致。⚠ 讽刺的是 `GetBodyWorldOffset` 的 doc **自己在讲纪律**（"换系只准有一处，不许复制一份"）——**它在论证纪律的同时又拷了一份** |
| **同一个系有 4–6 个名字** | 系统系 / 群组系 / 群组坐标系 / 行星参考系 / 根系 / 地心系 | 读者无法从名字确定一个量在哪个系，只能靠 doc block |
| **同一个词有多个意思** | `*World*`：`GetBodyWorldPosition`=**绝对**、`GetBodyWorldOffset`=**系统**；`*Unity*`：①系统系 Unity 单位 ②视图系 ③纯标量单位；`local*`：`localPosition`=天体相对、`SpacePart.localPosition`=船体局部 | 三个词各扛两三种意思 ⇒ "看名字猜系"必然猜错 |
| **同一接口名两种系** | `ISpatialEntity.Position`：`SpaceEntityGroup.Position`=系统系；`SpaceEntity.Position`=船体局部偏移 | 同名成员、两个实现、两个系 |
| **两套单位尺度并存** | 世界覆盖层 1 unit = 50 km（`SpaceConstants:9`）；船检查器 1 m = 0.1 unit（`PFView:25`） | 同一个"Unity 单位"在不同窗口里量纲不同，`RadiusToSphereScale` 因此不能跨窗口复用 |

用户裁定"全用 `DVector3`"之后，最自然的推论是"那 `V3`（也是 double）也一起收掉，全库只剩一个矢量类型"。
**已实测：不划算，否决。** 两条硬阻塞：

1. **6 个方向常量在两个类型里是正交的，不是同号异号。** `V3.up=(0,0,−1)`·`forward=(1,0,0)`（MJ 的 NED 约定）vs `DVector3.up=(0,1,0)`·`forward=(0,0,1)`（游戏世界 Unity 约定）——
   **同一个名字装不下两个值**。强行统一 ⇒ 要么改 6 处活的移植物（`Astro.cs:666` · `Simple.cs:135` · `Q3.cs:206` · `Q3.cs:214`）**并让 `Q3.LookRotation` 的默认 up 静默换向**，
   要么改 **49 处**用 `DVector3.up` 当游戏极轴的地方。**两条都会改数值。**
2. **名字 `V3` 删不掉**：约 40 个上游测试文件 / 2773 个 `V3` 记号引用它，且它们在"不得就地修改"的护栏下（`MechJebLibTest.csproj:16`）。
   ⇒ 只能用 `global using V3 = …` 别名，而 `global using` 要 **C# ≥ 10**，`MechJebLibTest` 被钉在 **LangVersion 8**（模拟上游形状）⇒ **要改那个 csproj 的形状**。

**另外**：约 **55 个成员**要从 `V3` 搬进 `DVector3`（机械），但其中 **4 个必须重定义**（`normalized` 的 NaN 分支 · `Normalize()` 的 NaN/次正规 · `Equals` 的 **NaN 语义** · `ToString` 的 `[G17]` vs `(F3)`），
而后两个**正是上游测试断言的对象**（`EqualityHashingTests:54-61` 断言 `NaN.Equals(NaN) == true`；`StringRepresentationTests` ~25 条断言 `[1.5, 2.5, 3.5]`）。
⇒ 按 §0.2 的分档，这是 **T-C**（改约定 ⇒ 上游红），而**它的收益是纯概念性的、数值与性能收益为零**。

⇒ **结论：不做。** `V3` 的正确处置是**关在边界里**——而这恰好是本库 **2026-09-18 已有的裁定**：
`OrbitView.cs:19-20` 原话：*"按用户 2026-09-18 裁定，本类型内部用 MJ 的 `V3`（**`DVector3` 是明确目标**，见 P-1 §3.1 的迁移债）。**`V3` 只许出现在本类型及其构造工厂里，不得渗进我们自己的代码。**"*
⇒ 那正是 **§11.3 S2（封边界）**。**用户这次要的是 float/double，不是 V3/DVector3**；`V3` 与 `DVector3` **都是 double**，不构成"同时存在 float 和 double"的问题。

### 11.8 小结：哪些"消除歧义"其实是把它藏起来（**不许做**）

1. **给向量加一个运行时"系别"字段**（或在字典里记一份）——那是把**编译期**问题推到**运行期**，编译器仍然不查，事故照旧。
2. **靠注释/文档说明系别**——本库现行做法，**已被 6 次事故证伪**。
3. **两条路都留着，加一个开关**——两个权威 + 一个开关 = **三份**歧义（本库在"新旧交会律"上刚付过这个学费）。
4. **把显式转换改成隐式转换**——见 §11.4。
5. **给"死活不明"的东西加一个 `#if` 或默认关闭的开关**——那是把"该删的"变成"待定的"，正是用户点名的屎山。

## §12 `V3` 与 `DVector3` 统一（**用户 2026-09-26 裁定；本节是施工方案**）

> 用户原话：**「我还是希望 V3 和 DVector3 可以统一。」**
> §11.7 的原判「否决」**已撤回**——它错在把「两个名字装两个值」当成了「两个概念不可调和」。**这个统一能做，而且能让上游 6193 条仍全绿。**

### 12.1 为什么可以做（三条纠正）

**纠正一：常量冲突靠「改我们的名字」解决，不必动上游断言。**
`V3.up/forward/…` 是 **NED / 船体姿态**约定，`DVector3.up/forward/…` 是 **游戏世界极轴**约定——**两个概念共用一个名字**。
⇒ **`V3` 那一套的名字与值原样保留**（`ConstantDirectionalVectorTests` 的断言**仍全绿**），
把**我们的**世界轴常量改名成 `worldUp` / `worldForward` / `worldDown` / `worldLeft` / `worldRight` / `worldBack`（**49 处，纯改名、零数值变化**）。
`DVector3.forward` 在宿主里只当「退化时的备用轴」用（`CelestialBodyDef.cs:79` · `SpaceEntityGroup.cs:1419-1425` · `CombatManager.cs:2102` · `SteeringController.cs:103`），
改名成 `worldForward` 后那些 `|radialDir.y| < 0.9 ? up : forward` 的**分量判据依然成立**（世界极轴仍是 +Y）✅

**纠正二：4 个「必须重定义」的成员——让 `V3` 的语义赢，上游断言就仍全绿。**

| 成员 | 现在的 `DVector3` | `V3`（**采用这个**） | 上游断言 |
|---|---|---|---|
| `Equals(T)` | `x == other.x && …`（**NaN 判不等**） | `x.Equals(other.x) && …`（**NaN 判相等**） | `EqualityHashingTests:54-61` 断言 NaN 相等 ⇒ **采用 V3 后仍绿** |
| `ToString()` | `(1.500, 2.500, 3.500)`，当前文化 | `[1.5, 2.5, 3.5]` + `IFormattable` + `G17` 不变文化 | `StringRepresentationTests`（~25 条）⇒ **仍绿**（宿主调试输出格式会变，无害） |
| `normalized` | NaN→NaN · 次正规→`zero` | NaN→`zero` | — |
| `Normalize()` | NaN 保持 · 次正规不动 | NaN→`zero` · 赋值 `this` | — |

⇒ **这个统一可以做到「上游 6193 条全绿」** ⇒ 按 §0.2 的分档**实质上是 T-A 类**，**验证资产完好**。
（§11.7 原判 T-C，是因为预设了「我们的语义赢」；**让上游赢，那个代价就不存在**。）

**纠正三：名字 `V3` 只需一个别名文件，上游测试源码一个字不动。**
`global using V3 = PioneerFramework.DVector3;` 放在**共享树**里（三个工程都编 `ThirdParty/MechJebLib/**`）。
代价是 `MechJebLibTest` 的 `LangVersion` **8 → 12**（`csproj` 形状变了，**测试源码没变**）。
`global using` 要 C# ≥ 10，而 net48 上 C# 12 完全可用；上游测试源码在 C# 12 下向后兼容。

### 12.2 四步迁移（**每步一次闸门；任一步红灯就回滚这一步**）

| 步 | 做什么 | 判据 |
|---|---|---|
| **U1** | **先把我们的世界轴常量改名**（49 处 → `worldUp`/…）；**同批给旧名加 `[Obsolete(…, error: false)]`** ⇒ **编译器把每一处残留逐个列出来**（§10.3 的「让编译器守规矩」用在常量上）。⚠ 这个 `[Obsolete]` **只在 U1 存在**，U2 必须移除（U2 之后 `up` 合法地属于 V3 语义） | 0 错；**警告数 = 544 + 本批新增的 Obsolete 警告（要记账，不许当成「新增警告 0」）**；纯 231 / 集成 119 / 移植 6193 **不减** |

### 12.3 ⚠ 对 §11.3 Stage 3 的连带影响（**必须一起改设计**）

§11.3 的 Stage 3 原写「**适配层系仍是 `V3`**」。**统一之后 `V3` 就是 `DVector3`，这条不成立**——
「适配层系」不再自带一个类型。

### 12.4 统一之后白拿的两件（一条收益，一条护栏）

1. **62 个 `ToV3`/`ToD` 调用点消失**——连「删它们」这个动作都不需要，它们失去了存在意义。
2. **上游 6193 条用例开始覆盖我们自己的 `DVector3`**——本库最贵的那份验证资产**第一次**延伸到这个类型上。
   ⚠ 反面同理：**从此 `DVector3` 的任何改动都可能弄红上游用例** ⇒ 既是收益，也是护栏。

## §13 坐标系规则统一到 **+Y**（**用户 2026-09-26 裁定；本节是施工方案**）

> 用户原话：**「我希望的是我们的所有坐标系规则都统一，不要有的是 y 朝上有的是 z 朝上。」**
> ⇒ 目标 = **全库一个极轴约定**。**方向选 +Y，不选 +z**，理由见 13.1——这是**转换最少**的那个方向，而不是"另一个折中"。

### 13.1 为什么选 +Y（一句话：**+Y 是唯一能让 RimWorld 边界零转换的方向**）

| 方向 | 极轴在哪几处是"外来的" | 边界转换 |
|---|---|---|
| **统一到 +z** | RimWorld 的 `GetTileCenter` · `CurSunPositionInWorldSpace` · `PlanetLayer` 球体全是 **+Y** ⇒ 必须在 **tile 入料 + 渲染出料** 永远各转一次 | **入料 4 处 + 出料 3~4 处，且落在"错一次就静默毁掉一切"的位置** |
| **统一到 +Y** ✅ | 只有移植来的 `Astro`/`Angles` 是 +z（**那是我们可改的**）⇒ 改完**没有任何一处需要转** | **零** |

**统一到 +Y 之后**：`OrbitView.GameWorldToAdapter`/`AdapterToGameWorld`（`OrbitView.cs:202/205`）**变成恒等** ⇒
**41 处散落表达式 + 这一对函数整体消失**，§11 的 A1/A3 那两类"混系"歧义**在结构上不存在了**（不是"小心地用"，是"没有第二个系"）。

### 13.2 施工清单（已实测；**17 个 +z 位点里 12 个是干净的换元**）

**A. 干净的换元（`Astro` 里）**：`northpole → (0,1,0)`（`V3.cs:376`）· `IncFromStateVectors` `Acos(hhat[2])→Acos(hhat[1])`（`Astro.cs:203`）·
`LatitudeFromBCI` `r.z→r.y`（`:352`）· `EvecFromKeplerian`（`:49-51`）· `HunitFromKeplerian`（`:34`）· `RhatFromLatLng`（`:265`）·
`ECIToENU`/`ENUToECI` 两个矩阵（`:285-289`, `:369-373`）· `Simple.cs:135` 跟着常量走 · 宿主字面量若干。

**B. 四处必须小心（**这四处是全部的风险所在**）**：

| # | 位置 | 陷阱 |
|---|---|---|
| **B1** | `Astro.cs:707-760` `KeplerianFromStateVectors` 的**春分点块** | 🔴 **最危险的一处**：裸把 `[2]→[1]` **能编译、数看着也对、实际错**——`Ω=0,i=30°` 时给出 `lan=π` 而不是 `0`。`q` 要**变号**（`-hhat[1] → +hhat[2]`），`fhat`/`ghat` 要按 `(F0,F1,F2)→(F0,F2,−F1)` 重排。而它的输出**喂着每一个规划决策**（经 `OrbitView`） |

| **B3** | `Astro.cs:355` `LongitudeFromBCI` | 不是换一个分量：`Atan2(r.y,r.x) → Atan2(-r.z,r.x)`（方位基准 `+ŷ → −ẑ`） |
| **B4** | `V3.cs:389-409` `cart2sph`/`sph2cart` | 真把 `z` 当极轴参数化 ⇒ 是重写不是换元。**在本库是死代码** ⇒ 可删 |

**C. 🔴 一个必须点名的雷**：`V3.up/down/left/right/forward/back` **不是世界极轴**——它们文件里写明是 *"valid for vessel body orientations"* 的 **NED 船体约定**（`V3.cs:362`）。
**世界极轴统一不需要动它们。** 但今天 **`V3.down == V3.zaxis == V3.northpole` 三者同值 `(0,0,1)`** ⇒ **盲目的全局替换会静默改错一堆东西**。
⇒ 纪律：**这 6 个常量一个都不许碰**；只改 `northpole` 与"用作极轴的地方"。

### 13.3 测试迁移的成本（**实测，不是估**）

## §16 多核：怎么治（**用户 2026-09-26：「你的意思是我们的多核优化有问题？详细看看怎么治」**）

### 16.1 先定性：**架构是对的，漏的是"写面"**

并行区的**骨架没问题**，而且是有意设计的：`物理并行区只按索引写 physicsResultsScratch（组数与顺序步内稳定）`（`SpaceGameComp.cs:47`）·
`result.ActiveSlices = activeSlices`（`:1823`，主线程同一步内消费）· "累加冲量、主线程统一应用"（`:1826-1827`、`:2175-2177`）。
**唯一的硬跨核串行点是探针**（见 16.3），**没有 `lock`**。

出问题的只有一件事：**三类"不该在并行区里发生的写"漏了进去**。所以治法不是重写并行，而是：

> **把并行区的"写面"穷举出来，并让每一次写只允许落在三种合法形态之一：**
> **A 只写本迭代独占的**（`physicsResults[i]`、`group.*`）——已经在做；
> **B 预暖/预建**（把"第一次会写"变成"进并行区之前已经写好"）；
> **C 搬出并行区**（写变成"装进结果、主线程提交"）。

顺带一条**正面样本**（值得当范式引用）：`BodySampleCache` 是**故意**设计成并发安全的——不可变 `Sample` + 单次引用赋值，
`BodySampleCache.cs:10-26` 连历史撕裂事故都写在注释里。**新代码要写共享状态就照它写。**

### 16.2 逐条治法

#### R1 `systemMembersCache` 的字典写（**正确性**）

- **现状（我读过）**：`private Dictionary<int, List<CelestialBodyDef>> systemMembersCache`（`:18`）；`GetSystemMembers` 在 `:152` 读、**`:169` 写**；清在 `:86`（`EnsureInitialized`）。它从并行体内可达（`ComputeGroupPhysics → ComputeGroupFieldAccelJerk → CollectSystemSources → GetSystemMembers`）。
- **治法 = 形态 B（预暖）**：在并行分发（`:2201` / `:2208`）**之前**，对 movableGroups 里**每个不同的 `CelestialBodyId`** 各调一次 `celestialMgr.GetSystemMembers(id)`。
  **成本 O(不同根数)**（1–2 次），此后全程命中。
- **加固（防下一条）**：`GetSystemMembers` 加**开发构建断言**——若"当前在并行区内"且缓存未命中 ⇒ 报错。
  ⚠ "当前在并行区内"**必须用 `[ThreadStatic]` 标记**（在并行体首尾置位），**不能用 `static bool`（那本身就是竞态）**。
- **判据**：≥32 组场景反复跑，`GetSystemMembers` 的 miss 计数（加探针）在并行区内为 **0**；闸门全绿。
- **风险**：极低。唯一注意：预暖要在**同一 tick**上做（tick 变了缓存键不变——键是 rootId，不含 tick ⇒ 无此问题）。

#### R2 `PerfProbe.SliceBuffer` 的字典写（**只在探针开启时发生**）

- **现状（我读过）**：`sliceBufferByGroup` / `sliceGroupByBuffer` 两个普通 `Dictionary`（`:89`/`:94`），写在 `:253/262/275`，调用点是 `SpaceGameComp.cs:1584`（**并行体内**，门 = `if (PerfProbe.Enabled)`）。
- **⚠ 更正代理的一处错**：它说"全库无 `Remove` ⇒ 无界泄漏"——**不成立**：`Reset()` 里 `sliceBufferByGroup.Clear(); sliceGroupByBuffer.Clear();`（`:771-772`）。所以是"随会话内出现过的 group id 数增长、`Reset()` 时归零"，**不是无界泄漏**。
- **治法 = 形态 C，而且可以做得更省**：这个探针要检验的是**"每组独占一个 scratch 且身份恒定"**——**这件事根本不需要在多线程里做**。
  ⇒ 改成：**分发前**（主线程）扫一遍记 `(groupId → scratch 引用)`，**并行区结束后**再扫一遍比对。零竞态、零并行区分配，还少了并行区的字典开销。
- **判据**：`Mismatch("切片缓冲", …)` 与 `SliceBufferShared` 计数为 0；`[性能探针]` 汇总里该行为 0。

#### R3 + R4 诊断静态 + 工作线程日志（**一处结构性移动同时治两条**）

- **现状（我读过）**：`private static double BurnDiagNextTick`（`:2016`）在**并行体内被读-改-写**（`:1302` 读、`:1304` 写；另有主线程 `:2892`）；
  **并行体内有 8 处 `Log.Message`**：`:1406` `:1410` `:1426` `:1479` `:1524` `:1762` `:1791` `:1802`。
- **治法 = 把整个 `[燃烧·诊断]` 块（`:1302-1433`）搬出并行体**，放到**主线程结果应用循环**（`:2219`）里、在**该组结果被应用之前**。
- **⭐ 采样点为什么能保持（这条不搞清楚就会破坏一个用两轮实测换来的口径）**：
  并行体算的是**结果**，组的字段在应用循环之前**仍是本步开始时的状态** ⇒ 在应用循环内、**先跑诊断再应用该组结果** ⇒ 采到的仍是"本步累加之前"的状态 ⇒ **与现状同口径**。
  （`SpaceGameComp.cs:1320-1323` 那条"诊断在本步累加**之前**采样 ⇒ 模型也只积到上一步末（elapsed − 一步）"的注释，就是这条口径的来源；改完要把注释一并搬到新位置。）
- **附带收益**：静态节流变成单线程读写（无竞态、无不确定性）；8 处日志全部回到主线程（`Log.Message` 的正确用法本文件已有范式：`:1717-1726`、`:2297-2311` "装进结果、主线程打"）；
  重仪器（`TryToOrbitView` + 400 步 RK4）从并行区移到串行区——**但它 10 秒一次、有上界**，而且 P28 还会把它默认关掉。
- **判据**：`git grep -n "Log\." 在 `1288-1960` 区间内**归零**；≥32 组场景反复跑无异常、日志无乱序；`[燃烧·诊断]` 的读数与改前**逐字一致**（同场景对照）。

#### 那个 `Interlocked`（**不是竞态，但随 N 线性放大争用**）

- **现状（我读过，且代码注释自证）**：`PerfProbe.GravityClockEnd` 里 `Interlocked.Add(ref GravityTicksTotal, dt)` + `Interlocked.Increment(ref GravitySegments)`（`PerfProbe.cs:634-639`），
  调用点 `SpaceGameComp.cs:1211/1216/1223`，`bool timing = timeSegment;`，而两个物理步调用点都传 `timeSegment: true`（`:1862`、`:1912`）⇒ **常驻**。
  **代码注释自己写着**：*"★ 2026-09-20：引力场段计时改为**常驻**……成本 = 每组每子步两次 `Stopwatch` 读（纳秒级；**组数是个位数**）"*。
  ⇒ **它的成本论证建立在"组数是个位数"上**，而那正是用户 2026-09-26 推翻的假设。Fast 档下 = 2 × 8 = **每组每步 16 次原子 RMW**，全落在**同两行长**。
- **治法（仍是形态 A，因为结果数组每迭代独占）**：给 `GroupPhysicsResult`（已是 struct 数组，每迭代独占 `physicsResults[i]`）加两个字段
  `fieldTicks` / `fieldSegments`；并行体内只写 **自己那一格**（无 `Interlocked`、无共享行）；**主线程在应用循环里一次归并**进全局。
  ⇒ 争用归零，**读数口径不变**。
- **判据**：同场景同机器下 `[步耗时]` 的引力场段读数与旧值一致；**≥32 组时该段不再随组数上升**。

### 16.3 并行纪律：把"写面"从注释变成可检查的东西

现在并行区的规矩散在三处注释里（`:47`、`:1089-1098`、`:1826-1827`）。治法：

1. **一张显式清单**（并行区**允许**的写，只此三类）：① `physicsResults[i]`（含新加的计时段）② 本迭代持有的 `group.*` ③ 本迭代持有的 scratch（`gravityScratchByIndex[i]`、`group.thrustSliceScratch`）。
2. **`#if DEBUG` 并行区守卫**：进并行体前把 `[ThreadStatic] inRegion = true`，出后置 false；
   在**所有已知的共享写路径**（`GetSystemMembers` 的写、`PerfProbe` 的字典写、任何 `Log.`）里断言 `!inRegion`。
   ⇒ **下一条漏进来的共享写会在开发构建里当场炸**，而不是靠人记得。
   ⚠ 这就是 §10.3「让编译器守规矩」在并发上的对应物；用 `[ThreadStatic]`（**不能**用 `static bool`）。
3. **把台账第 22 条"并行区零分配原则"扩写成"并行区零分配 + 零共享写"**（原文只说了分配；R1/R2/R3 都是"零共享写"的违例）。

## §18 显卡能不能加速轨道机动自动规划（**用户 2026-09-26 提问；本节是讨论，不是施工单**）

### 18.1 本库已经就"GPU"裁定过一次，但对象不同

- **已有裁定（感知层，§1.8[O]）**：**拒用 GPU**，理由 = 规模差 2–3 个数量级 · readback 架构性 stall · 必须写两套 · 不确定性 · shader 不可测 · 全库零先例。
- **机动规划与感知层的差别**：感知层是每周期一次的小矩阵；**规划是"一次几百~几千个独立评估"** ⇒ 并行形状**确实比感知层好**。所以值得单独算一遍，不能直接搬那条裁定。
- **本轮核实的两条事实**：① **GPU compute 零先例**——全库 `ComputeShader` 0 处、`.compute` 文件 0 个；② **但渲染侧 shader 管线有先例**（`tools/PFViewShaderBundle/` 自带构建与断言脚本 + `PFViewMaskOutlineRenderer.cs`）⇒ "加 shader"这件事在工程上不是从零，"用 GPU 做通用计算"才是从零。

### 18.2 先算工作量（这一节基本就决定了答案）

| 规划入口 | 并行元素数 | 单元素内容 |
|---|---|---|
| `TwoImpulseTransfer` 多起点 | **12 个种子**（`TwoImpulseTransfer.cs:257-268`） | 每个 = 一次 `CompassSearch`（≤60 sweeps × ≤6 evals） |
| `ChangeOrbitalElement` θ 粗扫 | **180 个方向**（`:173-182`） | 每个 ≈35 次要素求值 |
| `PlanRecovery` 网格 | **360 格**（`RendezvousCore.cs:163-209`） | 每格 1 次 `Gooding`（≤200 级数 + 12 步 Householder） |
| 点火相位扫描 | **7 档**（`SpaceGameComp.cs:2703`） | 每档 400 步 RK4 |
| **合计** | **10¹ ~ 10³ 个元素**，总算术量约 **2–3 × 10⁷ double flops**；单核**实测 5.4–8.3 ms** | |

**GPU 值得用的门槛**（经验值）：**≥10⁵ 个"均匀"工作项**，且**每次派发的活 ≥1 ms**。
⇒ 我们**两个条件都不满足**：元素数是 10¹–10³（差 2–3 个数量级），而且下面 18.3 说明它们**天生不均匀**。

### 18.3 五条硬障碍（前三条是决定性的）

1. **🔴 数据相关的收敛循环 = GPU 最坏的形态。**
   `Shepperd`（外层 `for i < imax=50` + 内层 `while (gcf != gold)`）· `Izzo`（≤35 轮 Householder + 收敛判据）· `Gooding`（≤200 级数）。
   **每个元素迭代到收敛为止** ⇒ 一个 warp 里的线程各自跑不同轮数，**分支发散把吞吐优势吃掉**。
   GPU 擅长"每个元素做同样的常数工作量"，最不擅长"每个元素各自迭代到收敛"。
2. **🔴 双精度。** 全库（含移植的 `V3`/`DVector3`）是 **double**。消费级卡的 **FP64 常常只有 FP32 的 1/32 ~ 1/64**。
   ⇒ 就算把 2–3×10⁷ flops 交给 GPU，实际吞吐可能**低于 8 个 CPU 核**。
   （要换 float 才快——而那会改数值，正是本计划全局禁止的那件事。）
3. **🔴 确定性。** 本库整套验收方法是"**逐位不变 / 同场景同机器前后对比 / 影子校验 / 确定性构建**"（§4.1 腿一）。
   GPU 的归约顺序不定、且**随厂商与驱动变化** ⇒ **这些仪器全部失效**。规划器会从"最可测的模块"变成"唯一没法测的模块"。
4. **readback 延迟**（次要）：同步读回要 stall；异步则至少 1 帧。规划是 30 s 节流、每次一调 ⇒ **1 帧延迟其实可以接受**。
   ⚠ 所以**这条不是主要障碍**——我在上一版里把它当主因是错的；真正拦住的是第 1–3 条。
5. **必须写两套 + 不可测**：kernel 无法单步、无法打日志；而两个纯测试工程是**无 Unity 的 headless**（本库有 `ViewFrame.cs:96-105` 的 ECall→`SecurityException` 先例）
   ⇒ 规划器会**失去全部测试覆盖**。而规划器恰恰是本库测试最密的模块（33 用例仿真 · `RendezvousLadderTests` · `TwoImpulseTransferTests` · `A4_CostProbe`）。
   ⇒ 违反本库"**唯一权威**"（第二份实现）与"**可判定判据**"两条纪律。

### 18.4 唯一诚实的 GPU 形状（如果将来真要）

**满足"≥10⁵ 均匀元素 + 单精度可接受 + 允许不确定 + 异步消费"四项的，只有这两类：**

1. **密集多起点网格**：把 `(t, dt)` 铺成 10⁴–10⁶ 格，每格一次 Lambert，**只回传 argmin**（单标量结果，无逐元素 readback）。
   ⚠ **但那是换算法**（现在是 12 种子的模式搜索），而且台账**已实测否掉过一次同类捷径**：*"闭式 τ 再在窗口上求解" = **11.88 ms vs 直接 5.55 ms***。
   ⇒ 要动必须先证明"换算法后答案不变或更好"，不是"换个硬件跑同一套"。
2. **出发窗口热图（porkchop 式）**：给 UI 显示"什么时候出发便宜"。这是**规划辅助的可视化**，**不改规划器**，而且它的输出本来就是给人看的、不需要逐位可复现。**这是本库唯一"GPU 天然合适"的规划相关形状。**

### 18.5 ⭐ 如果真要用显卡，正确目标是**渲染侧**（数字支持，且已有先例）

- **事实（我核过）**：`DrawOrbitPath`（`SpaceGroupVisualManager.cs:724-738`）**每个点一次 `Graphics.DrawMesh`**（`:736`）；
  采样数被夹在 `[36,180]` ⇒ **一条轨道线每帧最多 180 次 draw call**；`:378`/`:760`/`:839` 是同一形态的逐标记绘制。
- ⇒ **本库每帧真正贵的是 draw call，不是数学**（§17.5 已判）。而 draw call 的替代方案（**一个程序化 mesh / 实例化 / GPU 端顶点生成**）
  正是 GPU 天然擅长的形状：**均匀 per-vertex、无分支、单次提交、无需 readback、不参与确定性判据**。
- **而且本库有基础设施先例**：`tools/PFViewShaderBundle/`（构建 + 两个断言脚本）+ `PFViewMaskOutlineRenderer`。
  ⇒ 这条路的"从零"程度远低于 compute。
- **判据**：`[帧耗时]`（µs 口径）同场景前后对照 + draw call 计数（现在 ≤180/轨道/帧）。

### 18.6 结论

| 问题 | 答案 |
|---|---|
| 机动自动规划能用显卡加速吗？ | **不能，不建议。** 元素数差 2–3 个数量级 · 数据相关收敛（分歧） · 双精度（消费卡 FP64 1/32–1/64） · **确定性验收全废** · 必须写两套且失去测试覆盖 |
| 那该怎么做？ | **CPU 并行那几个 10¹–10³ 的独立项**（§17.4 #1–#5），再叠加 §17.6 的**结构降阶**。零风险、保住全部验收仪器、8 核约 8×，且**不需新硬件假设** |
| GPU 值得投在哪？ | **渲染侧的批绘制**（§18.5）——那是"乘帧率"的成本，形状对、有先例、不碰确定性 |
| 可复用的判据 | GPU 值得用 ⇔ **≥10⁵ 均匀工作项 · 单精度可接受 · 允许不确定 · 异步消费**。**规划器四项全不满足；本库物理/规划侧没有任何一处满足前三项。** |
