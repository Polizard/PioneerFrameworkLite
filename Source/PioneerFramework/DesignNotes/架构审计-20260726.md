# PioneerFramework 架构审计

> 审计日期：2026-07-26
> 审计范围：全项目源码
> 目的：找出真实存在的架构问题，不分轻重，一个不放过

## 严重问题（Bug / 会导致错误行为）

### 1. PFView 轨道绘制二次缩放

**文件**: `Source/PioneerFramework/PFView/MainTabWindow_PFView.cs`  
**位置**: `DrawOrbitLinesGL` 方法（约 L946-L955）

轨道点数据从 `GetOrbitPathUnity` 获取时已经是 Unity 单位（内部已乘 `UnitsPerMeter = 1/50000`），但在 `WorldToView` 中又被乘了一次 `MetersToView = 0.1`。同一个量被两个不同的缩放因子处理，产生错误渲染结果。

```csharp
// 问题代码示例
Vector3 a = WorldToView(new DVector3(
    pts[i].x * SpaceConstants.MetersPerUnit, ...
// pts[i] 已经是 Unity 单位，又乘了一次 MetersPerUnit
// WorldToView 内部又乘了 MetersToView，三重缩放
```

**根因**: 坐标链中 "米→Unity" 的转换分散在多个位置，缺少统一入口。

### 2. 两个 3D 视图缩放因子不统一

| 视图 | 常量 | 1 Unity = |
|------|------|-----------|
| `MainTabWindow_PFView` | `MetersToView = 0.1` | 10m |
| `Window_SpaceBattleView3D` | `SpaceConstants.UnitsPerMeter` | 50,000m |

两处相差 **5000 倍**。同一飞船在两个视图中渲染尺寸完全不同。这不是功能不完整，是两个视图各自定义了独立的缩放常量，从未统一。

### 3. Morton3D 越界静默返回 0

**文件**: `Source/PioneerFramework/SpatialIndexing/Morton3D.cs`  
**位置**: `Encode` 方法（L21）

```csharp
if (x < 0 || x >= MAX_DIM || y < 0 || y >= MAX_DIM || z < 0 || z >= MAX_DIM)
    return 0;
```

坐标越界时不报错，返回 0（原点格子）。多个越界的 Part 会被压缩到同一个格子，产生幽灵碰撞。这是调试噩梦——错误只在特定飞船尺寸和射弹轨迹下才会触发。

**建议**: 至少加 `Log.Warning`，最好在构建 Morton grid 时就拒绝越界的 Part。

## 高优先级问题（设计缺陷 / 会导致长期维护成本）

### 4. DVector3 隐式转换到 Vector3

**文件**: `Source/PioneerFramework/Base/Core/DVector3.cs`  
**位置**: L81

```csharp
public static implicit operator Vector3(DVector3 v)
```

双精度是整个坐标系统的核心设计目标，但这个隐式转换让任何地方都可以无警告地将 DVector3 截断为单精度。编译器不会帮你找到这些精度泄漏点。

**实际影响**: `TargetingSystem.EngageTarget` 中位置被直接 cast 到 `float`，在 10^9 米尺度上引入 ~64m 量化误差。

**建议**: 删除隐式转换，改为显式方法 `ToVector3()` 或 `ToVector3Precise()`，强制调用方明确表示接受精度损失。

### 5. 战斗缓存 CombatCache 在战斗期间从不更新

**文件**: `Source/PioneerFramework/Base/Game/TimeScaleManager.cs`  
**位置**: `InitializeCombatCacheIfNeeded`（L324）

进入 Combat 模式时计算一次加速度和急动度，存入 `PhysicsStateCache`。整个战斗期间——无论飞船如何机动变轨——缓存值不变。插值用的是进入战斗瞬间的加速度，随时间越插越歪。

**建议**: 每次物理步进时重新计算缓存，或改用不依赖缓存的插值方案。

### 6. `OrbitMath.GetWorldDeltaV` 不接受 `mu` 参数

**文件**: `Source/PioneerFramework/Base/Orbital/OrbitMath.cs`  
**位置**: `GetWorldDeltaV` 方法

该方法计算 R/T/N 基向量时硬编码使用 `OrbitMath.GM`（主天体的引力参数）。如果飞船绕火星飞行，调用者即使传入了火星的 GM，该方法也会用地球/太阳的 GM 来推导角动量方向。

**建议**: 给 `GetWorldDeltaV` 增加 `mu` 参数。

### 7. `SpatialGrid3D.ApplyChanges()` 是空方法

**文件**: `Source/PioneerFramework/SpatialIndexing/SpatialGrid3D.cs`  
**位置**: L171

```csharp
public void ApplyChanges()
{
    // 空实现
}
```

惰性 GC 方案（600 tick TTL + 每 tick 回收 1/20）的设计文档写得完整，但实现从未完成。粗网格在运行期间持续膨胀，从未被清理。

**建议**: 实现该方法，或如果粗网格不需要 GC（cell 数量少且固定），直接删除整个 emptyQueue 机制。

## 中等问题（过度工程 / 设计冗余）

### 8. RendezvousPlanner 中 AutoSweepTransfer 扫参范围可能遗漏最优解

**文件**: `Source/PioneerFramework/Base/Orbital/RendezvousPlanner.cs`

~~*(已订正：RendezvousPlanner/OrbitTransferPlanner 均有 UI 接入，Gooding Lambert 在交会规划中正常使用，非死代码。)*~~

`AutoSweepTransfer` 目前在 `departureDelay ∈ [0, 1]`（归一化到轨道周期）和 `transferTime ∈ [0.1, 2.0]`（归一化到最小转移时间）的 2D 网格上搜索最小 dV。当目标与自身在同一轨道上（相位角极小）或异面转移时，最优解可能落在这个网格之外。网格的采样密度（当前每维 20 步）也可能错过尖锐的 dV 谷值。

**建议**: 检查扫描范围是否覆盖所有合理转移场景，考虑在最小值附近局部细化。

### 9. RendezvousPlanner/OrbitTransferPlanner 的离开和到达机动使用硬编码倒计时

两个规划器使用 `executeTick = departureTick = Find.TickManager.TicksGame + delayTicks` 硬编码机动执行时刻。如果玩家在规划后暂停或变速，实际执行可能不是预期的时机。这是功能性的——队列在 displayTick 到达时执行——但缺少"距机动还有 X 秒"的用户反馈。

**建议**: 在 ManeuverQueueWindow 中显示倒数计时（已有部分实现），并添加机动到期的 UI 通知。

### 10. 时间缩放命令队列过度工程

**文件**: `Source/PioneerFramework/Base/Game/TimeScaleManager.cs`  
**规模**: 约 200 行

`Queue<TimeScaleCommand>` + 延迟执行 + `CanExecuteNow` 检查构成了一套完整的命令队列系统。实际场景中：
- 非战斗下命令立即执行，队列深度从不超过 1
- 是单生产者单消费者场景
- 可以用两个变量代替整个队列

**建议**: 简化为直接状态切换 + 一个 `pendingCommand` 字段。

### 11. ThreadSafety 目录对单线程项目过度武装

**目录**: `Source/PioneerFramework/ThreadSafety/`  
**规模**: 8 个文件、约 1000 行

包含 `RaceConditionDetector`、`FMA支持检测`、`压力测试`、`性能基准` 等。项目中唯一的并发操作是 `SpaceGameComp.UpdateAllMovements` 中的一次 `Parallel.ForEach`（标准用法，写入 `ConcurrentBag`，主线程消费，无竞态风险）。

**建议**: 删除 `RaceConditionDetector` 和相关压力测试代码。保留 FMA 检测和性能基准（可能有实际用途）。

### 12. SpatialGrid3D 和 CombatGrid 的重复模式

两个类有几乎相同的结构（Dictionary 存储 + Queue 延迟 GC + DebugPrintStats），但没有共享接口或基类。是复制粘贴衍生。

**建议**: 提取公共抽象，或如果 SpatialGrid3D 确实不需要 GC（见问题 7），则让它显式声明自己不需要 GC。

## 低优先级问题（命名误导 / 文档偏差）

### 13. "N 体摄动"实为限制性多体

**文件**: `Source/PioneerFramework/Base/Orbital/NBodyIntegrator.cs`

`MultiBodyAccelJerk` 只遍历主天体和主天体的卫星。其他行星和恒星的引力摄动全不算。这是"限制性 N+1 体"而非"N 体"。

**建议**: 重命名为 `RestrictedMultiBodyAccelJerk` 并在注释中明确说明限制范围。如果将来需要真正的 N-body，再扩展。

### 14. `SpaceEntity.Position` 与 `SpaceEntityGroup.Position` 语义冲突

两者都实现 `ISpatialEntity`，但：
- `SpaceEntity.Position` = Entity 在 Group 内的局部偏移
- `SpaceEntityGroup.Position` = Group 在世界坐标系的位置

通过同一个接口暴露但语义不同，粗网格中两种对象混合存储，`GetNearby` 对不同类型返回不同含义的结果。

**建议**: 将 SpaceEntity 从 ISpatialEntity 中移除，或让 SpaceEntity 返回世界坐标（组合 Group.Position + localOffset）。

### 15. 战斗重力缓存的加速效果可忽略

**文件**: `Source/PioneerFramework/SpatialIndexing/CombatGrid.cs`  
**位置**: `ComputeProjectileGravity`（L249-L275）

缓存只缓存了重力源列表（不缓存位置），每次仍重新计算每个天体的具体位置。`GetGravitySources` 就是一个简单遍历，缓存带来的加速微乎其微，但增加了代码复杂度。

**建议**: 要么缓存位置（需要确保 tick 对齐），要么去掉缓存，简化代码。

### 16. 炮塔旋转纯粹装饰

`WeaponInstance.UpdateTurretRotation` 使炮塔向目标旋转，但 `FireWeapon` 发射时完全忽略 `turretRotation`，直接用 `(target - spawnPos).normalized` 作为方向。

**建议**: 如果不需要物理约束，在注释中明确标注"仅视觉效果"。如果需要物理约束，让 FireWeapon 使用实际的 turretRotation。

## 教训

1. **双精度坐标的隐式转换是自己打自己脸**——如果架构的核心约束不能被编译器强制执行，架构就是纸面上的。
2. **审计也会犯错**——Gooding Lambert 经重新追踪确认在 `RendezvousPlanner → ComputeTransfer` 中被正常调用，RendezvousPlanner 由 `SpaceGroupVisualManager` 的"交会规划"按钮打开。整个链路（UI → Lambert → QueueManeuver → StartBurn → 三阶积分）是贯通的。
3. **多个视图中各自定义缩放常量必然导致不一致**——应该有且只有一个 `CoordinateTransform` 工具类。
4. **"以后可能用到的"框架代码（ThreadSafety、命令队列）是对当前代码的债务**——每行代码都有维护成本，无论它是否在执行。
