# 太空战斗性能优化 - 审计清单

> 审计日期：2026-08-04
> 审计范围：太空战相关算法（CombatManager / CombatGrid / TargetingSystem / ProjectileInstance / SpaceEntityGroup / SpaceEntity / SpaceGameComp 战斗路径）
> 目的：评估"航天器多格占用"方案的性能压力，找出战斗循环中的性能优化空间，逐项讨论后落地

---

## 结论摘要

1. **多格注册本身便宜**（一次性注册 + 射弹查询反而受益），**真正的固定开销来自"每 2 tick 全量重算 + 全量比较"**——即使船完全没跨格。
2. 战斗循环存在两类问题：
   - **GC 分配洪水**：每 2 tick 恒定分配 List/HashSet（武器重建、覆盖格列表、pair 去重、Morton 查询缓冲）；
   - **重复计算**：同一 tick 内圆轨位置被重复算 4~6 次（每次含 Cos/Sin + 天体字典链）。
3. 按性价比排序，前 4 项（per-tick 位置缓存 / 武器脏标记 / 覆盖格盒体化 / scratch 集合复用）预计可把每 tick 分配次数降一个数量级、重复计算减少约 70%。

## 一、多格占用的成本分析（核心关切）

### 现状

`CombatGrid.AddShip` 把船注册到其世界 AABB 覆盖的所有细网格格（20km/格），`shipCoveredCells` 记录每艘船的覆盖格列表。

### 成本拆解

| 环节 | 频率 | 成本 | 结论 |
|------|------|------|------|
| `AddShip` 注册 | 1 次/船 | AABB 计算 + 格枚举 | 可忽略 |
| 射弹查询命中 | 每射弹 | DDA 第一步即命中（船注册在全部覆盖格），`projectileQueryResults` HashSet 去重 | **收益**：跨格船不漏检，多格是高速射弹隧穿防护的前提 |
| `UpdateShipPosition` | **每 2 tick × 每艘移动船** | 重算 `GetGroupWorldBounds` + `CoverCells`（分配 List）+ `CellsEqual`（O(k²) Contains） | **主要固定开销**：与是否跨格无关 |

### 关键问题

- [CombatGrid.cs L136-L190](file:///d:/PioneerFramework/Source/PioneerFramework/SpatialIndexing/CombatGrid.cs#L136-L190) `UpdateShipPosition`：每 2 tick 无条件全量重算。母舰覆盖 40 格 → 每次 1600 次元组比较 + 1 个 List 分配。
- [CombatManager.cs L114-L162](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/CombatManager.cs#L114-L162) `SyncAllShipsToGrid`：每 2 tick 新建 `HashSet<int>`、对所有船调 `GetGroupPos`，仅为判断"是否跨格"服务，属于"为更新而更新"。

## 二、五大热点（按严重度排序）

### 热点 1：`UpdateWeapons` 每 2 tick 全量重建武器列表（最大 GC 元凶）

- **位置**：[CombatManager.cs L666-L695](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/CombatManager.cs#L666-L695)
- **问题**：每 2 tick 为**每个 group** `new List<WeaponInstance>()` + `AddRange` 后整体覆盖 `groupWeapons[groupId]`。武器只在部件变更时才变，却按固定节拍重建。30 艘船 = 每 2 tick 30 个 List 分配。
- **讽刺点**：`SpaceEntity.GetWeapons()` 已有缓存（`weaponsDirty`），此路径完全没用上。
- **方向**：脏标记触发重建 + 复用列表实例。

### 热点 2：`GetPhysicsTickSafe()` 每次都是 GetComponent 链

- **位置**：[TimeScaleManager.cs L119-L123](file:///d:/PioneerFramework/Source/PioneerFramework/Base/Game/TimeScaleManager.cs#L119-L123)
- **问题**：static 方法，每次 `Current.Game?.GetComponent<TimeScaleManager>()`。被 `GetGroupPos`、射弹更新、重力计算、圆轨查询到处调用，一个 tick 内调用几十次。
- **方向**：缓存组件引用。

### 热点 3：圆轨位置每次调用全量重算（三角 + 字典链）

- **位置**：[SpaceEntityGroup.cs L487-L519](file:///d:/PioneerFramework/Source/PioneerFramework/Base/Core/SpaceEntityGroup.cs#L487-L519) `GetCircularPositionAtTick`；[SpaceEntityGroup.cs L276-L305](file:///d:/PioneerFramework/Source/PioneerFramework/Base/Core/SpaceEntityGroup.cs#L276-L305) `GetCentralBodyOffset`
- **问题**：一个圆轨 group 每 2 tick 内该函数被调 **4~6 次**（SyncAllShips 1 次 → UpdateShipPosition 内部 1 次 → 碰撞 GetGroupPos 1 次 → GetGroupVelocity 1~2 次），每次 = Cos+Sin + `GetBodyById` 字典 + `GetBodyLocalPosition`（又是 Cos/Sin 链）。同一 tick 相同结果算 6 遍，无 per-tick 缓存。
- **方向**：per-tick 位置/速度缓存（键 = groupId + tick 戳）。

### 热点 4：`TargetingSystem` 每 tick O(N²) 全组扫描

- **位置**：[TargetingSystem.cs L38-L63](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/TargetingSystem.cs#L38-L63)
- **问题**：**每个真实 tick**（非每 2 tick）对每个 group 扫全部 group，每对调 `GetGroupPos`（三角+字典链）。30 艘船 = 870 次位置重算/秒。节拍与其他战斗逻辑不一致（2 tick）。`EngageTarget` 里每 tick 每 group 又 `new List` 收集武器（与热点 1 重复）。
- **方向**：降频（4~6 tick）+ 走粗网格 `GetGroupsInRange` + 复用列表。

### 热点 5：激光武器每发射一次线性扫全部船

- **位置**：[CombatManager.cs L1039-L1079](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/CombatManager.cs#L1039-L1079) `FireRayWeapon`
- **问题**：不查细网格，`foreach` 全部 group × 全部 entity 做 slab 测试。O(N×E) 每次开火。
- **方向**：复用 `CombatGrid.GetShipsNearProjectile` 走网格查询。

## 三、多格方案专项优化空间

- [x] **覆盖格盒体化**：`CoverCells` 始终产出完整矩形盒（minX..maxX × minY..maxY × minZ..maxZ），`shipCoveredCells` 无需存 `List<(int,int,int)>`，存 **6 个 int**（min/max 格坐标）即可。比较 O(1)，迭代时才物化。直接消灭"每 2 tick 分配 List + O(k²) 比较"。（✅ 2026-08-04）
- [ ] **格内列表去重**：`fCell.ships.Contains/Remove` 是 O(n) 线性扫描，同格多船时 O(n²)，覆盖格多时被放大。
- [x] **`EnumerateShipPairs` 的 `GetFrameId` 每格调用**：[CombatGrid.cs L271](file:///d:/PioneerFramework/Source/PioneerFramework/SpatialIndexing/CombatGrid.cs#L271) 每船每覆盖格调一次 `GetReferenceFrameId`（字典链），应提升为每船一次。（✅ 随 #3 完成）
- [ ] **DDA 3 步上限复核**：射弹最坏位移 = 速度 × 2s（2 tick），当前 20000m 格下安全（10000m/s 刚好一格）。未来若武器速度提升需重查上限。
- [x] **旋转保守放大 2 倍**（✅ 2026-08-04）：`SpaceEntity` 新增统一入口 `AabbHalfSize => BoundsSize`（半边长 = 整个 BoundsSize，覆盖任意旋转最坏投影），6 处 `BoundsSize*0.5` 消费方（CombatGrid.GetGroupWorldBounds、CombatManager 碰撞/球快筛/激光/命中检测、SpaceEntity.QueryRayHit 快速拒绝）全部改用该属性，避免局部不一致。

**方案**：group 懒缓存（键 = physicsTick，纯解析函数保证同一 tick 结果恒定）。

**改动文件**：

### Bug A：非圆轨目标射弹 100% 脱靶（高速弹隧穿检测失效）

**症状**：目标距射弹仅 800m，射弹却飞 100s/572km 脱靶；射弹实际飞行方向与瞄准方向相反（x 分量反）。

**根因**：[CheckSegmentGroupHit](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/CombatManager.cs#L320-L326) 目标参考系检测中，非圆轨目标的 `groupPosPrev` 直接取 `CurrentOrbit.position`（未回退上一步）→ "射弹世界位移 - 目标位移" 变成纯射弹世界位移。射弹继承 6000m/s 轨道速度，世界位移方向背离目标 → slab 检测永远不命中。圆轨分支用解析函数回退所以正常（此前测试用圆轨船未暴露）。

**修复**：非圆轨分支改为线性回退 `CurrentOrbit.position - velocity × (physicsTick - prevPhysicsTick)`（dt ≤ 2s，误差米级）。

### Bug B：射弹粗细网格双向泄漏（实体/射弹数量持续增长）

**症状**：细网格射弹 8→43、粗网格实体 2→13 持续增长，与 activeProjectiles（始终 0~1）脱节。

**根因**：`ProjectileInstance.LastCellCoord` 与 `fineCx/fineCy/fineCz` 共享存储。粗网格（1000km 格）`RegisterProjectileToGrid` 写入覆盖细网格坐标；细网格移动/删除用被污染的坐标删不掉旧格；粗网格注销读被细网格更新过的坐标也删不掉。ISpatialEntity 接口缺陷，双向践踏。

**修复**：[ProjectileInstance](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/ProjectileInstance.cs#L35-L45) 新增独立 `coarseCellCoord` 字段，`LastCellCoord` 不再映射到 fineCx，粗细网格坐标彻底分离。

### 验证方法（重新进游戏）
1. 非圆轨船对射 → 应出现 `[命中Part!]`/`[命中!]`，不再 100% 脱靶
2. `[网格状态]` 中 `弹灭` 应 ≈ `弹生`（细网格不再泄漏）
3. 粗网格 `实体=` 应稳定在船数（不再增长）

### Bug C：Combat 插值 2s 周期跳变（非圆轨目标仍脱靶的真根因）

**症状**：Bug A/B 修复后射弹能逼近目标（命中诊断距离 607m）但仍擦肩而过；非圆轨船 100% 脱靶，圆轨船正常；目标位置日志恒不变。

**根因**：[UpdateCombatInterpolation](file:///d:/PioneerFramework/Source/PioneerFramework/Base/Game/SpaceGameComp.cs#L885-L909) 中 `elapsed % 2.0` 取模循环，`CombatCache.dt=2.0` → 非圆轨目标的 `CurrentOrbit.position` **每 2s 跳回战斗开始位置**。射弹用连续物理位置，检测基准错位 → 相对位置突变 → 命中检测永远失败。圆轨目标 `GetGroupPos` 用解析位置（physicsTick 连续）不受影响，故此前圆轨测试正常。

**修复**：插值时间改为相对 `CombatCache.baseTick` 连续推进（去取模）；`t > dt` 时调用新增 `RebuildCombatCache`（以当前轨道状态重采样 acc/jerk，更新 baseTick），位置/速度连续无跳变。日志目标位置恒定是 2s 周期采样对齐的巧合，佐证了插值跳变。

### Bug C 深化：物理/渲染状态分离（万物统一物理时间步长）

**原则**：所有物理实体（船/射弹/天体）统一在 physicsTick 时间轴推进；渲染插值只是显示层平滑，**不得写回物理状态**。

**重构**：
- `SpaceEntityGroup` 新增 `RenderPosition` 属性（Combat 插值 / 圆轨解析 / 物理位置三态）+ `SetRenderedPosition` 内部方法。
- `UpdateCombatInterpolation` 插值结果只写 `SetRenderedPosition`，**不再覆盖 `CurrentOrbit.position/velocity`**——物理状态只由 `UpdateAllMovements` 在 physicsTick 推进，碰撞/射弹检测统一读物理状态，与射弹同基准。
- 渲染视图（Window_SpaceBattleView3D / Window_SolarSystemMap / Window_CombatTest 3 处）改读 `RenderPosition`；PFView 轨道图与位置对比日志保持物理基准（非战斗显示，物理更准）。
- 副作用收益：`RebuildCombatCache` 重建基准现在读的是真实物理位置（不再被插值污染），插值更准。

### Bug C 终局：目标参考系回退 dt 恒为 0（100% 脱靶真根因）

**症状（[命中调试] 日志铁证）**：`groupPos=(487366,...) groupPosPrev=(487366,...)` **完全相同**；目标船 AABB 半边长仅 140m（Ship3D 设计小船），射弹相对目标 431m，slab 偶发 HIT 但 QueryRayHit hits=0。

**根因**：[UpdateProjectiles](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/CombatManager.cs#L211-L216) 先把 `proj.prevPhysicsTick` 覆盖为当前值，再调用碰撞检测 → [CheckSegmentGroupHit](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/CombatManager.cs#L326-L329) 里 `physicsTick - proj.prevPhysicsTick` **恒为 0** → `groupPosPrev = groupPos` → 目标参考系退化，`worldDir` = 纯射弹世界位移（被 6000m/s 轨道速主导、背离目标）→ 永远脱靶。**此前 Bug A 的线性回退因 dt=0 从未生效。**

**修复**：射弹新增 `prevUpdatePhysicsTick` 字段（更新前保存旧值），回退改用 `dtPhysics = physicsTick - proj.prevUpdatePhysicsTick`；圆轨/非圆轨分支统一用此 dt。Normal 档行为不变（2s），Combat/Fast 档修正（0.033s / 16s）。

### Bug D：目标与炮口重合 → 卡膛弹（muzzle=0）

**症状**：[射弹生成] 日志铁证——`proj=2 (G2→G1) 位置=目标当前=瞄准点=完全相同，炮口速=0`。两船轨道接近到 <1m 时，`direction = (targetPos - spawnPos)` 零向量，`muzzle=0`，射弹只有船速无出膛速度 → 物理荒谬的"子弹卡在枪膛里"（射弹相对发射者速度 = 0 而非炮口速）。

**根因**：[FireWeapon](file:///d:/PioneerFramework/Source/PioneerFramework/Combat/CombatManager.cs#L1039-L1050) 未检查出膛方向有效性，重合时零向量归一化产生 muzzle=0。

**修复**：开火前计算 `aimDelta = aimPos - spawnPos`，`sqrMagnitude < 1.0`（重合）时跳过开火（不消耗冷却）；`weapon.Fire()` 移到方向检查通过之后。

## 附：射弹在飞自动降速 1/60（2026-08-04）

**需求**：有射弹在飞 → 时间流速自动降到 Combat 档（1/60，"子弹时间"）；射弹清空后恢复用户期望流速。

**实现**：
- `CombatManager.ManageProjectileTimeScale()`（每 2 tick 战斗循环末尾调用）：`activeProjectiles.Count > 0` 且当前非 Combat → `QueueCommand(ToCombat())`。**只降不升**，限频 60 tick（覆盖用户手动切走高流速，同时防 QueueCommand 刷屏）。
- `SpaceGameComp` 流速检查（每 240 tick）：新增分支——射弹在飞时**跳过恢复期望流速**，避免与降速逻辑打架（否则每 4s 会把 Combat 拉回 Fast）；射弹清空后走原恢复逻辑。

**行为**：射弹生成 → 1 秒内降到 1/60；射弹清空 → 最多 4 秒后恢复 DesiredTimeScale。射弹持续交火时保持 1/60。

### 四、经验教训（血泪，防止重蹈覆辙）

1. **先查射弹本身，再查命中检测**。"射弹不对劲"应该先看 `[射弹生成]` 的**出膛速度（muzzle，相对发射者）**——用户一句"子弹会卡在枪膛里吗"点破 muzzle=0 的卡膛 bug。本会话在命中检测上绕了 3 轮，漏看了 muzzle=0 的直接证据。
2. **参考系意识**：射弹继承 6000m/s 轨道速度后，世界系速度 ≠ 相对目标速度。检测必须在目标参考系做（射弹位移 - 目标位移）。两船相对静止时互相射击应该对称命中——这是判断检测对错的最快标尺。
3. **dt=0 陷阱**：`proj.prevPhysicsTick` 在碰撞检测**之前**被覆盖为当前值 → 回退 dt 恒为 0 → 修复代码从未生效。**任何"用差值做时间步长"的地方，必须确认字段在计算时未被覆盖**（新增 `prevUpdatePhysicsTick` 保存旧值解决）。
4. **单位/尺寸差异**：Ship3D 设计的小船（AABB 半边长 140m）vs 战斗测试船（3000m 级）——AABB 尺寸直接决定命中难度（射弹 431m 外对 140m 盒基本 miss）。排查时要先确认目标实际尺寸。
5. **圆轨测试掩盖非圆轨 bug**：早期测试全用圆轨船（解析位置走缓存），非圆轨分支（CurrentOrbit 直读）的 bug 一直没暴露。**测试场景必须覆盖两种轨道模式。**
6. **测试船不要重叠创建**：CompDebugShipSpawner 用 `DateTime.Now.Millisecond` 算角度，毫秒相同 → 两船完全重合 → 触发卡膛弹路径。测试应给船明显不同的轨道参数。
