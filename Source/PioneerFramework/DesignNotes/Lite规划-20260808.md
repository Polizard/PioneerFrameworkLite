# 先驱框架Lite（PioneerFramework Lite）立项规划

> 创建日期：2026-08-08
> 定位：本项目为「先驱框架Lite」的立项与边界规划文档，记录 Lite 与 master 的关系、范围、盘点结论与待决项。
>
> **状态标记**：同 MasterPlan（⬜ 待办 ｜ 🔵 进行中 ｜ 🟡 待验证 ｜ ✅ 已完成 ｜ ⚪ 已废弃）

---

## 1. 决策背景与原则

### 1.1 决策

鉴于先驱框架立项后的开发节奏，启动**先驱框架Lite**的编写：把当前**稳定的地月系部分**整理为 **DMS新边疆** 的前置，使玩家可以更早玩到新边疆。

### 1.2 原则性考虑（立项依据）

- **细心打磨优化算法** — 算法质量不妥协，物理/网格/性能优化持续精进。
- **实现更全面的功能** — 完整框架的功能覆盖面不减。
- **但让玩家不要等太久** — 通过 Lite 先行交付稳定闭环，完整框架继续在 master 演进。

三条原则的平衡点：**Lite 承担「尽早可玩」，master 承担「大而全」**。

### 1.3 与 DMS新边疆 的关系

- Lite 是**纯前置框架**（用户确认）：只提供地月系空间模拟能力，不含新边疆游戏内容。
- DMS新边疆 是独立内容 mod，依赖 Lite 提供的地月系能力。
- 玩家路径：Lite（前置框架）→ DMS新边疆（内容）→ 尽早可玩。

## 2. 仓库策略（已确认）

| 项 | 决策 | 说明 |
|----|------|------|
| 组织形态 | **独立新仓库** | 不共享 master 仓库，彻底解耦 |
| 代码来源 | 从 master 当前快照**一次性复制** | 冻结在稳定点 |
| 同步通道 | **切断**（不设 upstream、不自动 merge） | master 后续 commit 不流入 Lite |
| master 端影响 | **零改动** | 不新建分支、不改文件 |
| 移植机制 | 人工单向移植（仅用户主动要求时） | 关键修复/优化按需 cherry-pick 式移植 |

### 2.1 代价与边界

- **代价**：master 后续的 bug 修复、算法优化（如射弹多项式 O1、惰性宇宙 O2）不会自动流入 Lite。
- **边界**：两条线各自演进，互不干扰；只有用户主动要求时才做单向移植。
- **语义**：Lite = 稳定快照的「再发布 + 轻量维护」线；master = 持续研发线。

## 3. Lite 范围界定（用户确认）

### 3.1 纳入（已确认为可发布标准）

### 3.2 暂不纳入（设计决策确认，2026-08-08）

| 模块 | 原因 | MasterPlan 状态 |
|------|------|-----------------|
| 飞船装配(3D) | **设计决策：去掉「造大船」**——只保留 SOS2 式「有地图的单 part 船」 | 🔵 进行中 |
| 跨行星系 | **设计决策：不出地月系**——跨行星系/外行星系不做，天体与活动范围锁死地月系 | — |
| 地表探索 / 经济外交 | 未开始 | ⬜ 未开始 |

> **战斗系统保留**：空间站对射是核心玩法，战斗保留。但因单 part 化，部件级检测大幅简化（见 §5.3）。

> 飞船形态定调：**单 part + 内部地图**（SOS2 式）。即每个**载具类** SpaceEntity（船/空间站）仅一个 SpacePart，承载一张 Pocket Map（舱室），进出地图即登船。复用现有空间站模式（`CreateStationEntity` 已是单 part + Map）。
>
> ⚠️ **「单 part 化」只约束载具，不约束所有实体**：导弹/无人机等投射物是**无 Map 的纯物理 part/实体**，形态保留（`SpacePart.linkedMapId = -1` 即"无 Map part"；`ProjectileInstance` 本无 Map）。导弹/无人机武器 Def 字段（`WeaponDef` 的 missile*/drone* 字段）保留，当前实现与 master 一致走通用射弹路径。

### 3.3 首发功能目标（玩法闭环，2026-08-08 用户叙述）

| # | 目标 | 现状 | Lite 落地 |
|---|------|------|-----------|
| F1 | **有 dV 的空间站 / 单 part 卫星 / 导弹能变轨** | 变轨机制已存在（机动规划队列 + 缓释燃烧 + `RemainingDeltaV` 消耗）；**dV 来源未实现**（`RemainingDeltaV`/`MaxDeltaV` 字段有，但无补给/生成路径，测试里硬编码 1e7） | dV 体系落地：空间站/单 part 卫星/导弹携带真实 dV，机动执行消耗 dV 变轨（`ConsumeGroupDeltaV` 已就绪） |
| F2 | **空间站能开火** | 武器挂载机制已删（§5.5）；设计已定：Map 炮塔 Building → 3D 射弹 | 实现"地图建筑 ↔ 太空实体"桥接：炮塔建筑调用 `CombatManager` 新方法在 3D 空间生成射弹 |
| F3 | **空间站被打中 → 在地图对应 part 被击中的位置生成爆炸** | **未实现**（3D 命中目前只损伤 3D part，无 Map 内反馈） | 新增：命中 part 后，将 3D 命中点映射到 part 关联的 Pocket Map 内坐标，在该位置生成爆炸（视觉/伤害反馈） |

> 三个目标构成 Lite 首发最小玩法闭环：**变轨（机动）→ 对射（开火）→ 受击反馈（Map 内爆炸）**。F1 依赖现有变轨机制 + dV 补给新实现；F2 依赖 §5.5 桥接设计；F3 是全新功能（3D→2D 命中坐标映射 + Map 内爆炸生成）。

## 4. 盘点结论（2026-08-08 源码核查）

### 4.1 模块独立性核查结果

**纯净可提取（无战斗/装配依赖）**：

| 模块 | 文件 | 依赖情况 |
|------|------|----------|
| 轨道物理全链 | `Base/Orbital/`（NBodyIntegrator、OrbitMath、ManeuverPlanner、OrbitTransferPlanner、RendezvousPlanner、Gooding、CelestialBodyManager） | ✅ 无内部 PioneerFramework 子命名空间依赖 |
| 群组实体 | `Base/Core/SpaceEntityGroup.cs` | ✅ 纯净（仅 System/Unity/Verse/RimWorld） |
| 月球生成链 | `WorldGenStep/`、`WorldDrawLayer/`、`MapGeneration/MoonSurfaceMapGeneration.cs` | ✅ 纯净（无 PioneerFramework 内部依赖） |
| 组件层 | `Components/` | ✅ 纯净（无 Combat/Ships3D/SpatialIndexing 依赖） |

**硬耦合点（Lite 裁剪必须处理）**：

| # | 文件 | 依赖了谁 | 用途 |
|---|------|----------|------|
| C1 | `Base/Core/SpaceEntity.cs` | `Combat`(SpacePart/WeaponInstance/CombatGrid) + `Ship3D` + `Components` | 实体携带部件列表、武器缓存、Morton 索引、射线查询 |
| C2 | `Base/Game/SpaceGameComp.cs` | `Combat`(CombatGrid/CombatManager/ProjectileInstance) | 注册/销毁群组、射弹粗网格、时间缩放 |
| C3 | `Base/MapComp/SpaceMapGenerator.cs` | `Combat`(SpacePart) + `Components` | 空间站实体用 SpacePart 表体积 |
| C4 | `PFView/MainTabWindow_PFView.cs` | `Combat`（射弹/武器 UI） | 3D 视图绘制射弹、武器列表 |
| C5 | `Base/Game/TimeScaleManager.cs` | `CombatManager` | 射弹在飞时维持 Combat 时间档 |

### 4.2 核心结论

- **轨道物理与月球生成是干净的**，可整体提取。
- **但轨道核心实体 SpaceEntity 与战斗/装配深度纠缠**：`SpaceEntity` 内置 `SpacePart`（Combat 命名空间）、`WeaponInstance`、`Ship3D.shipDesign`、Morton 命中索引——这些是战斗与装配共用的运行时载体。
- 因此 **「删掉战斗和装配目录」不是可行方案**，必须选择裁剪策略（见 §5）。

### 4.3 空间站对 SpacePart 的真实依赖

`SpaceMapGenerator.CreateStationEntity` 用 `SpacePart` 构造空间站物理体积（宽×50m×深）——这是**无战斗语义的纯体积表示**，说明 SpacePart 作为「空间实体体积/质量基础层」可独立存在。

## 5. 裁剪策略（已收敛：单 part 化）

> 2026-08-08 用户定调：去掉「造大船」（Ships3D 多部件装配），只保留 SOS2 式「有地图的单 part 船」；不出地月系；**战斗保留**（空间站对射），但部件级检测大幅简化。

### 5.1 总体方案：A 型（最小依赖裁剪）+ 单 part 化

- **保留** `SpacePart`/`Components` 作为「空间实体体积/质量」基础层（无战斗语义）。
- **保留** 战斗系统（`CombatManager`/`ProjectileInstance`/`WeaponDef`/`WeaponInstance`/`TargetingSystem`/`CombatGrid`），用于空间站对射。
- **剥离** 装配系统：`Ship3D`/`ShipPartDef`/`ShipPartDefs`/`ShipPartInstance`/`ShipPartTemplate`/`ShipPartMeshGenerator`/装配窗口与 ThingComp。
- **单 part 化**：`SpaceEntity` 的 `List<SpacePart>` 语义收敛为「至多一个 part + 一张地图」；命中检查与船船碰撞随单 part 化大幅简化（§5.3）。

### 5.2 源码删除清单（Ships3D 整套）

|------|------|
| `Ships3D/Ship3D.cs` | 多部件装配数据 + 蓝图二进制序列化 |
| `Ships3D/ShipPartDef.cs` / `ShipPartDefs.cs` | 部件定义与注册表 |
| `Ships3D/ShipPartInstance.cs` / `ShipPartTemplate.cs` | 装配实例 / 模板 |
| `Ships3D/ShipPartMeshGenerator.cs` | 多形状 Mesh 生成 |

| `Ships3D/RoomTypeDef.cs` | ⚠️ **保留但迁出**：`SpacePart`/PFView 引用舱室类型，移到 `Base/Core` 或独立目录 |

### 5.3 战斗：保留 + 单 part 化简化

| 项 | 处理 |
|----|------|
| `Combat/CombatManager.cs` / `TargetingSystem.cs` / `ProjectileInstance.cs` | ✅ **保留**（空间站对射核心；武器来源改为新接口，见 §5.5 连带清理） |
| `Combat/WeaponDef.cs` / `WeaponInstance.cs` | ✅ **保留**（武器类型/实例类保留；"炮塔作为 part 挂载"机制删除，挂载方式待新写） |
| `SpatialIndexing/CombatGrid.cs` | ✅ **保留**（多格注册 + 速度分层碰撞 + RaySlabIntersection 工具） |
| `SpatialIndexing/Morton3D.cs` | ❌ **删除**（2026-08-08 用户定调「Morton 直接不要了」：单 part 化后部件级空间索引无价值） |
| `Base/Nozzle/CompNozzle.cs` + `ThingDef_Nozzle.xml` | ❌ 地面推进器测试（航天器发射系统前置，Lite 不做） |
| `Base/Game/RuntimePlanetLayerService.cs` | ✅ **保留**（运行时动态生成/移除 PlanetLayer 的基础设施，供 DMS新边疆 未来动态造星球） |
| `Base/Debug/RuntimePlanetLayerDebugActions.cs` | ❌ **删除**（纯调试入口，无生产调用路径） |
| `Base/MapComp/SpaceStationController.cs` | ❌ **删除**（2026-08-08 用户定调「冻结地图也删了」）——连带清理引用：`SpaceGameComp` 解冻逻辑、`MapArchiveManager` 封存冻结、`SpaceMapGenerator` 两处 controller 添加、`SpaceStationMapParent` 冻结 Gizmo |
| `ThreadSafety/` 整目录（9 文件） | ❌ **删除**（纯测试工具：DeterminismTest/FmaSupportTest/PerformanceBenchmark/RaceConditionDetector/StressTest/TestResult/ThreadSafetyAssert/ThreadSafetyTestRunner/Window_ThreadSafetyTest） |
| `Base/Debug/CompGPUDebug.cs` + `Window_GPUComputeTest.cs` | ❌ **删除**（GPU 计算纯调试入口） |
| `Base/MapComp/MapArchiveManager.cs` / `MapArchiveData.cs` | ✅ **保留**（地图封存/取档正式功能，`SpaceGameComp.BeginArchiveMap/BeginRestoreMap` 驱动） |

**单 part 化简化（核心收益）**：

1. **射弹命中**（`CombatManager.CheckSegmentGroupHit`）：现状两级检测「Entity AABB slab → `entity.QueryRayHit`(Morton 部件级) → 命中 Part」。载具（船/空间站）单 part 化后命中链路简化为「Entity AABB slab → 命中唯一 part」；`QueryRayHit` 删除（Morton DDA 遍历、二分查找整条链路移除）。
2. **船-船碰撞**（`CombatManager.CheckShipCollisions`）：现状「球快筛 + AABB 重叠 + 速度分层」，本就不依赖部件数，**保持现状**；载具单 part 化后 AABB 即整船外形，无需部件聚合，`GetGroupBounds` 逻辑简化。
3. **导弹/无人机（无 Map part）**：非载具，走 `ProjectileInstance` 通用路径（无部件、无 Morton），不受单 part 化影响。

### 5.5 Components 保留判定

| 组件 | 保留？ | 理由 |
|------|--------|------|
| `RoomComponentData` | ✅ | 载具（船/空间站）核心：内部地图（`SpaceMapGenerator.GenerateRoomMap` 消费） |
| `EngineComponentData` / `PropellantTankComponentData` / `CargoComponentData` | ❌ **删除**（2026-08-08 用户定调） | 无创建路径（无任何 `AddComponent` 调用），thrust/propellant/cargoCapacity 无消费方；F1 dV 体系移植时随 master 组件体系一并带入 |

> 💡 **武器来源新设计（2026-08-08 用户定调）**：**Map 炮塔 Building（2D 地图内建筑）→ 新方法直接在 3D 太空空间生成射弹**。即武器不再挂载在船体 part 上，而是由地图内的炮塔建筑发起开火：炮塔建筑调用 `CombatManager` 新增的"Map 炮塔开火"方法（复用现有 `FireWeapon` 的 groupId + targetPosition + spawnPosition 语义，传入炮塔在 3D 空间对应的 spawn 位置与目标），直接在 3D 空间生成 `ProjectileInstance`。这与已删的 CompNozzle（地图建筑 → 3D 推力）同构——"地图建筑 ↔ 太空实体"桥接。对射武器来源由此闭环，无需实体级武器列表。
