# 航天器管理界面规划（Brainstorm 草稿）

> 状态：Brainstorm 中，待用户补充关键决策
> 本文档不是最终实施计划；最终计划将在问题确认后整理为正式 Markdown 计划案。

---

## 1. 背景与问题

当前“地面装配 / 发射”存在两条相互交错的链路：

1. **原版链路**
   - 火箭自带 `CompLaunchable_TransportPod`。
   - 点选火箭可直接走原版 TransportPod 发射到世界地格。
   - 与 PFL 的轨道实体、舱内口袋地图没有统一关联。

2. **PFL 链路**
   - 发射台负责总装状态机：设计 → 施工 → 完工。
   - 火箭/发射台都有各自 Gizmo。
   - 发射方式已开始统一到 `RocketLaunchManager` / `Dialog_RocketLaunch`，但仍偏“操作入口”，不是完整“航天器管理”。

**核心痛点：**

- 火箭 Gizmo 与发射台 Gizmo 任务边界不清晰。
- 原版发射与 PFL 入轨同时存在，缺少统一的产品化入口。
- “设计航天器”的 UI 仍缺失。
- 发射方式、发射轨迹、舱内地图类型等没有统一规划。
- 玩家无法从同一界面完成“设计 → 建造 → 装载 → 选择发射方式 → 发射”。

---

## 2. 目标

建立一个统一的“航天器管理界面”，作为地面航天器的总入口：

1. **设计航天器**
   - 选择型号/模板。
   - 配置 Part、载荷、框架尺寸。
   - 区分“航天舱室”与“普通运输仓”。
   - 决定是否生成/使用口袋地图。

2. **规划发射方式**
   - 原版 TransportPod 发射。
   - PFL 轨道入轨。
   - 两种方式的适用条件、校验、录入统一界面。

3. **规划发射轨迹**
   - PFL：目标轨道 / 入轨机动 / 后续转移规划。
   - 原版：世界地图目标地格 / 运输舱到达行为。

4. **整合入口**
   - 点选火箭：只保留“进入火箭舱内”以及真正进入口袋地图。
   - 点选发射台：打开“航天器管理”界面。
   - 其他管理动作收进管理界面，减少 Gizmo 泛滥。

## 3. 初步信息架构

### 3.1 建议的 UI 形态

优先考虑“发射台 Gizmo → 航天器管理窗口”，窗口内用标签页组织：

| 标签页 | 内容 |
|--------|------|
| 总览 | 当前航天器状态、设计摘要、建造进度、燃料/载荷/人员概况 |
| 设计 | 型号、Part、载荷、框架尺寸、舱室类型、是否生成舱内地图 |
| 施工 | 材料需求、施工进度、蓝图/框架状态 |
| 舱内 | 进入舱内地图、人员/建筑装载、舱内检查 |
| 发射 | 发射方式选择、条件校验、发射确认 |
| 轨迹 | PFL 轨道规划 / 原版目的地规划 |

### 3.2 备选形态

- **向导式流程**：设计 → 建造 → 装载 → 发射，逐步引导。
- **单一窗口 + 分区**：不做标签页，所有信息一屏展示，适合首发可用即可。

---

## 4. 核心数据模型设想

引入一个“航天器”聚合对象（暂名 `Spacecraft` / `RocketProject`），统合：

- `RocketDesignSpec`：设计数据。
- 建造状态：蓝图 / 框架 / 已完工。
- 发射方式：`RocketLaunchMode`。
- 发射轨迹配置：PFL 轨道参数 / 原版世界目标。
- 关联地面火箭 Building / 发射台 / 舱内口袋地图。
- 燃料、载荷、人员、检修口等信息。

这样 Gizmo 不再分散管理状态，而是都读取/写入同一个航天器对象。

| 现有对象 | 未来角色 |
|----------|----------|

## 6. 需要用户确认的关键问题

### Q1. 管理界面的入口层级
- A. 只从“发射台 Gizmo”进入。
- B. 还可以从火箭 Gizmo 进入（但火箭只保留舱内入口）。
- C. 增加全局“航天器管理”主按钮/Architect 菜单。
- 推荐：A + 全局主按钮可选，避免火箭 Gizmo 复杂化。

### Q2. 管理范围
- A. 只管理“当前发射台上的这一艘航天器”。
- B. 管理“该发射台历史/所有航天器”。
- C. 管理“全殖民地所有航天器/在轨航天器”。
- 推荐：先做 A，预留 B/C 扩展。

### Q3. 设计 UI 的深度
- A. 参数表单：型号/Part/载荷/尺寸下拉 + 数字输入。
- B. 可视化网格：发射台/框架上拖拽布局。
- C. 两步走：先 A，后 B。
- 推荐：C。

### Q4. “航天舱室 / 普通运输仓”是否进入本期设计？
- A. 进入：在设计页选择类型，决定是否生成口袋地图。
- B. 暂缓：仍只记录为设计，本期继续自动生成舱内地图。
- 推荐：A 作为本期核心设计点，因为当前管理界面刚好需要统合这一点。

### Q5. 原版与 PFL 是否由“舱室类型”决定？
- A. 是：普通运输仓 → 只能原版；航天舱室 → PFL 入轨。
- B. 否：同一航天器可任选发射方式。
- C. 可配置：默认绑定，但允许 dev 覆盖。
- 推荐：A（更清晰），dev 保留强制切换。

### Q6. 原版发射的目的地如何规划？
- A. 在管理界面内选世界地格，然后交给原版 `CompLaunchable` 执行。
- B. 仍由原版世界目标选择器完成，管理界面只负责发起。
- 推荐：A 的第一版可简化成 B，后续增强为 A。

### Q7. PFL 发射轨迹规划首版范围
- A. 只选“目标轨道高度/近圆轨道”+自动圆轨化。
- B. 支持轨道面/倾角/远地点等参数。
- C. 接入完整机动规划（Lambert/交会/转移）。
- 推荐：A 作为首发，B/C 后续。

### Q8. “进入火箭舱内”的具体含义
- A. 直接切换相机到舱内地图。
- B. 选中 pawn 后执行“登船”，pawns 真正移动到舱内地图。
- C. 需要建立登船口/门，pawn 通过 Job 走进舱内。
- 推荐：B 作为首发，C 后续；用户已提到“pawn 真的从该入口进入”，所以至少 B。

### Q9. 如何让 pawn 真的进入？
- 是“选中多个 pawn → 点击进入 → 传送到舱内出生点”。
- 还是“点击火箭 → 自动把该火箭附近的 pawn 装入”？
- 还是“需要站在火箭入口格，点击进入”？
- 需要用户指定。

### Q10. 原版 Gizmo 的裁剪范围
- 除了火箭“进入舱内”外，是否连“装载/卸载殖民者”“发射…”“强制发射”等也全部移入管理界面？
- 推荐：是，火箭 Gizmo 只保留“进入舱内”；其他一律通过管理界面。

### Q11. 存档兼容
- 现有发射台/火箭/地图数据如何迁移到新“航天器”对象？
- 旧存档没有航天器对象时，是否自动从 `CompAssemblyPad` 升级？
- 推荐：提供兼容读取，旧存档按当前单航天器模型自动迁移。

### Q12. PFL 与 DMS:NF 内容层分工
- 正式型号、Part 定义、控制台/舱室建筑 Def 由 DMS:NF 提供；
- PFL 只做机制层、管理界面框架、通用操作。
- 请确认是否有其他内容层需要在本界面预留接入点。

## 7. 用户已确认的决策（截至当前）

1. 管理界面入口：只从发射台 Gizmo 进入。
2. 管理范围：只管理当前发射台上的这一艘航天器。
3. 设计 UI：两步走，先参数表单、后可视化布局。
4. 舱室类型本期进入设计页，并决定是否生成舱内口袋地图。
5. 舱室类型不直接决定发射方式，只做限制：
   - 普通运输仓：可 PFL 入轨，但无舱体/无口袋地图；原版着陆按原版运输仓处理。
   - 航天舱室：可原版、可 PFL；原版着陆后生成持久乘员舱 Building，并可重连口袋地图。
6. 原版目的地选择仍由原版世界目标选择器完成，管理界面只发起。
7. PFL 轨迹首版：只选目标高度/近圆轨道并自动圆轨化。
8. 进入舱内：采用原版 `MapPortal` / `Dialog_EnterPortal` 模式，pawn/物品经 Job 真正进入。
9. 舱内 5×5 地图固定一个出口格，火箭地面同一格作为入口；进出都走它。
10. 落地乘员舱被摧毁：物品/pawn 按 PortalContainerProxy/掉落方式转移到周边；在轨状态销毁或后续再定。
11. 火箭 Gizmo 只保留“进入火箭舱内”。
12. 不兼容旧存档；当前开发都在 PFL 内，解耦后续再做。
