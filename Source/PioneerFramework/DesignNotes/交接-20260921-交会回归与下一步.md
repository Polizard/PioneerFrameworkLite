## ★ 更新 5（2026-09-21，**用户指出主推带矢量角**）：点火门不该比锥窗严

### 那条被我一直漏掉的机制

`SpaceMapComp.GetThrustAlong`：**主推逐引擎判** `dot(该引擎轴, 指令方向) ≥ coneCos`，
凡落在**指令方向 ±10°**（`DefaultThrustConeCos`）锥内的轴**都按指令方向出力**；
而冲量是沿 `burnDirection` 累积的（`pendingImpulse += burnDirection * dv`）。
⇒ **只要还有一根轴在锥内，出力方向就是对的** —— 这正是用户说的"快对准了差一点点时，朝正确方向点火"。
（也解释了现场那个 `带角度点火：残留 79.5°` 仍能出力：六根轴互隔约 90°，
总有一根落在 `79.5° − 90° + 10°` 的窗口里。）

### 因此改掉的那个数

`IgnitionAlignGateDeg` 原为 **2°**（照抄上游 `AlignedToleranceDegrees = 1`）——
**对我们是过度严格**：上游单喷管靠姿态对准，我们是多轴矢量 ⇒ 抄它的数就白丢了"矢量角"这份余量。
实测代价：晚点火 85 s ⇒ 下一发节点落进过去 ⇒ 级联到霍曼卡死。
**现改为由锥窗推导**（`IgnitionAlignGateDeg = acos(DefaultThrustConeCos)`≈10°），
并加两条断言：**门 > 收心死区**（否则收心后仍在门外 → 死锁）、**门 ≤ 锥窗**（否则门内一根轴都不在锥内 → 出力恒 0 白等）。

**闸门**：Debug 0 错 · 警告 557 = 基线 · 纯 196 · 集成 80 · 移植 6179 · 确定性字节相同 · DLL `3776677D` 已部署。

### 先记 MJ 执行器的完整算法（这次是真读齐了，附出处）

| 环节 | MJ 怎么做 | 出处 |
|---|---|---|
| **靶** | `GetBurnVector(Orbit)` = `nextPatch.WorldOrbitalVelocityAtUT(UT) − currentOrbit.WorldOrbitalVelocityAtUT(UT)`。`nextPatch` = 建节点时把 Δv 施加到 `patch` 上算出的**结果轨道** ⇒ 靶 = **"在那个位置的、那个速度"**，参照是**活轨道** | KSP `ManeuverNode.GetBurnVector(Orbit currentOrbit)`（官方 API 文档：「the residual Dv as a vector3d of the node, Zero if patch or nextPatch is not found」） |

| **油门** | `ThrustForDv(_dvLeft, τ)` ⇒ `desiredAccel = (dV − spooldownDv)/τ` ⇒ `throttle = Clamp(desiredAccel/MaxAccel, 0.01, 1.0)`。展开 = **`throttle × MaxAccel × τ = _dvLeft`** —— **油门与"还差多少"是同一件事** | `MechJebModuleThrustController.cs:289-296` |

| **姿态** | 每帧 `SetAttitude() → attitudeTo(_worldDirection, INERTIAL_COT)`，`_worldDirection = Planetarium.rotation × _direction`（derotated 惯性系，跨 tick 一致） | `MechJebModuleAttitudeController.cs:265-278` |

### 由此定位到的**真差异**（不是靶，靶我们是对的）

**MJ 没有任何一帧可以被锁死。** `_dvLeft` 每帧从活轨道重算，而油门**就是**它的函数。
我们：点火锁 `burnCommandAccel = Δv/t_b` 常量化 ⇒ `BurnStep.Compute` 按它烧满整段
⇒ **发动机实际给不出那个加速度时，整段燃烧都按错的加速度走，没有任何一帧会去纠正它** ✗✗。
（用户 2026-09-19 那条"机动 = Δv + 加速度"的裁定本意是"油门随时适配质量"，但实现把它**锁成了常量**。）

### 改动（就这一处，最小）

- `SpaceEntityGroup.burnThrottleCap`（新字段）：**有节点靶时 = 本步还差多少**（= `DeficitToTargetV`
  每拍从活状态重算的差额）；`0` = 未启用（RTN 退路律仍走记账式，行为不变）；
- `SpaceGameComp` 执行器靶分支：`burnCommandAccel = 0.0`（不再常量加速度）+ `burnThrottleCap = defRem`；
  收工时一并清零；
- `BurnStep.Compute` 的调用处：`remainingForStep = min(remainingBurnDV, burnThrottleCap)`。
- ⇒ 本步 Δv = **`min(a_可用·dt, 差额)`**，需求与可得**同一把尺子**；差额一直在减小 ⇒ **必然收手**。

### ② 相位共轨（**端到端完成**）

`RendezvousGoal.Kind.PhaseSynced` 从"只有语义"变成**能判**：

- **`RendezvousGoal.SignedPhaseDeg`**：沿轨**有符号**相位差（正 = 目标在前方）。
  ⚠ 与阶梯里那个 `PhaseDifferenceDeg`（**无符号短弧 0..180**）是**两个量**：
  那个回答"要收多少角度"，这个回答"**该加速还是该等**"——**做判据必须用有符号的**，
  否则"我在你前方 5°"与"在我后方 5°"会被判成同一件事（而且不会报错）。
- **判据三条同中**：同轨（Δa）+ 相对速度 + 相位差；**缺相位参 ⇒ 保守返回 false**（不冒充达成）。
- **统一求值口** `SpaceEntityGroup.IsRendezvousGoalMet(target, gm, out phaseErrDeg)`：
  完成判据与捷径**都走它**（相位目的要算相位差与 Δa，两处各拼一次就会两套口径）。
- 用例 5 条（`RendezvousGoalTests`）：符号方向性 / 短弧折返 / 三条同中 / 缺参不冒充 / 既有目的回归。
