### 1.1 步 1：热循环换 span（§2-A）✅

**改动**：`SpaceEntity.PartsList`（`internal List<SpacePart>`，只给本程序集热循环用）；
`CombatManager` 三处热循环（`CollectPartAabbs` / `CollectPartAabbsInClip` / `CountUsableParts`）
改 `CollectionsMarshal.AsSpan(entity.PartsList)`。对外仍是只读 `IReadOnlyList<Part>`。

**台架**（`PartHotAccessBench`，同进程同轮交错，256 件 × 64 遍 × 201 采样取中位数）：

| 路径 | ns/件 | µs/遍 | 分配 |
|---|---|---|---|
| `IReadOnlyList` 接口 | **3.25** | 0.83 | 0 B |
| `Span` | **2.66** | 0.68 | 0 B |
| Δ | **−18.4%** | | 校验和两侧逐位相等 |

口径：这是**取件微循环**，不含几何运算；生产 `part盒重组` ≈42 ns/件，故这一刀在整链里
约 **1.4%**（0.6 ns/件）。**不吹大**：它值的是"零风险、顺手拿"，不是性能拐点。

**回退**：三处 `span` 换回 `entity.Parts[i]`，删 `PartsList` 一行。

### 1.7 第二批：步 4 电 + 步 5 热（规则层）✅

**形状**：纯函数内核 + 群级状态 + **每步 O(组数)/每组 O(1)**；物理步里**不遍历组件**（§0-1 红线）。

- `PowerThermalCore`（`Components/`）：`Step(in Inputs) → Outputs` 纯函数。分配顺序固定
  **推进 > 护盾 > 武器 > 传感器**；供给 = 发电 + 电池放电（受放电上限与存量约束）；
  剩余发电按充电上限回充；输出 4 个通道 brownout + 总 brownout + `overheat`。
  超温默认公式 `1 / (1 + max(0, 产热−散热) / max(散热, 1e-3))`：不超温**恰 1.0**。
- `ShipStats` **+6 槽**：`powerDrawPropulsion/Shield/Weapon/Sensor`（四通道，总 `powerDraw` 由它们求和）、
  `powerDischargeLimit`、`powerChargeLimit`（`powerStorage` 改为**容量**口径）。
- `BatteryComponentData`（新组件 + `PartRole.Battery`）：只给**容量/充放上限**三个静态量；
  **当前存量是群级** `SpaceEntityGroup.StoredEnergyJ`（持久化）。理由：存量每步都变，逐件存就得每步扫组件。
- 组件接线：引擎 `powerDrawWatts`（推进通道）、传感器 `powerDrawWatts`（传感通道）、
  武器挂点 `powerDrawWatts`（武器通道）、电池（容量/限值）。全部默认 0 ⇒ **老船零行为变化**。
- `SpaceEntityGroup`：`RecomputeDerived` 里把 Σ 聚合缓存成 10 个 float（`HasPowerOrHeat` 标记）；
  `UpdateAllMovements` 每步对标记群跑一次 `StepPowerThermal`（主线程，物理并行区之前）；
  新槽必须在 `SpaceEntity.RecalculateShipStats` 同步（已加）。
- 目录：新增 `PF_ShipPart_Battery_Debug`（5 MJ / 200 kW 充放）。

**判据**（`PowerThermalCoreTests` 10 条 + `PowerThermalIntegrationTests` 7 条）：
功率守恒（供给 0–1000 W 扫描，`used ≤ supply`）· 优先级（150 W 供给下 100/50/0/0）·
单调性（供给↑ brownout 不降，需求↑ 不升）· 电池放电受"上限 ∧ 存量/dt"双约束 ·
充电受"剩余 ∧ 充电上限 ∧ 剩余容量"三约束 · 无输入恰 1/1 · 同输入逐位同输出 ·
组件→部件→实体→群四层接线。

**读数**（`PowerThermalBench`，Debug 口径）：典型有电船 **134 ns/群/步**；无输入快路径 **51 ns/群/步**；
老船走 `HasPowerOrHeat=false` 分支，每群每步只付一次 bool 判断。

**本批的默认裁定**（用户 2026-10-22「不需要我测试就回到主线继续做」⇒ 按设计稿默认值落地，可改）：
1. **周期 = 每物理步**（Normal 2 s/步）。设计稿写"每秒"，但规则比步还细没有意义；这已是"最细节拍"。

   开关；被动阵列本来常开）——留了活动系数入口，等各自子系统给信号。
3. **消费端未接线**：`Brownout/Overheat` 已算出来并可读，但**没有任何系统乘它**（见 §2-1 的理由）。

**回退**：`UpdateAllMovements` 删 `StepAllGroupsPowerThermal` 一行 + 删 `SpaceEntityGroup` 的
`StepPowerThermal/BuildPowerInputs/缓存字段` + 删 `PowerThermalCore.cs`/`BatteryComponentData.cs` +

### 1.9 第四批：推进消费端 —— **欠电 ⇒ 拒绝点火**（用户 2026-10-26 裁定）✅

**裁定**：不要"按比例降推力"，要**拒绝点火**。落成三条语义：

1. **全有或全无**：推进通道要么全额供给、要么本步完全不需求（`PowerThermalCore.CanSupplyChannel`：
   发电 + 电池可放 ≥ 需求）。**不再给"一半推力"**——那会变成"点了火却推不动"，还白烧电池；
2. **点火入口拒绝**：`SpaceEntityGroup.StartBurn` 先问 `CanSupplyPropulsionNow()`（用上一步电快照 +
   群级实时存量）；不够 ⇒ **直接返回、不置 `HasActiveBurn`**，置 `BurnIgnitionBlockedByPower`；
3. **燃烧中掉电**：`StepPowerThermal` 置 `PropulsionPowered=false`（并把本步推进需求收成 0），
   物理并行区只写 `result.BurnStarvedNoPower`（不碰 group），**主线程统一 `EndBurn()`** ——
   与"工质尽"同一条退场路径，不留僵尸燃烧。

**数据出处**：`ShipPartDef.powerDrawWatts`（点火功耗，默认 0）→ `EngineComponentData.powerDrawWatts`。
⚠ **默认 0 是刻意的**：`LaunchService` 的默认设计用调试推进器、不带反应堆；若给老推进器填功耗，
**既有发射会全部点不着火** ⇒ 新增一条独立目录 `PF_ShipPart_Thruster_Electric_Debug`（100 kW，
一台调试反应堆 120 kW 刚好够）作为该机制的验收件，老推进器保持 0。

**判据**（`PropulsionPowerGateTests` 11 条）：`CanSupplyChannel` 的发电/放电上限/存量/dt=0 四档 ·

## §4 事故与修复：obj 目录写不进去（2026-10-22 00:47）

**现象**：`dotnet build` 报 `MSB3491 Could not write lines to file obj\Debug\… Access to the path … is denied`；

**修复**：给这三个目录补当前用户 FullControl allow（保留 deny/owner/SACL），逐条复核 `writeOwner=true`。
报告与回滚件：`_acl-repair-20261022/`（已进 `.gitignore`；**别删**，回滚命令在里面）。
修复后原命令直接通过（Debug 构建 3.4 s）。
