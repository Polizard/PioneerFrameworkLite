## 1. 表示层合并：bool / bitmask

### 1.1 技术事实

- **省**：内存占用（7 个 bool = 7 字节 → 1 个 byte）、缓存线、组合条件判断（`(flags & mask) == mask` 一次 AND）。
- **不省**：短链分支判断本身（JIT 下分支预测命中 >95%，收益噪声级）；Mono 无 SIMD，位运算只省内存不省指令。

### 1.2 值得做的落点

| 位置 | 现状 | 合并方式 |
|---|---|---|
| `SpaceEntity.cs` | 7 个 public bool | `[Flags] enum EntityFlags : byte`，getter 语义不变 |
| `SpaceEntityGroup.cs` | IsActive/IsMovable/IsCollidable/HasGravityWell + OrbitDirty | 同上 |
| 战斗/物理循环 | 6 处散落 `!IsActive \|\| !IsCollidable` | 收敛为派生属性 `IsSimulationEligible`，统一一致性 |

```csharp
[Flags] private enum EntityFlags : byte
{
    None = 0, CanInteract = 1 << 0, IsSelectable = 1 << 1, HasMap = 1 << 2,
    IsMapArchived = 1 << 3, IsMovable = 1 << 4, IsAffectedByGravity = 1 << 5, IsCollidable = 1 << 6,
}
private EntityFlags flags;
public bool IsCollidable => (flags & EntityFlags.IsCollidable) != 0;
```

定位：存档体积、序列化路径、字段语义、一致性；**不是性能优化，是一致性重构**。

### 1.3 明确不做

`WeaponInstance.CanFire`（每 tick 每武器至多一次）、`ProjectileInstance` 少量标志（每 2 tick 一次）、"getter 从 byte 解包"反模式（JIT 下与读 bool 等价）。

## 2. 计算层共享：真正的合并

合并的本质 = **冗余计算消除 + 表示方式选择**。

### 2.1 公式合并：`GetBodyLocalPosition` + `GetBodyLocalVelocity`

两者是同一套 cos/sin/refX/refY 的两种组合：

```
pos = R·(cos·refX + sin·refY)
vel = ωR·(-sin·refX + cos·refY)
```

现状两次调用 = 2 Cos + 2 Sin + 2 `GetOrbitFrame`（normalize + 叉积）。合并为 `GetBodyLocalState(bodyId, tick, out pos, out vel)`，一次 Cos/Sin 出两个量。**常数缓存**：`angularVelocity` 与 `OrbitFrame` 对同一 body 不随 tick 变，应缓存而非每次重算。

### 2.2 幂运算合并（已做对，保持）

`ComputeBodyAccelJerk_Expanded`：`invR = 1/sqrt(rSq)` → `invRSq = invR·invR` → `invR3 = invRSq·invR`，全程一次 `Math.Sqrt`，教科书式（r²→r³ 用乘法递推）。

### 2.3 共享计算（材料表模式）——最猛的一把

把"每个消费者各自算一遍"变成"每 tick 算一次，所有人共享"。对应两处热路径：

1. **Fast 档子步放大**：`UpdateAllMovements` 中 `subSteps=8`，8 次子步循环每次对每 moon 重算 `GetBodyLocalPosition/Velocity`——同一批天体的 Cos/Sin 每 tick 算 8 遍 × 每 group 各自算一遍；
2. **射弹 × 引力源**：`ComputeProjectileGravity` 每射弹对每源调 `GetBodyWorldPosition`——弹幕战 = 射弹数 × 源数 次完整三角函数。

```csharp
// 每物理 tick，并行积分前顺序预计算一次（材料表）
DVector3[] bodyLocalPos = new DVector3[bodyCount];  // 按 bodyId 索引
DVector3[] bodyLocalVel = new DVector3[bodyCount];
for (int i = 0; i < bodyCount; i++)
    CelestialBodyManager.GetBodyLocalState(i, tick, out bodyLocalPos[i], out bodyLocalVel[i]);

// N 体积分、射弹引力、轨道保持全部只读数组
```

收益：消子步 8 倍重复采样、消"射弹 × 源"乘性开销、连续数组缓存友好、**并行区只读天然线程安全**。配套：whitelist `Contains` 移出子步循环（循环提升）。

### 2.4 循环提升

- `MultiBodyAccelJerk` 内 whitelist `Contains` → 提出子步循环（whitelist 在子步期间不变）；
- `UpdateAllMovements` 内 `GetBodyLocalPosition(primaryBody.bodyId, currentTick + UPDATE_INTERVAL_TICKS)` → 走材料表。

## 3. sqrt 与三角函数的量化分析

### 3.1 本质区别

| 函数 | 实现 | 单次成本 |
|---|---|---|
| `Math.Sqrt` | x64 `sqrtsd` 指令（可内联） | ~10-20 周期 |
| `Math.Sin/Cos/Tan` | libm 调用（不可内联），.NET 4.8 无 `Math.SinCos` | ~30-60ns |

**三角函数单位成本是 sqrt 的 5~10 倍，且唯一随"组数 × 月球数 × 子步数"乘性放大。**

### 3.2 调用点分布（热路径）

| 调用点 | 每次成本 | 频率 |
|---|---|---|
| `GetBodyLocalPosition` / `GetBodyLocalVelocity` | 2 libm 各 + `GetOrbitFrame`（**重复算同一份 cos/sin**） | 每 2 tick × 组 × 源 × 子步 |
| `GetCircularPositionAtTick` | 2 libm | 每 tick 每圆轨组首次 miss（Fast 档一帧 8 次 miss） |
| 同函数 `Cross(...).normalized` | 叉积 + 1 sqrt（**轨道常数，应缓存**） | 每 miss 一次 |
| `ComputeProjectileGravity` | 每源 `GetBodyWorldPosition` | 每射弹 × 每源 |
| `GetCentralBodyOffset` | 1 次 `GetBodyLocalPosition` | 每 tick × 每圆轨组 |

### 3.3 量化估算（Fast 档、30 组、1 行星 + 3 月、50 射弹）

```
N-body 星历（每 2 tick）：30 组 × 4 源 × 8 子步 × 2 方法 × 2 libm = 3840 次 ≈ 154µs
  对照：积分器本体乘加 ≈ 48µs → 三角成本 ≈ 积分本体 3 倍
射弹引力（每 2 tick）：50 × 4 × 2 ≈ 400 次 ≈ 16µs
圆轨解析（每帧，Fast）：20 组 × 8 tick × 4 libm ≈ 26µs
结论：Fast 档三角每 2 tick ~170-200µs，是最大单一热点。
```

### 3.4 优化手段（按收益）

1. **星历合并 + 材料表**：3840 → 8 次，收益 ~150µs/2tick；
2. **角度递推**（见 3.6）：线性相位用 `sin(θ+Δ)=sinθ·cosΔ+cosθ·sinΔ`（4 乘 2 加 ~2ns），`cosΔ/sinΔ` 每实体常数，libm 归零；
3. **版本号缓存**（见 4.5-V1）：圆轨 Fast 档 8 次 miss → 1 次；
4. **yDir 常数缓存**：`Cross(normal, radialRef).normalized` 只依赖轨道常数，`EnterCircularOrbit` 时缓存；
5. **射弹引力走材料表**：消"射弹 × 源"乘性开销。

### 3.5 明确不做

sqrt 牛顿迭代/查表（`sqrtsd` 已指令级）、查表/多项式近似用于物理（误差累积进轨道，只适合 `GetOrbitPathUnity` 渲染预览）、FMA（调用边界吃掉收益）。

**查表法澄清**：现代 libm 是"范围归约 + 多项式逼近"不是查表；double 精度下查表插值表太大 + 随机访问 cache miss。本项目角度是百万弧度量级，range reduction 无法避免，**递推可完全绕开**。

### 3.6 角度递推的误差安全性

- **数学性质**：sin/cos 递推 = 旋转矩阵乘法，特征值 `|λ|=1`——**中性稳定**，误差线性增长而非指数爆炸。
- **量化**：double 每步 ~2 ulp ≈ 2.2e-16 rad/步；1 游戏天 ~1.3e-11 rad（7000km 轨道 ~0.1mm），1 游戏年 ~1cm。需求 ≥1m，余量 10⁴~10⁵ 倍。
- **四重锚点护栏**：① 每 60000 tick 精确 `Math.Sin/Cos` 重锚；② `Enter/ExitCircularOrbit`/`InvalidateOrbitCache` 变更时重锚；③ 存档恢复重锚（递推状态不序列化）；④ 惰性重锚（长时间未查询直接重锚）。
- **倍角跳跃（任意 tick 查询）**：`sin(2θ)=2sinθcosθ` 翻倍，O(log Δtick) 步跳任意远，零 libm。
- **确定性边界**：与直接 `Math.Sin/Cos` 比对 1e6 tick 后 ~1e-9 差异——不是 bug，全链路统一走递推即确定，或重锚 + 容差 1e-9。
- **约束**：物理积分（N 体角度非线性）绝不能用，只用于圆轨解析与天体星历。

## 4. 冷门技巧调研

### 4.1 已核实的原版机制（Rimsage）

| 机制 | 意义 |
|---|---|
| tick 循环"时间驱动回填"：一帧 0~2×倍率 个 tick，`clock.ElapsedMilliseconds > 45.45f` 硬保护 | Fast 档 8x 一帧最多 ~16 tick → `UPDATE_INTERVAL_TICKS=2`+`subSteps=8` = 每帧最多 64 次 N 体积分；time-slicing 意义是压平峰值 |
| `GameComponentTick()` 每 tick；`GameComponentUpdate()` 每帧（**暂停也执行**） | "暂停也要跑"的工作放 Update |
| 原版 `TickList` 按 `GetHashCode() % interval` 随机入桶 | 低频任务按 hash 分摊而非顺序 |
| `Game.GetComponent<T>()` 是 components 列表线性查找 | 静态缓存组件引用 |
| `GenDate.DayOfYear` 本体 ~10ns | patch 的 prefix 若比本体贵即负优化 |

### 4.2 时序操控

- **T1 TickList 式 hash 分摊**（★4/中）：顺序 `index % N` 会让同类实体峰值挤同一 tick；hash 固定入桶随机化。相位避开 2 的幂倍数。
- **T2 相位分离错峰**（★3/中）：`CombatManager` 与 `SpaceGameComp` 全挤同一 2-tick 边界，峰值 tick 是相邻 3~5 倍；无依赖阶段挪奇数 tick。风险：阶段间顺序依赖（`SyncAllShipsToGrid` 先于 `CheckShipCollisions`）。
- **T3 时间预算驱动增量任务**（★4/中）：`BATCH_SIZE` 固定批次的坑是慢元素超预算；用 `Environment.TickCount`（~10ns）记起点 + 游标续跑。适合 `MapArchiveManager`。
- **T4 节流写法**（★2/确认）：`lastUpdateTick + interval` 优于 `tick % interval`（回绕/跳 tick 会错位）。`CombatManager` 的 `% 2` 待统一。

### 4.3 数据与内存

- **D1 接口返回类型破坏 struct 枚举器**（★5/中）：`GetEntityIds()` 返回 `IReadOnlyCollection<int>` → `foreach` 装箱 `HashSet<T>.Enumerator`，每次遍历隐形分配。改返回 `HashSet<int>` 零分配。中招：`ConsumeGroupDeltaV`/`ApplyExplosionDamage`/`CheckSegmentGroupHit`/`SyncAllShipsToGrid`/`GetGroupRadius`/`GetGroupMass`/`UpdateWeapons`。
- **D2 yield 迭代器分配**（★4/小-中）：`GetAllGroups()`/`GetGroupsInRange`（嵌套 yield 两层状态机）；内部热路径直接遍历 `groups.Values`（零分配），yield 留 UI。
- **D3 struct 字段链整块复制**（★5/大）：`group.CurrentOrbit` 是 64B struct，`CurrentOrbit.position.x` 每次求值复制整块到栈。热循环外 `OrbitState orbit = group.CurrentOrbit;` 提升。风险：写路径保持原样（拷贝语义）。
- **D4 并行结果预分配数组**（★4/中-大）：ConcurrentBag 每次 Add 可能 new node + 枚举顺序不定。`Parallel.For(0, count, i => results[i] = ...)` 无锁零分配，按输入序。伪共享：元素多按线程分块。
- **D5 Morton 键化网格**（★4/中）：`Dictionary<(int,int,int), Cell>` → `Dictionary<ulong, Cell>`（坐标 +2^20 后 `Morton3D.Encode`）。注意 21 位范围（±2M 格）。

### 4.4 计算代数

- **M1 sqrt 别用牛顿迭代**：`sqrtsd` 已指令级；牛顿替代是 x87 时代遗产。
- **M2 角度递推**（★5/大）：见 3.6。
- **M3 GetBodyLocalState 合并**：见 2.1，优先级最高。
- **M4 查表只用于渲染/预览**：物理不可用；UI/`GetOrbitPathUnity` 可用。

### 4.5 版本号缓存 / 惰性失效

- **V1 tick 号缓存 → 版本号缓存**（★5/大）：`GetCircularPositionAtTick` per-tick 缓存键在 Fast 档一帧 8 tick 全 miss；圆轨参数只在 Enter/Exit/碰撞分离时变 → `orbitVersion`（变更 ++）+ `lastCachedTick` 双键，每帧 8 次重算 → 1 次。同款适用 `CombatGrid.cachedGravityTick`。
- **V2 失效点收敛**：版本号是"变更计数"不是"时间"；weaponsVersion 全网 3 处失效点是教科书。
- **V3 缓存哨兵用 int**：double 键在 `deltaReal * scale`（1/60、8）下同 tick 可能差 1 ULP → miss 率高于预期。键用 `(int)Math.Round(physicsTick)`。

### 4.6 多线程与确定性

- **P1 Parallel 阈值化 + 预热**（★3/中）：<~64 元素分区开销超过收益；首调触发线程创建（~几十 ms），加载时预热。两分支走同一套写入逻辑。
- **P2 确定性 = 按输入序写结果**（★4/中-大）：ConcurrentBag 枚举顺序由调度决定 → 顺序敏感阶段（撞行星销毁级联、dV 消耗）不确定。预分配数组 + 按索引处理。浮点本身确定，**破坏点是聚合顺序与共享写**。
- **P3 并行区严禁懒缓存/共享可变状态**（★5/红线）：`ComputeGroupPhysics` 并行区当前写 `group.CurrentOrbit.velocity += burnDv`、懒缓存字段——"碰巧安全"（每 group 独占 + 主线程屏障后读）。**"并行前顺序填充、并行区只读"是唯一安全形态**。
- **P4 档位/子步路径改变物理序列**：`subSteps=1` 与 `8` 是两条积分序列 → 切档轨迹跳变。跨档位确定性需固定权威子步数。
- **P5 超线程假核**：纯 FPU 负载超线程无增益，`MaxDegreeOfParallelism = ProcessorCount - 1`。

### 4.7 Harmony 与引擎层

- **H1 prefix 短路未必划算**（★4/中）：`GenDate.DayOfYear` 本体 ~10ns，prefix 里 `GetComponent` + double 运算贵 3~5 倍。加廉价快速路径——Normal 档直接 `return true`；组件引用切静态缓存。
- **H2 Postfix ref 参数按需声明**：不改写不声明 `ref`；能 `return false` 短路就短路。
- **H3 Transpiler 真相**：一次性成本，运行时零额外；代价是维护性不是性能。
- **H4 GetComponent 静态缓存**（★3/中）：推广 `GetPhysicsTickSafe` 模式到 `CelestialBodyManager`/`CombatGrid`/`SpaceGameComp`/`CombatManager`。
- **H5 委托缓存替代反射**：`Delegate.CreateDelegate` 已做对；`AccessTools.Field(...).GetValue` 每次 ~100ns，应静态缓存。

### 4.8 坑表（看起来对，实际是坑）

| 技巧 | 真相 |
|---|---|
| Mono 上 SIMD 向量化 | Unity 桌面 Mono JIT 无自动向量化，`Vector<T>` 退化标量 |
| Unity Job System / Burst | RimWorld 不打包 `Unity.Jobs`/`Unity.Burst`，mod 无法引用 |
| `[MethodImpl(AggressiveInlining)]` 过度 | 代码膨胀 + i-cache 压力；只给确凿热点叶子函数 |
| `Parallel` 内嵌套 `Parallel` | 线程池饥饿 + 潜在死锁 |
| FMA 优化 | .NET 4.8 无 `Math.FusedMultiplyAdd`，Mono 不自动融合；`FmaSupportTest` 的"JIT 优化"用例是假的（两函数体相同，只查 OS 平台） |
| 手写 `& (n-1)` 替代 `% n` | JIT 对常量 2 的幂已自动优化 |
| ConcurrentBag 线程安全 = 顺序无关 | 线程安全 ≠ 顺序确定（见 P2） |
| `DateTime.Now` 测耗时 | ~100ns+ 受时钟跳变影响；用 `Environment.TickCount`（~10ns） |
| 共享 `System.Random` 于并行区 | 非线程安全；`[ThreadStatic]` 或 seed+threadIdx |
| `List.Remove(proj)` O(n) | 倒序 `RemoveAt(i)`；机动队列用 `Queue<T>.Dequeue` |
