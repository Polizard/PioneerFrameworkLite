# 太空战斗系统 — 设计思路

## 一句话目标

在现有 3D 太空战视图和飞船装配系统之上，实现一套**弹丸命中 → 部件损伤 → 结构失效**的战斗闭环，玩家可操控飞船与敌舰交火，远程炮击摧毁对方部件，必要时展开接舷战进入 Map 内战斗。

---

## 架构立场：无边界战斗（世界连续模拟）

**定义**：战斗不是"切入的实例/战场"，而是世界连续模拟的一部分。没有 StartBattle/EndBattle 生命周期、没有战场边界、没有"战斗场景"。

**排除的方案**：CoDE 式领域展开（作战区域实例）、Starsector/Nebulous 式战斗场景切换。

**依据**：RimWorld 本体哲学——袭击不是"进入战斗"，而是敌人在地图上走过来开打，战斗与生存、建造、外交共享同一世界状态。本项目把这一哲学扩展到太空层。

**推论**：

1. **战斗网格是常驻子系统**：`CombatGrid` 是持久 `GameComponent`，随世界存在，不随任何一场战斗创建/销毁。
2. **交战是涌现的**：敌对 Group 进入武器射程即产生交战（engagement），由常驻系统检测与结算；不区分"哪场战斗"，也没有"生成一波敌人"的刷怪器。
3. **战斗结束不留战场**：残骸留在世界里（残骸打捞、物流约束自然成立）。
4. **精度分层**：世界处处有战斗可能，但全精度模拟的成本不允许处处全精度 → 三层模拟 tier（见「未来方向：无边界战斗的三层模拟 tier」章节）。
5. **实体表示统一**：`SpaceEntityGroup` 是唯一实体表示，战斗状态（weapons/combatState）挂在 Group 上，而非独立的"战斗"对象。

```
每 Tick（战斗管理器更新）:
  1. AI 决策 → 目标选择、开火指令
  2. 武器冷却计时 →
     冷却完毕 → 发射弹丸（生成 ProjectileInstance）
  3. 弹丸推进 → 每 tick 更新位置
  4. 碰撞检测 → 弹丸 OBB 与目标部件 OBB 求交

### 弹丸运行时实例（射弹专属）

```
ProjectileInstance（运行时数据，不序列化存档）:
  - sourceGroupId: int         # 发射方 Group ID（用于统计/特效归属，不用于友军识别）
  - weaponDef: WeaponDef       # 发射的武器定义

  - velocity: Vector3          # 当前速度向量（受引力影响）
  - remainingLife: float       # 剩余飞行时间（秒），超时自动销毁
  - damage: float              # 命中伤害（无差别）
  - armorPenetration: float    # 穿甲值（穿透层数）
  - affectedByGravity: bool    # 是否继续受引力影响
  - flybyDistance: float        # 最近一次飞越任意 Group 的距离（太空垃圾判定用）
  - trailEffect: bool          # 是否显示拖尾特效
  - currentGravitySources: List<int> # 当前受引力影响的天体 ID 列表（优化用）

**设计决策：射弹飞行使用欧拉积分（显式一阶）**

```
每 tick（游戏世界 1 秒）:
  acceleration = CalculateGravity(projectile.position)  # 当前位置的引力加速度
  projectile.velocity += acceleration × TickDelta       # 更新速度
  projectile.position += projectile.velocity × TickDelta # 更新位置
```

**时间步长设定**：
  - TickDelta = **1 秒**（游戏世界时间）
  - 炮弹速度 = **800 m/s**
  - 每 tick 飞行距离 = **800 m**
  - 线段检测是**必须的**（点检测会漏检，隧道效应严重）

为什么用欧拉积分而不是高阶方法：
  1. **简单快速**：每 tick 只需一次引力计算 + 两次向量乘加，无额外存储
  2. **步长足够小**：TickDelta = 1s，对于秒级飞行时间的炮弹可接受
  3. **误差不敏感**：命中判定用线段检测，位置误差不影响碰撞结果
  4. **与轨道系统一致**：SpaceEntityGroup 的轨道更新也使用类似积分方式
  5. **无需预测**：射弹只做实时飞行，不需要像轨道规划那样做长期预测

对比：
  - 欧拉积分：1 次加速度计算/tick，误差 O(Δt²)
  - 三阶泰勒：3 次加速度计算/tick，误差 O(Δt⁴)
  - 对于 1s 步长，三阶泰勒精度提升显著，但计算成本也提升 3 倍
  - 结论：欧拉积分足够简单，命中判定不依赖精确位置，无需高阶方法
```

**设计决策**：射弹**无敌我识别**，命中任何 Group 的部件都会造成伤害。这意味着：
- 友军在射弹路径上会被误伤
- 战斗中需要注意阵型和距离，避免"友军伤害"
- 简化了碰撞检测逻辑（无需判断目标阵营）

## 战斗流程

### 1. 交战触发

```
进入交战距离（例如 ≤ maxRange 的 120%）→ 战斗管理器标记交战状态
  ├─ AI 模式：自动选择目标、开火
  └─ 玩家模式：通过 Gizmo 选择目标、手动/自动开火
```

### 2. 目标选择

```
FindTarget(SpaceEntityGroup attacker):
  1. 遍历 SpaceGameComp 中所有敌方 Group
  2. 筛选条件：
     - 敌方 faction
     - 距离 ≤ maxRange × 1.2
     - 在武器跟踪弧线内（如炮塔有 trackingArc 限制）
  3. 评分排序：
     - 距离近 + 分
     - 体积大（部件多）+ 分
     - 残血（hp 比例低）+ 分
     - 威胁大（有武器已锁定自己）+ 分
  4. 返回最高分目标 GroupId
```

### 3. 开火（按武器类型分发）

```
FireWeapon(attacker, target):
  1. 遍历 attacker 所有 WeaponInstance
  2. 对每个冷却完毕、未过热的武器，按 weaponType 分发：

  【射弹】
    a. 计算目标提前量（考虑相对速度）
    b. 加入精度散布（accuracyRadius + distance × accuracyFalloff）
    c. 生成 ProjectileInstance
    d. 设置冷却、增加 overheatCounter

  【射线】
    a. 计算射线方向 + 散布
    b. 执行射线逐层穿透判定（见射线章节）
    c. 显示光束视觉
    d. 设置冷却

  【导弹/无人机】
    a. 计算拦截弹道（预测目标位置 + 导弹初速度）
    b. 生成新的 MissileGroup / DroneGroup
    c. MissileGroup 初始轨道指向拦截点
    d. 将 MissileGroup 加入 SpaceGameComp
    e. 设置冷却

  3. 若 overheatCounter ≥ overheatThreshold → 进入过热状态
```

### 4. 射弹飞行（每 tick 更新，欧拉积分）

```
时间步长：TickDelta = 1 秒（游戏世界）
炮弹速度：800 m/s → 每 tick 飞 800 m

UpdateProjectiles():
  for each projectile in activeProjectiles:
    1. if projectile.affectedByGravity:
         acceleration = CalculateGravityAt(projectile.position)
         projectile.velocity += acceleration × TickDelta（1秒）
    2. prevPosition = projectile.position
       projectile.position += projectile.velocity × TickDelta（1秒）
    3. 更新 flybyDistance（最近一次飞越任意 Group 的距离）
    4. projectile.remainingLife -= TickDelta（1秒）
    5. if remainingLife ≤ 0 → 销毁（miss）
    6. 射弹碰撞检测（用 prevPosition → position 的线段，防止穿透）

CalculateGravityAt(position):
  // 复用 NBodyIntegrator 的引力计算
  totalAcceleration = Vector3.zero
  for each celestialBody in activeGravitySources:
    direction = celestialBody.position - position
    distance = direction.magnitude
    gravity = G × celestialBody.mass / (distance × distance)
    totalAcceleration += direction.normalized × gravity
  return totalAcceleration
```

**线段检测必要性**：
  - 每 tick 飞 800 m，部件尺寸约 10-50 m
  - 点检测会漏检（隧道效应）
  - 必须用 **SegmentHitsOBB(prevPosition → position)** 检测

### 5. 命中判定（按武器类型）

**射弹：点/线段 vs OBB**

```
HitDetection(projectile):
  1. 获取 targetGroup 对应的 Ship3D 数据
  2. 遍历所有 ShipPartInstance：
     a. 计算部件的 OBB（bounds × rotation + position）
     b. 检测弹丸运动线段与 OBB 求交
     c. 若命中多个部件 → 取弹丸进入方向的第一个（入口部件）
  3. 若命中 → ApplyDamage(part, projectile) → 销毁弹丸
  4. 若未命中 → 记录 miss（用于太空垃圾判定）
```

**射线：收集所有被穿过的部件（逐层穿透）**

```
RayHitDetection(weapon, sourcePos, direction, maxRange):
  1. 收集射线路径上的所有部件（按距离近 → 远排序）
  2. 穿透力 = weapon.armorPenetration
  3. for each part in sortedParts:
       a. damageAtRange = damage / (distance / referenceDistance)²
       b. ApplyDamage(part, damageAtRange, "Ray")
       c. 穿透力 -= part.armorValue
       d. 若穿透力 ≤ 0 → 停止传递
  4. 返回最远命中点（用于视觉）
```

**导弹/无人机：终末阶段碰撞**

```
UpdateMissileGroups():
  for each missileGroup in missileGroups:
    1. 获取 targetGroup 的当前坐标
    2. if distance_to_target < engageDistance:
         → 切换 Phase = Terminal
         → 向目标当前位置直线加速
    3. for each targetPart in targetShip.parts:
         if missile_position within part.OBB:
           → ApplyDamage(part, missileImpactDamage)
           → 导弹销毁，MissileCount--
           → 若 MissileCount == 0 → 移除 MissileGroup
    4. if fuel_remaining ≤ 0 && Phase != Impacted:
         → 导弹自毁
    5. 若 missileGroup 是无人机且 Phase == Terminal:
         → 每 tick 执行自有武器开火判定（同射弹/射线）
```

### 6. 伤害应用（简化版：直接摧毁）

```
MVP 阶段设计决策：
  - 命中部件 → 直接摧毁（无 HP 计算、无装甲减免）
  - 简化实现：命中即 part.isActive = false

ApplyDamage(ShipPartInstance part):
  1. part.isActive = false  // 直接摧毁
  2. 从 Ship3D.parts 移除/禁用
  3. 若部件是 isRoomModule → 对应的 Map 标记为"受损"状态
  4. 更新框架质量（质量中心变化）
  5. 触发摧毁特效（爆炸粒子、碎片）

后续扩展（可选）：
  - 部件 HP 系统
  - 装甲减免公式：effectiveDamage = damage × (1 - armor / penetration)
  - 穿甲值递减
  - 护盾拦截
```

### 7. 战斗结束

```
当一方所有部件被摧毁 / 所有武器失效 / 跳转离开战场 → 战斗结束
  - 胜利方：保留战场残骸（可选回收）
  - 失败方：飞船残骸变为静态物体，可对接打捞
```

## 碰撞检测细节

### 射弹：线段 vs OBB

弹丸在每 tick 内飞行一段距离，用**线段与 OBB 求交**检测，防止高速穿透（速度 > 部件尺寸 / tick 时长时，点检测会穿透）。

```
bool SegmentHitsOBB(Vector3 p0, Vector3 p1, ShipPartInstance part):
  // 1. 将线段端点转换到部件局部坐标系
  Matrix4x4 worldToLocal = Matrix4x4.TRS(part.position, part.rotation, part.def.bounds).inverse
  Vector3 a = worldToLocal.MultiplyPoint(p0)   // 线段起点
  Vector3 b = worldToLocal.MultiplyPoint(p1)   // 线段终点

  // 2. 转换为相对线段 d = b - a，起点 a
  // 3. 标准 Slab 算法：检测 AABB([-0.5,0.5]³) 与线段求交
  // 4. 若有交点，返回命中，记录命中位置（用于特效）
```

#### 部件级碰撞检测优化（五层过滤）

针对每 tick 飞 800m 的高速射弹，部件级检测采用多层优化：

**第一层：包围球预判（淘汰 80%）**

```csharp
// ShipPartInstance 预计算字段（部件创建时计算一次）
public float boundingRadius;  // 包围球半径 = max(size.x, size.y, size.z) * 0.866f
public Vector3 worldCenter;   // 世界坐标中心

// 线段-球检测（极快，约 10 次浮点运算）
bool SegmentHitsSphere(Vector3 p0, Vector3 p1, Vector3 center, float radius)
{
    Vector3 lineDir = p1 - p0;
    Vector3 toCenter = center - p0;

    float t = Mathf.Clamp01(Vector3.Dot(toCenter, lineDir) / lineDir.sqrMagnitude);
    Vector3 closest = p0 + lineDir * t;

    float distSqr = (closest - center).sqrMagnitude;
    return distSqr <= radius * radius;
}
```

**第二层：方向预过滤（淘汰 20-30%）**

```csharp
// ShipPartInstance 预计算字段
public Vector3 forward;  // 部件朝向（引擎朝后、武器朝前）

// 快速过滤：射弹从后方飞来，引擎不太可能命中
bool CanHitPart(Vector3 projectileDir, ShipPartInstance part)
{
    float dot = Vector3.Dot(projectileDir, -part.forward);
    if (dot < -0.5f)  // 夹角 > 120°
        return false;
    return true;
}
```

**第四层：Slab 算法优化**

```csharp
bool SegmentHitsOBB_Optimized(Vector3 p0, Vector3 p1, OBB obb)
{
    Vector3 localP0 = obb.WorldToLocal(p0);
    Vector3 localP1 = obb.WorldToLocal(p1);
    Vector3 dir = localP1 - localP0;

    float tMin = 0, tMax = 1;

    // X 轴 Slab（优化：预计算逆矩阵，避免重复乘法）
    float invDirX = 1.0f / dir.x;
    float t1 = (-obb.halfSize.x - localP0.x) * invDirX;
    float t2 = (obb.halfSize.x - localP0.x) * invDirX;
    if (t1 > t2) Swap(ref t1, ref t2);
    tMin = Math.Max(tMin, t1);
    tMax = Math.Min(tMax, t2);
    if (tMin > tMax) return false;

    // Y 轴 Slab（同样逻辑，提前退出）
    float invDirY = 1.0f / dir.y;
    t1 = (-obb.halfSize.y - localP0.y) * invDirY;
    t2 = (obb.halfSize.y - localP0.y) * invDirY;
    if (t1 > t2) Swap(ref t1, ref t2);
    tMin = Math.Max(tMin, t1);
    tMax = Math.Min(tMax, t2);
    if (tMin > tMax) return false;

    // Z 轴 Slab（同样逻辑）
    float invDirZ = 1.0f / dir.z;
    t1 = (-obb.halfSize.z - localP0.z) * invDirZ;
    t2 = (obb.halfSize.z - localP0.z) * invDirZ;
    if (t1 > t2) Swap(ref t1, ref t2);
    tMin = Math.Max(tMin, t1);
    tMax = Math.Min(tMax, t2);
    if (tMin > tMax) return false;

    return true;
}
```

### Unity 物理引擎 vs 纯 C# 数学：性能对比与策略

项目已验证 Unity 3D Physics 模块可用（`Window_Physics3DTest`），但直接使用 `Physics.Raycast` 或创建大量 `Rigidbody`/`Collider` 未必是最优解。以下是详细分析：

#### 方案一：纯 C# 数学计算（当前设计）

```
优点:
  - 零 GC 分配（避免频繁创建 GameObject/Collider）
  - 完全可控（自定义碰撞检测逻辑）
  - 不依赖 Unity 物理层（不受 Layer/碰撞矩阵限制）
  - 精度可控（OBB 线段求交完全精确）

缺点:
  - O(n×m) 时间复杂度（需手动剪枝）
  - 无法利用 GPU 加速
  - 需自行实现空间哈希等优化
```

#### 方案二：Unity Physics.Raycast（每枚射弹发射射线）

```
优点:
  - Unity 内部有空间分区（Broad Phase），自动剪枝
  - 可利用 GPU 加速（若启用）
  - 代码简洁

缺点:
  - 每次 Raycast 都有函数调用开销
  - 大量射弹时（100+），Raycast 调用本身成为瓶颈
  - 创建 Collider 有 GC 开销
  - Layer 和碰撞矩阵配置复杂
  - 精度不如自定义 OBB 检测
```

#### 方案三：Unity Physics.SphereCast（模拟弹丸体积）

```
优点:
  - 可模拟弹丸体积（非质点）
  - 避免高速穿透（球体移动更稳定）
  - 同样受益于空间分区

缺点:
  - 比 Raycast 更慢（球体求交计算量更大）
  - 无法精确检测部件级命中（只能检测到最近的 Collider）
```

#### 方案四：Unity Rigidbody + Collider（完全物理化）

```
优点:
  - 利用 PhysX 的完整物理模拟
  - 自动处理碰撞响应、反弹等
  - 可利用 GPU 物理加速

缺点:
  - 创建/销毁 Rigidbody 的巨大 GC 开销
  - 射弹数量受限（通常 < 100）
  - 无法精确控制命中判定（PhysX 有容差）
  - 重力影响难以与自定义引力系统融合
  - 性能取决于物理设置（Solver Iteration Count 等）
```

#### 方案五：混合策略（推荐）

```
核心思路：用 Unity Physics 做粗筛，用纯 C# 做细粒度检测

流程:
  1. 为每艘飞船创建一个大型 MeshCollider（Group 级别）
  2. 使用 Physics.SphereCastAll / Physics.OverlapSphere 做粗筛
     → 获取可能命中的飞船列表
  3. 对命中的飞船，用纯 C# OBB 线段求交做部件级精确检测
     → 确定具体命中哪个部件

性能对比:
  - 粗筛阶段：Unity Physics 自动空间分区，O(n×k)，k 很小
  - 细筛阶段：仅对候选飞船做精确检测，部件数有限
  - 总体复杂度：O(n) 粗筛 + O(k×m) 细筛，远低于 O(n×m)

实现细节:
  - Group 级 MeshCollider：合并所有部件的 Mesh 为一个
  - Layer 设置：飞船设为同一 Layer，射弹射线只检测该 Layer
  - 碰撞矩阵：只启用飞船层与射弹层的碰撞
  - GC 优化：复用 RaycastHit 数组，避免每次分配

伪代码:
  void UpdateProjectiles_Hybrid():
    for each projectile in activeProjectiles:
      // 阶段 1: Unity Physics 粗筛
      RaycastHit[] hits = Physics.SphereCastAll(
          projectile.position,
          projectile.radius,
          projectile.velocity.normalized,
          projectile.speed * TickDelta,
          LayerMask.GetMask("Ships")
      );

      // 阶段 2: 纯 C# 细粒度检测
      foreach (hit in hits):
        GroupId = GetGroupIdFromCollider(hit.collider)
        Ship3D ship = GetShip3D(GroupId)
        foreach (part in ship.parts):
          if SegmentHitsOBB(projectile.posLast, projectile.posNow, part):
            ApplyDamage(part, projectile)
            break
```

### CPU 开销专项优化

针对 CPU 性能的核心关切，以下是具体的开销估算和优化策略：

#### CPU 开销估算（基准）

```
假设：现代 CPU（3 GHz），每个 OBB 线段求交约 100 次浮点运算

场景 1：小规模战斗（2 艘船，10 枚射弹，每艘 30 部件）
  - 每 tick 检测量：10 × 60 = 600 次 OBB 检测
  - 每 tick 浮点运算：600 × 100 = 60,000 次
  - CPU 耗时：≈ 20 微秒（60,000 / 3,000,000,000）
  - 占比：< 0.1%（60 fps 下每帧约 16.7 毫秒）

场景 2：中等规模（4 艘船，50 枚射弹，每艘 30 部件）
  - 每 tick 检测量：50 × 120 = 6,000 次
  - CPU 耗时：≈ 200 微秒
  - 占比：≈ 1.2%

场景 3：大规模（4 艘船，200 枚射弹，每艘 30 部件）
  - 每 tick 检测量：200 × 120 = 24,000 次
  - CPU 耗时：≈ 800 微秒
  - 占比：≈ 4.8%

场景 4：射弹雨（4 艘船，500 枚射弹，每艘 30 部件）
  - 每 tick 检测量：500 × 120 = 60,000 次
  - CPU 耗时：≈ 2,000 微秒 = 2 毫秒
  - 占比：≈ 12%

结论：
  - 小规模战斗：CPU 压力可忽略
  - 中等规模：CPU 占比 < 5%，可接受
  - 大规模/射弹雨：需要优化
```

#### 优化策略 1：时间分片（Time Slicing）

```
核心思路：将检测工作分摊到多个 tick

实现:
  1. 将 activeProjectiles 分成 N 个批次（如 N=4）
  2. 每 tick 只处理一个批次
  3. 剩余批次延后到后续 tick

效果:
  - 射弹雨（500 枚）分摊到 4 个 tick：
    → 每 tick 检测量：125 × 120 = 15,000 次
    → CPU 耗时：≈ 500 微秒
    → 占比：≈ 3%（从 12% 降至 3%）

缺点:
  - 弹丸命中响应延迟 N 个 tick
  - 需要权衡延迟和 CPU 负载
  - 推荐 N=2~4（延迟 1~2 帧，玩家几乎无感知）
```

#### 优化策略 2：GPU 加速可行性（暂时不考虑）

```
核心思路：借道 Unity 让 GPU 算些东西

设计决策：
  - MVP 阶段：不用 GPU，先验证 CPU 方案能否满足需求
  - 如果瓶颈出现：先试 Job System + Burst（CPU 并行）
  - 如果还不够：再试 Compute Shader（需评估 RimWorld 框架兼容性）

可行性分析:
  1. Compute Shader（难度高）
     - RimWorld 使用的 Unity 版本可能不支持 Compute Shader
     - 需要评估框架兼容性
     - 数据传输开销（CPU → GPU → CPU）可能抵消加速收益
     - 适用场景：数万射弹的极端场景

  2. Unity Job System + Burst Compiler（难度中）
     - CPU 并行（不是 GPU），但比 Compute Shader 更容易集成
     - 自动利用多核，编译为高度优化的机器码
     - 不需要数据传输（都在 CPU 内存）
     - 适用场景：数千射弹的中等场景

  3. Physics.SphereCastAll（难度低）
     - Unity Physics 可能自动 GPU 加速（取决于版本）
     - 最简单，只需调用 Unity API
     - 适用场景：中等规模，快速验证

限制:
  - RimWorld 主线程限制：伤害应用必须在主线程
  - 碰撞检测可以 GPU/并行，命中结果需收集后回到主线程

串行依赖分析（GPU 不值得的核心理由）:

  碰撞检测流程存在严格串行依赖，GPU 无法有效处理：

  依赖点 1：命中后部件状态变化
    射弹 A 检测 → 命中部件 X → ApplyDamage → 部件 X.isDestroyed = true
    射弹 B 检测 → 检查部件 X → 发现已摧毁 → 跳过检测

    GPU 并行问题：
      - 射弹 A 和 B 同时检测部件 X
      - 两者都报告"命中部件 X"
      - CPU 应用伤害时，部件 X 被重复摧毁（或第二次命中无效）
      - GPU 无法知道射弹 A 已经摧毁了部件 X

  依赖点 2：射弹命中后销毁
    射弹 A 检测 → 命中部件 → 射弹 A 销毁 → 从 activeProjectiles 移除
    下一个射弹检测 → 射弹 A 已不在列表中

    GPU 并行问题：
      - 500 枚射弹同时检测 → 可能多枚射弹都命中同一部件
      - CPU 应用伤害时，多枚射弹都报告命中
      - 实际上只应该有一枚射弹命中（命中后部件可能被摧毁）

  依赖点 3：穿透传递（射线武器）
    射线命中逻辑：
      射线检测 → 命中部件 X → ApplyDamage → 穿甲值 -= 部件 X.armor
      → 检测下一个部件 Y → 穿甲值可能不够 → 跳过部件 Y

    GPU 并行问题：
      - 射线同时检测所有部件 → 报告命中部件 X, Y, Z
      - CPU 无法正确计算穿透传递（穿甲值递减是严格串行逻辑）

  结论：
    - GPU 无法处理串行依赖（核心间无法通信）
    - 即使勉强并行，CPU 后处理成本更高
    - 总耗时反而增加（GPU 传输开销 + CPU 串行处理）
    - 纯 CPU 串行处理更快更简单

#### 优化策略 3：LOD 碰撞检测（Level of Detail）

```
核心思路：根据距离动态调整碰撞检测精度

实现:
  1. 远距战斗（> 2 km）：使用 Group 级 AABB 检测（不检测部件）
     → 命中即造成随机部件伤害
  2. 中距战斗（500 m ~ 2 km）：检测关键部件（武器、引擎、核心）
     → 减少部件遍历数量
  3. 近距战斗（< 500 m）：检测所有部件（完整 OBB）

效果:
  - 远距战斗：检测量减少 80%（仅 Group 级）
  - 中距战斗：检测量减少 50%（仅关键部件）
  - 近距战斗：完整检测（但距离近，射弹数量少）

伪代码:
  void UpdateProjectiles_LOD():

#### 优化策略 4：Early Out（尽早退出）

```
核心思路：在检测过程中尽早发现无命中，提前退出

实现:
  1. 距离过滤：Sphere-Sphere 距离检测（O(1)），距离太远直接跳过
  2. 方向过滤：射弹方向与目标方向夹角过大，直接跳过
  3. 速度过滤：射弹速度方向与目标方向相反，直接跳过
  4. AABB 先判：部件 AABB 不相交，直接跳过 OBB 检测
  5. Slab 算法 Early Out：线段与任一 Slab 不相交，立即返回 false

效果:
  - 多数射弹在距离过滤阶段就被跳过（约 70%）
  - 剩余射弹在 AABB 阶段被跳过（约 20%）
  - 仅 10% 的射弹需要做完整 OBB 检测

伪代码:
  bool SegmentHitsOBB_EarlyOut(p0, p1, part):
    // Early Out 1: 距离过滤
    if Distance(p0, part.position) > maxRange:
      return false
    
    // Early Out 2: 方向过滤
    direction = (p1 - p0).normalized
    toTarget = (part.position - p0).normalized
    if Dot(direction, toTarget) < 0:
      return false  // 射弹背向目标
    
    // Early Out 3: AABB 先判
    if !SegmentHitsAABB(p0, p1, part.aabb):
      return false
    
    // 完整 OBB 检测（仅 10% 会走到这里）
    return SegmentHitsOBB(p0, p1, part)
```

#### 优化策略 5：对象池（Object Pooling）

```
核心思路：避免频繁创建/销毁射弹对象，减少 GC

设计决策：
  - 池大小：4096（约 16 KB 内存，固定数组）
  - 池满策略：随机删除一个活跃射弹（O(1)，无动态扩容）
  - 优点：实现简单，复杂度低，零 GC
  - 缺点：可能销毁"不该销毁的射弹"（概率极低，4096 > 实际需求）

伪代码:
  class ProjectilePool:
    private ProjectileInstance[] pool;       // 固定大小数组
    private int activeCount;                 // 当前活跃数量
    private const int MAX_SIZE = 4096;
    
    public ProjectilePool() {
      pool = new ProjectileInstance[MAX_SIZE];
      for (int i = 0; i < MAX_SIZE; i++)
        pool[i] = new ProjectileInstance();
      activeCount = 0;
    }
    
    public ProjectileInstance Get() {
      // 查找空闲槽位（O(n)，但 n 很小）
      for (int i = 0; i < MAX_SIZE; i++) {
        if (!pool[i].isActive) {
          pool[i].Reset();
          pool[i].isActive = true;
          activeCount++;
          return pool[i];
        }
      }
      
      // 池满：随机删除一个活跃射弹（O(1)）
      int randomIndex = Random.Range(0, MAX_SIZE);
      pool[randomIndex].isActive = false;  // 销毁旧射弹
      pool[randomIndex].Reset();
      pool[randomIndex].isActive = true;
      return pool[randomIndex];
    }
    
    public void Release(ProjectileInstance proj) {
      proj.isActive = false;
      activeCount--;
    }
    
    public void ReleaseAll() {
      for (int i = 0; i < MAX_SIZE; i++)
        pool[i].isActive = false;
      activeCount = 0;
    }

效果:
  - 零 GC 分配（射弹创建/销毁）
  - 固定内存（无动态扩容）
  - 满池时 O(1) 随机删除（无需复杂策略）
```

#### 多线程优化对比：轨道动力学 vs 战斗系统

```
核心问题：轨道动力学天生可并行，战斗系统存在串行依赖

对比分析：

| 系统 | 并行性 | 串行依赖 | 计算量 | 单线程耗时 | 多线程提升 |
|------|--------|---------|--------|-----------|-----------|
| 轨道动力学 | 高（天生可并行） | 无（飞船间独立） | 高（1000 次） | ~500 μs | ~4x |
| 战斗系统 | 中（碰撞检测可并行） | 高（伤害应用串行） | 低（2500 次） | ~100 μs | ~1.7x |

轨道动力学多线程方案（优先实现）：

  方案 A：引力计算并行（Job System + Burst）

    数据结构（NativeArray，零 GC）:
      public struct BodyData {
        public Vector3 position;
        public float GM;  // 引力常数 × 质量
      }

      public struct ShipData {
        public Vector3 position;
        public Vector3 velocity;
        public int id;
      }

    Job 定义:
      [BurstCompile]
      public struct GravityCalculationJob : IJobParallelFor {
        [ReadOnly] public NativeArray<BodyData> bodies;
        [ReadOnly] public NativeArray<ShipData> ships;
        public NativeArray<Vector3> accelerations;  // 输出

        public void Execute(int shipIndex) {
          var ship = ships[shipIndex];
          Vector3 totalAcc = Vector3.zero;

          foreach (var body in bodies) {
            Vector3 direction = body.position - ship.position;
            float distance = direction.magnitude;
            float gravity = body.GM / (distance * distance);
            totalAcc += direction.normalized * gravity;
          }

          accelerations[shipIndex] = totalAcc;
        }
      }

    性能预估:
      - 100 飞船 × 10 天体 = 1000 次引力计算
      - 单线程：约 500 μs
      - 4 线程并行：约 125 μs（理论 4x，实际接近）
      - 无串行依赖 → 提升接近理论值

  方案 B：三阶泰勒积分多步并行

    流程:
      Job 1: 计算所有飞船当前位置的加速度（acc1）
      Job 2: 更新到中间位置，计算 acc2
      Job 3: 更新到预测位置，计算 acc3
      Job 4: 综合三次加速度，更新最终位置和速度

    性能预估:
      - 三次引力计算 × 100 飞船 = 3000 次
      - 单线程：约 1500 μs
      - 4 线程并行：约 400 μs（三步 Job）
      - 提升：约 3.75x

战斗系统多线程方案（暂不值得）：

  可并行部分：碰撞检测（只读操作）
    - 线程 1-4 各检测 125 射弹
    - 输入：射弹位置、部件位置（只读）
    - 输出：命中结果列表（每个线程写不同索引）

  必须串行部分：伤害应用（状态更新）
    - ApplyDamage：部件.isDestroyed = true（写入）
    - 射弹销毁：射弹.isActive = false（写入）
    - RimWorld 主线程限制：所有状态修改必须在主线程

  性能预估:
    - 碰撞检测并行：80 μs → 25 μs（4 线程）
    - 伤害应用串行：20 μs（不变）
    - 数据准备/清理：10 μs（新增）
    - Job 调度开销：5 μs（新增）
    - 总耗时：60 μs（vs 单线程 100 μs）
    - 提升仅 1.7x，不值得增加复杂度

综合决策:
  - 轨道动力学：优先实现多线程（4x 提升，收益 375 μs）
  - 战斗系统：暂不实现多线程（当前已优化到位，100 μs足够快）
  - 战斗子 Grid：已完成（30x 提升）

总性能提升预估:
  轨道动力学多线程：从 500 μs → 125 μs（节省 375 μs）
  战斗子 Grid：从 2000 μs → 100 μs（已完成）
  战斗系统多线程：从 100 μs → 60 μs（暂不实现）
  总节省：约 375 μs/ tick（占每帧约 2.3%）
```

### 射弹雨优化（大规模射弹的性能策略）

当战斗中存在大量射弹（速射炮、弹幕武器），直接做 n 射弹 × m 部件的全量检测会导致 O(n×m) 计算量爆炸。采用以下分层优化方案（基于位图 + 数组的战斗子 Grid）：

```
第一层：位图 + 数组粗筛（10km 格子存 Group）

  核心数据结构:
    - cells: CellData[]（固定大小三维数组，零GC）
    - occupancy: ulong[]（位图标记哪些格子有船）
    - activeShipCells: HashSet<(int,int,int)>（仅记录有船的格子，通常 5-20 个）
  
  坐标转换（与战略 Grid 对齐）:
    - 战略 Grid: 1000 km
    - 战斗子 Grid: 10 km
    - 对齐: 1000 / 10 = 100（整数倍）
    - 转换: cellIndex = (int)posKm（直接截断，无除法）
  
  内存估算（200km³ 战场）:
    - 20×20×20 = 8000 格
    - 数组: 8000 × 8 字节 ≈ 64 KB
    - 位图: 8000 bits ≈ 125 bytes
  
  流程:
    1. 战斗开始时创建战斗子 Grid，将所有参战 Group 放入对应格子
    2. 维护 activeShipCells（仅包含有船的格子，数量极少）
    3. 每枚射弹只遍历 activeShipCells（5-20 个），而非扫 27 个格子
    4. 整数比较：射弹格子与船格子是否在 3×3×3 范围内（3 次整数比较）

第二层：activeShipCells 剪枝（仅遍历有船的格子）

  关键洞察：船的数量远少于格子数量
  - 5 条船 → 最多占用 5 个格子（船的跨度 < 10km）
  - 500 枚射弹 × 5 个格子 = 2500 次整数比较
  - 对比方案（扫 27 个格子）：500 × 27 = 13500 次字典查找
  - 提升：约 5 倍

第三层：Early Out（距离 + 方向过滤）

  对每个候选 Group，在做几何检测前快速淘汰：
  1. 距离过滤：(ship.position - proj.position).sqrMagnitude > maxRangeSqr → 跳过
  2. 方向过滤：Dot(proj.direction, ship.position - proj.position) < 0 → 跳过
  
  成本：约 6-12 次浮点运算
  跳过比例：约 50-70%（距离太远或射弹飞向反方向）

第四层：Group 级 AABB 先判

  对每个候选 Group，先做 Group 级别的 AABB 检测：
  1. 计算 Group 的整体 AABB（所有部件合并的包围盒）
  2. 射弹线段与 Group AABB 求交 → 无交则跳过该 Group 所有部件
  3. 若有交，再遍历该 Group 的部件做细粒度 OBB 检测
  
  成本：约 30 次浮点运算（Slab 算法）
  跳过比例：约 20-30%

第五层：部件级 OBB 检测（精确命中判定）

  对命中的 Group，逐个检测其部件：
  1. 射弹线段与部件 OBB 求交
  2. 命中 → ApplyDamage → 销毁射弹
  
  成本：约 100 次浮点运算
  命中比例：约 5-10%（每枚射弹命中一个部件）

综合效果（500 枚射弹 vs 5 条船）:
  - 无优化：500 × 5 × 30 = 75,000 次检测
  - 第一层：500 × 5 = 2,500 次整数比较
  - 第三层：约 1,000 次距离检测
  - 第四层：约 700 次 AABB 检测
  - 第五层：约 50-100 次 OBB 检测
  - 最终 CPU 耗时：约 50-100 μs（占 0.3-0.6% 帧时间）

性能提升：
  - 正常战斗（10-20 枚射弹）：几乎无开销变化
  - 射弹雨（100+ 枚射弹）：性能提升 50-100 倍
  - 空间稀疏时（多数射弹在空区域）：性能提升 100+ 倍
```

### 极端优化方法（真正硬核的性能策略）

当射弹数量达到 **数千枚**（如大规模舰队战、弹幕武器饱和攻击），上述分层优化仍可能不够。以下是一些**以牺牲精度/功能为代价**的极端优化方法，按激进程度排序：

```
第六层：时间压缩（牺牲精度换性能）

  将多个 tick 的射弹运动合并为一次检测：
  1. 累积 N 个 tick 的射弹位置变化（N = 2~4）
  2. 用一条更长的线段做一次碰撞检测
  3. 代价：可能跳过中间的部件（高速穿透风险增加）
  4. 适用场景：远距离射弹（飞行时间长，精度要求低）

  效果：检测次数减少 N 倍，精度下降（可能漏检小部件）

第七层：距离 LOD（远处射弹降级处理）

  根据射弹与最近 Group 的距离动态调整检测精度：
  - 距离 < 500 m：完整 OBB 检测（最高精度）
  - 距离 500~2000 m：简化为 Group 级 AABB 检测（命中即随机选一个部件受伤）
  - 距离 > 2000 m：完全跳过碰撞检测（视为"可能命中，概率判定"）

  概率命中判定（距离 > 2000 m）:
    hitProbability = exp(-distance / 500) × weaponAccuracy
    if Random() < hitProbability:
      随机选择目标 Group 的一个部件造成伤害
      生成命中特效（延迟渲染）

  效果：远距离射弹开销从 O(n×m) 降为 O(n)，视觉上几乎无差别

第八层：空间投影（降维打击）

  将 3D 碰撞检测降为 2D：
  1. 选择一个投影平面（如 XY 平面，或垂直于战场主轴的平面）
  2. 将所有射弹和部件投影到该平面
  3. 在 2D 平面上做碰撞检测（AABB 或 Circle-Circle）
  4. 对 2D 命中的候选对，再做 3D 验证

  优化点：2D 检测比 3D 快约 3-5 倍
  代价：可能误判（投影重叠但实际不相交），需要 3D 回检

  进阶：使用轴对齐投影，选择最能区分实体的轴（如战斗主轴）

第九层：蒙特卡洛采样（概率替代精确）

  当射弹数量极大（> 1000），用概率模拟替代精确检测：
  1. 将战场划分为网格，统计每个网格内的射弹密度和部件面积
  2. 每个网格的命中概率 = 射弹密度 × 部件面积 × 武器精度
  3. 根据概率生成命中事件，随机选择部件
  4. 完全跳过逐枚射弹的几何检测

  适用场景：弹幕武器、防空火力网（不需要精确命中哪一枚）
  代价：完全失去命中位置的精确控制，视觉上需要模拟弹丸轨迹

  效果：O(n+m) 复杂度，与射弹数量几乎无关

第十层：GPU 并行化（终极武器）

  将碰撞检测卸载到 GPU：
  1. 将射弹位置、速度、目标数据上传到 GPU 显存
  2. 将部件 OBB 数据上传到 GPU 显存
  3. 使用 Compute Shader 并行执行碰撞检测
  4. 每帧只上传变化的数据（增量更新）
  5. GPU 返回命中结果列表，CPU 处理伤害应用和特效

  优势：
    - 单帧可处理数万枚射弹的碰撞检测
    - 释放 CPU 资源用于其他逻辑
  劣势：
    - 实现复杂（需要学习 GPU 编程）
    - 数据传输开销（CPU ↔ GPU）
    - RimWorld 引擎对 Compute Shader 的支持有限

  可行性：Unity 支持 Compute Shader，理论上可行，但需要评估与 RimWorld 框架的兼容性

第十一层：量子隧道（玄学优化）

  开玩笑的，不存在这个方法。
```

**极端优化的适用场景与代价**

| 优化方法 | 适用场景 | 性能提升 | 精度损失 | 实现难度 |
|---------|---------|---------|---------|---------|
| 时间压缩 | 远距离射弹 | 2-4x | 中等 | 低 |
| 距离 LOD | 大规模战斗 | 10-50x | 低（远处） | 中 |
| 空间投影 | 扁平战场 | 3-5x | 低 | 中 |
| 蒙特卡洛采样 | 弹幕武器 | 100+x | 高 | 高 |
| GPU 并行化 | 数万射弹 | 100+x | 无 | 极高 |

**推荐的极端优化组合**

```
大规模战斗（1000+ 射弹）:

  第一层：空间哈希粗筛（过滤 90% 射弹）
  第二层：距离 LOD（远距离射弹降级）
  第三层：时间压缩（合并多个 tick 的检测）
  第四层：蒙特卡洛采样（弹幕武器用概率模拟）

  效果：
    - CPU 开销降低 50-100 倍
    - 视觉上几乎无差别
    - 实现复杂度中等

  不推荐：
    - GPU 并行化（实现成本太高，收益不确定）
    - 空间投影（精度损失较大，实现复杂度不低）
```

**性能监控与自适应切换**

## 战斗子 Grid 系统：当前实现与历史方案

> ⚠️ **实现状态（2026-08-05 对齐）**：本节以下保留的「为什么需要战斗子 Grid / 为什么选择 10km 格子 / 实现方案 / 详细实现」是早期方案（BattleSpatialGrid：固定数组 + 位图 + StartBattle/EndBattle 生命周期），**已被实际实现 `CombatGrid.cs` 取代**。请以「实际实现」为准，旧方案仅作性能分析过程的参考。

### 实际实现：CombatGrid.cs（现行方案）

> 代码：[CombatGrid.cs](../SpatialIndexing/CombatGrid.cs)（持久 `GameComponent`，与"无边界战斗"立场一致）

| 项 | 旧方案（已废弃） | 现行实现（CombatGrid.cs） |
|----|------------------|---------------------------|
| 生命周期 | StartBattle/EndBattle 随战斗创建销毁 | 持久 `GameComponent`，随世界存在 |
| 网格组织 | 固定三维数组 + 位图 + activeShipCells | `Dictionary<int frameId, SystemGrid>` → `Dictionary<(cx,cy,cz), FineCell>`，无边界按需创建 |
| 细格大小 | 10 km | 20,000 m（20 km） |
| 参考系 | 无 | `GetFrameId` 统一根行星/恒星参考系（绕卫星的船与绕行星的船进同一网格） |
| 船注册 | 单格 | 世界 AABB 覆盖格多格注册（`CoverBox` 闭区间 6-int，O(1) 比较），位置变更差集增删 |
| 射弹检索 | 弹丸扫 3×3×3 邻格 | 射弹入格 + 跨格时 Slab 方法沿路径走格（最多 3 步，防高速穿格） |
| 碰撞对 | 每弹遍历邻格 | `EnumerateShipPairs` 遍历船覆盖格（与空格数解耦），`pairScratch` 去重 |
| 空格回收 | 无 | `DrainEmptyCells`：快路径每 2 tick 队首 20% 斩杀 + 慢路径每 600 tick 全量兜底；`queuedEmpties` 去重防膨胀 |
| 引力计算 | 每弹每 tick 全量 | 按 physicsTick 缓存引力源列表 |

**设计要点**：

- **无边界**：格子按需创建、空格 TTL（600 tick）后回收，`CellCount` 反映实际占用，不随世界尺寸膨胀。
- **完备性保证**：两船重叠必共享至少一个覆盖格（AABB 覆盖格注册保证）；射弹跨格走 Slab，高速不穿格。
- **多格覆盖**：普通船最多覆盖 2×2×2=8 格，巨型船更多；位置变更时仅差集增删覆盖格。

### 为什么需要战斗子 Grid

```
战略 Grid（1000 km 粒度） vs 战斗子 Grid（10 km 粒度）

场景：两艘飞船在相距 200 km 的距离上交战，各有 30 个部件，战场区域约 200 km³

战略 Grid:
  - 整个战场在同一个单元格内（200km < 1000km）
  - GetNearby 返回所有部件（无剪枝）
  - 射弹碰撞检测：n 射弹 × 60 部件（全量）

战斗子 Grid（10 km 粒度）:
  - 战场被划分为约 8000 个单元格（20 × 20 × 20）
  - 每个单元格平均只有 0.0075 个 Group
  - 射弹碰撞检测：n 射弹 × activeShipCells（通常 5-20 个 Group）
```

**核心价值**：当战斗涉及大量射弹（100+），战斗子 Grid 能将 O(n×m) 降为 O(n×k)，其中 k 是 activeShipCells 的数量（远小于 m）。

### 为什么选择 10 km 格子

```
关键决策理由：

1. 内存可控（200km³ 战场）:
   - 20×20×20 = 8000 格
   - 数组: 8000 × 8 字节 ≈ 64 KB
   - 位图: 8000 bits ≈ 125 bytes

2. 与战略 Grid 对齐:
   - 战略 Grid: 1000 km
   - 1000 / 10 = 100（整数倍）
   - 坐标转换: cellIndex = (int)posKm（直接截断，无除法）

3. 27格覆盖合理:
   - 27格 = 3×3×3 = 30 km 覆盖范围
   - 炮弹速度 800 m/s → 每 tick 飞 800 m → **12.5 tick 才跨格一次**
   - 30 km 覆盖远大于炮弹每 tick 飞行距离，无漏检风险

4. 存 Group 而非部件:
   - 战斗子 Grid 存储的是 Group（方盒子）而非部件
   - 粗筛后进入 Group 级 AABB 检测，命中后才进入部件级 OBB 检测
   - 避免在 Grid 层面处理大量部件

5. 1km 格子不可行:
   - 200km 战场需要 8,000,000 格
   - 数组约 64 MB（不可接受）

6. 50km 格子太粗:
   - 27格覆盖 150 km，剪枝效果差
   - 每个格子可能包含多个 Group
```

### 战斗子 Grid 的实现方案

**数据结构设计（位图 + 数组方案）**

```
BattleSpatialGrid:
  - cellSize: 10 km（固定）
  - cells: CellData[]（固定大小三维数组，零GC）
  - occupancy: ulong[]（位图标记哪些格子有船，快速剪枝）
  - activeShipCells: HashSet<(int,int,int)>（记录有船的格子，仅 5-20 个）

CellData:
  - ships: SpaceEntityGroup[]（预分配 4 个槽位）
  - count: byte（当前实际数量）

ProjectileInstance（新增字段）:
  - cellIndex: int（缓存当前所在格子索引，避免每 tick 重算）
```

**坐标转换（与战略 Grid 对齐）**

```
战略 Grid: 1000 km
战斗子 Grid: 10 km

对齐: 1000 / 10 = 100（整数倍）

坐标转换（以 km 为单位）:
  cx = (int)position.x    // 直接截断，无除法
  cy = (int)position.y
  cz = (int)position.z

一维索引计算（预计算步长）:
  const int Y_STRIDE = 200  // 200 格/轴（-100km ~ +100km）
  const int X_STRIDE = 200 * 200
  index = (cx + 100) * X_STRIDE + (cy + 100) * Y_STRIDE + (cz + 100)
```

**碰撞检测流程**

```
UpdateProjectiles():
  for each projectile in activeProjectiles:
    1. 获取 projectile 缓存的 cellIndex（整数，无需每 tick 重算）
    2. 遍历 activeShipCells（仅 5-20 个，远小于扫 27 个格子）:
         a. 整数比较：射弹格子与船格子是否在 3×3×3 范围内（3 次整数比较）
         b. 距离过滤：(ship.position - proj.position).sqrMagnitude > maxRangeSqr → 跳过
         c. 方向过滤：Dot(proj.direction, ship.position - proj.position) < 0 → 跳过
         d. Group 级 AABB 检测（Slab 算法，约 30 次浮点运算）
         e. 命中 → 进入部件级 OBB 检测 → ApplyDamage → 销毁弹丸
    3. 更新 projectile 位置，检查是否跨格:
         a. 新 cellIndex = ToCellIndex(newPos)
         b. 若跨格 → 更新缓存（约 12.5 tick 才发生一次）
```

**战斗子 Grid 生命周期**

```
1. CombatManager.StartBattle() → 创建战斗子 Grid
   - 确定战场范围（所有参战 Group 的包围盒扩展 100km）
   - 创建 cells 数组（8000 格，约 64 KB）
   - 将所有参战 Group 放入对应格子
   - 初始化 activeShipCells

2. 每 tick 更新：
   a. 更新所有 Group 在战斗子 Grid 中的位置（船移动慢，每 5-10 tick 更新一次即可）
   b. 碰撞检测（上述流程）

3. CombatManager.EndBattle() → 销毁战斗子 Grid，释放内存
```

**战斗子 Grid 创建条件（满足任一）**

```
1. 战场内射弹数量 > 50
2. 参与战斗的 Group 数量 > 4
3. 战场面积 > 5 km²（通过所有 Group 的包围盒计算）
```

**性能对比**

| 场景 | 无战斗子 Grid | 有战斗子 Grid（10km） | 提升 |
|------|--------------|---------------------|------|
| 2 艘船，10 枚射弹 | ~1200 次检测/tick | ~50 次检测/tick | 24x |
| 4 艘船，50 枚射弹 | ~12000 次检测/tick | ~250 次检测/tick | 48x |
| 4 艘船，200 枚射弹 | ~48000 次检测/tick | ~1000 次检测/tick | 48x |
| 5 艘船，500 枚射弹 | ~150000 次检测/tick | ~2500 次检测/tick | 60x |

**注意**：战斗子 Grid 存储的是 Group（方盒子）而非部件。粗筛后进入 Group 级 AABB 检测，命中后才进入部件级 OBB 检测。

### 结论：建议实现

```
推荐方案：

1. MVP 阶段：实现战斗子 Grid（10km 格子）
   - 开发成本适中
   - 满足所有规模战斗需求
   - 内存仅 64 KB

2. 性能监控：
   - 在 CombatManager 中添加性能统计（每 tick 检测次数、耗时）
   - 低于阈值时可跳过战斗子 Grid，直接全量检测（小规模战斗）

3. 未来扩展：
   - 近距离接舷战（< 10km）时，可在 10km 格子内部再套一层 100m 的局部位图
   - 当前不实现，待需要时添加

不推荐方案：
- 不实现战斗子 Grid（大规模战斗性能瓶颈）
- CellSize 固定为 1000 km（与战略 Grid 相同，失去战斗级剪枝效果）
- CellSize 固定为 1 km（200km 战场需 64 MB 内存）
```

### 与现有 SpatialGrid3D 的关系

```
推荐：创建独立的 BattleSpatialGrid 类，不继承 SpatialGrid3D

原因：
  - SpatialGrid3D 用 Dictionary 存储格子，我们用固定数组
  - SpatialGrid3D 用浮点除法转换坐标，我们用整数截断
  - 独立实现更简单，避免修改现有类影响其他模块
```

// 战场范围（以 km 为单位）
public struct BattleBounds
{
    public double minX, maxX;  // 例如：-100km ~ +100km
    public double minY, maxY;
    public double minZ, maxZ;
    
    public int GridSizeX => (int)((maxX - minX) / 10.0);  // 例如：200 格
    public int GridSizeY => (int)((maxY - minY) / 10.0);
    public int GridSizeZ => (int)((maxZ - minZ) / 10.0);
    public int TotalCells => GridSizeX * GridSizeY * GridSizeZ;  // 例如：8000 格
}

// 每个格子的数据
public struct CellData
{
    public SpaceEntityGroup[] ships;  // 预分配 4 个槽位
    public byte count;                // 当前实际数量（通常 0 或 1）
    
    public void Initialize()
    {
        ships = new SpaceEntityGroup[4];  // 预分配，避免动态扩容
        count = 0;
    }
    
    public void AddShip(SpaceEntityGroup ship)
    {
        if (count < 4)
        {
            ships[count] = ship;
            count++;
        }
        else
        {
            // 理论上不会触发（船的跨度 < 10km，单格最多 1 条船）
            // 但如果发生，记录警告或扩展数组
        }
    }
    
    public void RemoveShip(SpaceEntityGroup ship)
    {
        for (int i = 0; i < count; i++)
        {
            if (ships[i] == ship)
            {
                ships[i] = ships[count - 1];  // 用最后一个元素填补空位
                ships[count - 1] = null;
                count--;
                break;
            }
        }
    }
}

// 战斗子 Grid 主类
public class BattleSpatialGrid
{
    // 常量
    private const double CELL_SIZE_KM = 10.0;  // 10 km 格子
    private const double STRATEGIC_CELL_KM = 1000.0;  // 战略 Grid
    
    // 战场范围
    private BattleBounds bounds;
    
    // 核心数据结构
    private CellData[] cells;           // 固定大小三维数组（一维索引）
    private ulong[] occupancy;          // 位图（标记哪些格子有船）
    private HashSet<(int, int, int)> activeShipCells;  // 有船的格子集合
    
    // 预计算步长（用于坐标转换）
    private int yStride;
    private int xStride;
    
    // 参战 Group 缓存（用于快速遍历）
    private List<SpaceEntityGroup> allShips;
    
    // 初始化
    public void Initialize(BattleBounds bounds)
    {
        this.bounds = bounds;
        
        int totalCells = bounds.TotalCells;
        
        // 创建数组（零 GC，预分配）
        cells = new CellData[totalCells];
        for (int i = 0; i < totalCells; i++)
            cells[i].Initialize();
        
        // 创建位图（totalCells bits，约 125 bytes for 8000 cells）
        int bitmapSize = (totalCells + 63) / 64;  // 每个 ulong 64 bits
        occupancy = new ulong[bitmapSize];
        
        // 创建活跃格子集合
        activeShipCells = new HashSet<(int, int, int)>();
        
        // 预计算步长
        yStride = bounds.GridSizeZ;  // Z 轴跨度
        xStride = bounds.GridSizeY * bounds.GridSizeZ;  // Y×Z
        
        // 参战船列表
        allShips = new List<SpaceEntityGroup>();
    }
    
    // 坐标转换：世界坐标 → 格子索引（无除法！）
    private int WorldToCellIndex(DVector3 posKm)
    {
        // 截断到格子坐标（相对于战场原点）
        int cx = (int)(posKm.x - bounds.minX);  // 直接截断，无除法
        int cy = (int)(posKm.y - bounds.minY);
        int cz = (int)(posKm.z - bounds.minZ);
        
        // 边界检查（避免越界）
        cx = Math.Clamp(cx, 0, bounds.GridSizeX - 1);
        cy = Math.Clamp(cy, 0, bounds.GridSizeY - 1);
        cz = Math.Clamp(cz, 0, bounds.GridSizeZ - 1);
        
        // 一维索引计算
        return cx * xStride + cy * yStride + cz;
    }
    
    // 坐标转换：格子索引 → 格子坐标
    private (int cx, int cy, int cz) CellIndexToCoord(int index)
    {
        int cz = index % bounds.GridSizeZ;
        int cy = (index / bounds.GridSizeZ) % bounds.GridSizeY;
        int cx = index / xStride;
        return (cx, cy, cz);
    }
    
    // 添加船到格子
    public void AddShip(SpaceEntityGroup ship)
    {
        DVector3 posKm = ship.Position / 1000.0;  // 转换为 km（假设原始单位是 m）
        int cellIndex = WorldToCellIndex(posKm);
        
        // 添加到格子数组
        cells[cellIndex].AddShip(ship);
        
        // 更新位图
        int bitIndex = cellIndex;
        occupancy[bitIndex / 64] |= (1UL << (bitIndex % 64));
        
        // 更新活跃格子集合
        var coord = CellIndexToCoord(cellIndex);
        activeShipCells.Add(coord);
        
        // 缓存到船列表
        allShips.Add(ship);
    }
    
    // 移除船从格子
    public void RemoveShip(SpaceEntityGroup ship)
    {
        DVector3 posKm = ship.Position / 1000.0;
        int cellIndex = WorldToCellIndex(posKm);
        
        // 从格子数组移除
        cells[cellIndex].RemoveShip(ship);
        
        // 如果格子空了，更新位图和活跃集合
        if (cells[cellIndex].count == 0)
        {
            int bitIndex = cellIndex;
            occupancy[bitIndex / 64] &= ~(1UL << (bitIndex % 64));
            
            var coord = CellIndexToCoord(cellIndex);
            activeShipCells.Remove(coord);
        }
        
        // 从船列表移除
        allShips.Remove(ship);
    }
    
    // 更新船的位置（船移动时调用）
    public void UpdateShipPosition(SpaceEntityGroup ship, DVector3 oldPosKm, DVector3 newPosKm)
    {
        int oldIndex = WorldToCellIndex(oldPosKm);
        int newIndex = WorldToCellIndex(newPosKm);
        
        if (oldIndex != newIndex)
        {
            RemoveShip(ship);
            // 临时设置位置用于 AddShip
            ship.Position = newPosKm * 1000.0;
            AddShip(ship);
        }
    }
    
    // 查询射弹附近的船
    public List<SpaceEntityGroup> GetNearbyShips(ProjectileInstance proj)
    {
        var result = new List<SpaceEntityGroup>();
        
        // 获取射弹的格子坐标（从缓存的 cellIndex 获取）
        var projCoord = CellIndexToCoord(proj.cellIndex);
        
        // 遍历活跃格子（仅 5-20 个）
        foreach (var shipCoord in activeShipCells)
        {
            // 整数比较：是否在 3×3×3 范围内
            if (Math.Abs(shipCoord.cx - projCoord.cx) <= 1 &&
                Math.Abs(shipCoord.cy - projCoord.cy) <= 1 &&
                Math.Abs(shipCoord.cz - projCoord.cz) <= 1)
            {
                // 在范围内，获取该格子的船
                int shipIndex = shipCoord.cx * xStride + shipCoord.cy * yStride + shipCoord.cz;
                var cell = cells[shipIndex];
                
                for (int i = 0; i < cell.count; i++)
                    result.Add(cell.ships[i]);
            }
        }
        
        return result;
    }
    
    // 快速位图检查（用于剪枝）
    public bool HasShipsNearCell(int cellIndex)
    {
        var coord = CellIndexToCoord(cellIndex);
        
        // 检查周围 27 个格子的位图
        for (int dx = -1; dx <= 1; dx++)
            for (int dy = -1; dy <= 1; dy++)
                for (int dz = -1; dz <= 1; dz++)
                {
                    int cx = coord.cx + dx;
                    int cy = coord.cy + dy;
                    int cz = coord.cz + dz;
                    
                    // 边界检查
                    if (cx < 0 || cx >= bounds.GridSizeX ||
                        cy < 0 || cy >= bounds.GridSizeY ||
                        cz < 0 || cz >= bounds.GridSizeZ)
                        continue;
                    
                    int neighborIndex = cx * xStride + cy * yStride + cz;
                    int bitIndex = neighborIndex;
                    
                    // 位图检查：1 个 CPU 周期
                    if ((occupancy[bitIndex / 64] & (1UL << (bitIndex % 64))) != 0)
                        return true;  // 有船在附近
                }
        
        return false;  // 附近无船
    }
}

public class ProjectileInstance
{
    // 原有字段
    public Vector3 position;          // 当前位置（Unity 单位，米）
    public Vector3 prevPosition;      // 上一 tick 位置（用于线段检测）
    public Vector3 velocity;          // 速度向量
    public float damage;              // 伤害值
    public float armorPenetration;    // 穿甲值
    public WeaponDef weaponDef;       // 武器定义
    public bool isActive;             // 是否活跃
    
    // 新增字段：战斗子 Grid 相关
    public int cellIndex;             // 缓存的格子索引（避免每 tick 重算）
    public int ticksSinceLastUpdate;  // 距上次跨格的 tick 数（用于统计）
    
    // 更新位置（每 tick 调用，欧拉积分）
    public void UpdatePosition(float deltaTime, BattleSpatialGrid grid, List<CelestialBody> gravitySources)
    {
        prevPosition = position;
        
        // 欧拉积分第一步：更新速度（受引力影响）
        if (affectedByGravity && gravitySources != null)
        {
            Vector3 acceleration = CalculateGravity(position, gravitySources);
            velocity += acceleration * deltaTime;
        }
        
        // 欧拉积分第二步：更新位置
        position += velocity * deltaTime;

        // 检查是否跨格（约 12.5 tick 才发生一次）
        DVector3 posKm = new DVector3(position.x / 1000.0, position.y / 1000.0, position.z / 1000.0);
        int newIndex = grid.WorldToCellIndex(posKm);
        
        if (newIndex != cellIndex)
        {
            cellIndex = newIndex;
            ticksSinceLastUpdate = 0;
        }
        else
        {
            ticksSinceLastUpdate++;
        }
    }
    
    // 计算当前位置的引力加速度
    private Vector3 CalculateGravity(Vector3 pos, List<CelestialBody> sources)
    {
        Vector3 totalAccel = Vector3.zero;
        const float G = 6.674e-11f;  // 引力常数
        
        foreach (var body in sources)
        {
            Vector3 dir = body.position - pos;
            float distSq = dir.sqrMagnitude;
            if (distSq < 1e-6f) continue;  // 避免除零
            
            float accel = G * body.mass / distSq;
            totalAccel += dir.normalized * accel;
        }
        
        return totalAccel;
    }
}

**碰撞检测主流程**

```csharp
public class CombatManager
{
    private BattleSpatialGrid battleGrid;
    private List<ProjectileInstance> activeProjectiles;
    private List<CelestialBody> activeGravitySources;  // 当前活跃引力源
    private PerformanceMonitor perfMonitor;
    
    // 每 tick 更新射弹碰撞
    public void UpdateProjectileCollisions()
    {
        perfMonitor.StartTimer("CollisionDetection");
        
        int totalChecks = 0;
        int aabbChecks = 0;
        int obbChecks = 0;
        int hits = 0;
        
        foreach (var proj in activeProjectiles)
        {
            if (!proj.isActive) continue;

            // 第一层：位图粗筛（快速检查附近是否有船）
            if (!battleGrid.HasShipsNearCell(proj.cellIndex))
            {
                // 附近无船，跳过后续检测，但仍需更新位置（欧拉积分，1秒步长）
                proj.UpdatePosition(1.0f, battleGrid, activeGravitySources);
                continue;
            }
            
            // 第二层：获取附近的船（遍历 activeShipCells）
            var nearbyShips = battleGrid.GetNearbyShips(proj);
            
            foreach (var ship in nearbyShips)
            {
                totalChecks++;
                
                // 第三层：Early Out（距离过滤）
                float distSqr = (ship.Position - proj.position).sqrMagnitude;
                if (distSqr > proj.weaponDef.maxRange * proj.weaponDef.maxRange)
                    continue;  // 距离太远
                
                // 第三层：Early Out（方向过滤）
                Vector3 toShip = (ship.Position - proj.position).normalized;
                if (Vector3.Dot(proj.velocity.normalized, toShip) < 0)
                    continue;  // 射弹飞向反方向
                
                // 第四层：Group 级 AABB 检测
                aabbChecks++;
                AABB shipAABB = GetGroupAABB(ship);
                if (!SegmentHitsAABB(proj.prevPosition, proj.position, shipAABB))
                    continue;  // 不命中 Group AABB
                
                // 第五层：部件级 OBB 检测
                obbChecks++;
                Ship3D ship3D = GetShip3D(ship);
                
                foreach (var part in ship3D.parts)
                {
                    if (!part.isActive) continue;
                    
                    OBB partOBB = GetPartOBB(part);
                    if (SegmentHitsOBB(proj.prevPosition, proj.position, partOBB))
                    {
                        // 命中！
                        hits++;
                        ApplyDamage(part, proj);
                        proj.isActive = false;
                        SpawnHitEffect(proj.position, part, proj.weaponDef);
                        break;  // 一枚射弹只能命中一个部件
                    }
                }
                
                if (!proj.isActive) break;  // 射弹已命中，跳过后续船
            }
            
            // 更新射弹位置（欧拉积分，1秒步长）
            proj.UpdatePosition(1.0f, battleGrid, activeGravitySources);
            
            // 检查射弹是否超时
            if (proj.ticksSinceLastUpdate > proj.weaponDef.projectileLifetime * 60)
            {
                proj.isActive = false;
            }
        }
        
        perfMonitor.EndTimer("CollisionDetection");
        perfMonitor.RecordStats(totalChecks, aabbChecks, obbChecks, hits);
    }
    
    // 性能监控
    private class PerformanceMonitor
    {
        private Dictionary<string, long> timers = new Dictionary<string, long>();
        
        public void StartTimer(string name)
        {
            timers[name] = System.Diagnostics.Stopwatch.GetTimestamp();
        }
        
        public void EndTimer(string name)
        {
            long elapsed = System.Diagnostics.Stopwatch.GetTimestamp() - timers[name];
            double ms = elapsed / (double)System.Diagnostics.Stopwatch.Frequency * 1000.0;
            
            // 记录到日志或显示到 UI
            if (ms > 1.0)
                Log.Warning($"CollisionDetection took {ms:F2}ms (可能需要优化)");
        }
        
        public void RecordStats(int total, int aabb, int obb, int hits)
        {
            // 记录到统计系统
        }
    }
}

```csharp
// Group 级 AABB 获取
private AABB GetGroupAABB(SpaceEntityGroup group)
{
    Ship3D ship3D = GetShip3D(group);
    
    // 遍历所有部件，计算合并的 AABB
    Vector3 min = new Vector3(float.MaxValue, float.MaxValue, float.MaxValue);
    Vector3 max = new Vector3(float.MinValue, float.MinValue, float.MinValue);
    
    foreach (var part in ship3D.parts)
    {
        if (!part.isActive) continue;
        
        OBB obb = GetPartOBB(part);
        // 将 OBB 的 8 个顶点投影到世界坐标
        for (int i = 0; i < 8; i++)
        {
            Vector3 vertex = obb.GetVertex(i);
            min = Vector3.Min(min, vertex);
            max = Vector3.Max(max, vertex);
        }
    }
    
    return new AABB(min, max);
}

// 部件 OBB 获取
private OBB GetPartOBB(ShipPartInstance part)
{
    Ship3D ship3D = part.ship;

    // 获取部件在飞船坐标系中的 OBB
    Vector3 localCenter = part.def.localPosition;
    Vector3 localSize = part.def.size;
    Quaternion localRotation = part.def.localRotation;

    // 转换到世界坐标系
    Vector3 worldCenter = ship3D.transform.TransformPoint(localCenter);
    Quaternion worldRotation = ship3D.transform.rotation * localRotation;

    // 更新预计算字段（供碰撞检测优化使用）
    part.worldCenter = worldCenter;

    // 计算包围球半径（对角线的一半）
    float maxDim = Mathf.Max(localSize.x, Mathf.Max(localSize.y, localSize.z));
    part.boundingRadius = maxDim * 0.866f;  // sqrt(3)/2 ≈ 0.866

    // 计算部件世界朝向（用于方向预过滤）
    part.forward = worldRotation * Vector3.forward;

    return new OBB(worldCenter, localSize, worldRotation);
}

// 线段-AABB 检测（Slab 算法）
private bool SegmentHitsAABB(Vector3 p0, Vector3 p1, AABB box)
{
    Vector3 direction = p1 - p0;
    float length = direction.magnitude;
    direction /= length;  // 归一化
    
    float tMin = 0.0f;
    float tMax = length;
    
    // X 轴 Slab
    if (Math.Abs(direction.x) < 1e-6f)
    {
        if (p0.x < box.min.x || p0.x > box.max.x)
            return false;
    }
    else
    {
        float t1 = (box.min.x - p0.x) / direction.x;
        float t2 = (box.max.x - p0.x) / direction.x;
        if (t1 > t2) { float tmp = t1; t1 = t2; t2 = tmp; }
        tMin = Math.Max(tMin, t1);
        tMax = Math.Min(tMax, t2);
        if (tMin > tMax) return false;
    }
    
    // Y 轴 Slab（类似）
    // Z 轴 Slab（类似）
    
    return true;
}

// 线段-OBB 检测
private bool SegmentHitsOBB(Vector3 p0, Vector3 p1, OBB obb)
{
    // 将线段转换到 OBB 的局部坐标系
    Vector3 localP0 = obb.WorldToLocal(p0);
    Vector3 localP1 = obb.WorldToLocal(p1);
    
    // 在局部坐标系中做 AABB 检测（OBB 变成了 AABB）
    AABB localAABB = new AABB(-obb.size / 2, obb.size / 2);
    return SegmentHitsAABB(localP0, localP1, localAABB);
}

public void HandleFastShipMovement(SpaceEntityGroup ship, DVector3 oldPos, DVector3 newPos)
{
    // 计算移动距离
    double dist = (newPos - oldPos).magnitude;
    
    if (dist > 10.0)  // 超过 10km（一个格子）
    {
        // 线性插值，确保不跳过中间格子

            oldPos = interpPos;
        }
    }
    else
    {
        battleGrid.UpdateShipPosition(ship, oldPos, newPos);
    }
}

// 战场范围计算
private BattleBounds CalculateBattleBounds(List<SpaceEntityGroup> participants, double marginKm)
{
    double minX = double.MaxValue, maxX = double.MinValue;
    double minY = double.MaxValue, maxY = double.MinValue;
    double minZ = double.MaxValue, maxZ = double.MinValue;
    
    foreach (var ship in participants)
    {
        DVector3 posKm = ship.Position / 1000.0;
        minX = Math.Min(minX, posKm.x);
        maxX = Math.Max(maxX, posKm.x);
        minY = Math.Min(minY, posKm.y);
        maxY = Math.Max(maxY, posKm.y);
        minZ = Math.Min(minZ, posKm.z);
        maxZ = Math.Max(maxZ, posKm.z);
    }
    
    // 扩展边界
    minX -= marginKm;
    maxX += marginKm;
    minY -= marginKm;
    maxY += marginKm;
    minZ -= marginKm;
    maxZ += marginKm;
    
    // 确保 10km 对齐（整数格子）
    minX = Math.Floor(minX / 10.0) * 10.0;
    maxX = Math.Ceiling(maxX / 10.0) * 10.0;
    minY = Math.Floor(minY / 10.0) * 10.0;
    maxY = Math.Ceiling(maxY / 10.0) * 10.0;
    minZ = Math.Floor(minZ / 10.0) * 10.0;
    maxZ = Math.Ceiling(maxZ / 10.0) * 10.0;
    
    return new BattleBounds(minX, maxX, minY, maxY, minZ, maxZ);
}

## 四类武器详解

武器按攻击方式和行为分为四类，**每类有完全不同的物理模型和命中判定**。

---

### 1. 射弹（Projectile）

最常见的实弹武器。弹丸是一个有质量的运动点，发射后受引力场影响沿弹道飞行。

```
射弹行为:
  - 有初速度和方向，发射后不受武器本身控制
  - 轨迹受经过的所有天体引力影响（复用 NBodyIntegrator）
  - 超时未命中目标则消散
  - 命中 → 一次性伤害

射弹命中判定（每 tick）:
  - 方法：点 vs OBB（线段求交用于防高速穿透，见碰撞检测章节）
  - 若命中：调用 ApplyDamage
  - 若脱靶：弹丸消散（不造成伤害）

射弹伤害应用:
  - ApplyDamage(part, proj)
  - 命中即造成 damage，不考虑平方反比

射弹特殊机制（未来）:
  - 太空垃圾：每次射弹miss/flyby（飞越目标一定距离内），在飞越位置生成太空垃圾威胁
  - 太空垃圾密度达到阈值 → 影响轨道、损伤过往飞船
  - 由独立的 SpaceDebrisManager 管理（后续 Phase）
```

---

### 2. 射线（Beam/Ray）

定向能武器，瞬时到达，沿射线路径进行**逐层伤害判定**。

**射线比射弹简单得多**：
  - 无飞行时间（瞬时命中，无需每 tick 更新位置）
  - 无引力影响（直线，无需欧拉积分）
  - 无碰撞检测循环（一次射线判定，收集所有命中部件）
  - 无对象池需求（瞬时判定，无需存储运行时实例）
  - 只需要：起点 + 方向 + 距离 → 收集命中部件 → ApplyDamage

```
射线行为:
  - 瞬时到达（无飞行时间）
  - 轨迹为直线（不受引力、介质影响）
  - 威力随距离衰减（平方反比律）
  - 沿射线方向，从近到远依次判定命中部件

射线威力衰减:
  damageAtDistance(d) = damageAtReference / (d / referenceDistance)²
  即：距离翻倍 → 伤害变为 1/4

射线命中判定（逐层穿透）:
  1. 从武器发射点向目标方向发射射线
  2. 收集射线穿过的所有部件（按距离排序：近 → 远）
  3. 对第一个部件进行伤害判定（damage × 衰减系数）
  4. 若穿透（armorPenetration > 部件装甲）：
     a. 伤害传递到第二个部件
     b. 若仍有穿透力 → 继续传递
  5. 直到穿透力耗尽或遍历完所有部件

  穿透计算:
    remainingPen = armorPenetration - 部件装甲值
    若 remainingPen > 0 → 可穿透下一层
    穿透后 damage × 衰减系数（模拟能量扩散）

射线视觉:
  - 从武器发射点画一条线段到最远命中点（或最大射程）
  - 材质：高亮渐变（近端亮、远端暗）
  - 持续时间：1 tick（瞬时）
  - 命中点附加闪光粒子
```

---

### 3. 导弹（Missile）

制导弹药，本质上是一个**拥有独立轨道的 SpaceEntityGroup**，可以集群作战。

```
导弹行为:
  - 发射后形成一个新的 Group（MissileGroup）
  - MissileGroup 和普通 Group 一样接受轨道指令、机动规划
  - 当 MissileGroup 进入目标"接舷战距离"（例如 50m）时：
    → 导弹脱离正常轨道，切换为终末阶段
    → 向目标当前位置直线加速（终末速度）
    → 不再机动，锁定目标位置

导弹 Group 结构:
  MissileGroup:
    - ParentGroupId: 发射方 Group ID（用于区分敌我）
    - TargetGroupId: 目标 Group ID
    - Phase: EnRoute | Terminal | Impacted
    - MissileCount: 该 Group 下的导弹数量（1 枚或多枚）
    - FuelRemaining: 剩余燃料（超过燃料上限仍未命中 → 自毁）

导弹命中判定:
  - 当任一导弹进入目标部件 OBB → 触发命中
  - 命中判定：终末阶段中，任一导弹坐标 vs 目标部件 OBB
  - 命中 → ApplyDamage → 该导弹销毁
  - 全部导弹命中或自毁 → MissileGroup 从 SpaceGameComp 移除

导弹特性:
  - 可被拦截：其他武器命中 MissileGroup 中的成员 → 导弹销毁
  - 难以规避：终末阶段直线加速，拦截窗口短
  - 适合饱和攻击

Group 体系的价值:
  一个 MissileGroup 可包含一枚导弹，也可包含数十枚。
  复用 Group 系统意味着导弹可以像普通飞船一样接受复杂的机动指令，
  例如"绕过小行星带"、"覆盖式饱和攻击"、"分波次打击"。
```

---

### 4. 无人机（Drone）

带武器的微型飞船，本质上是**可自主开火的导弹 Group**。

```
无人机行为:
  - 和导弹一样以独立 Group 飞行
  - 在接舷战距离外时：接受母舰指令，保持阵型
  - 进入接舷战距离后：
    → 向目标飞行（类似导弹终末阶段）
    → 同时用自有武器向目标开火（近距离射击）
    → 撞击目标 → 触发命中

无人机 vs 导弹的关键区别:
  - 导弹：终末阶段无武器，纯撞击伤害
  - 无人机：终末阶段持续开火 + 撞击（双重伤害来源）
  - 无人机需要独立的 WeaponDef

无人机 Group 结构:
  DroneGroup:
    - 继承 MissileGroup 的所有字段
    - weapons: List<WeaponInstance>（自有武器）
    - weaponsEngageRange: 接触目标后武器激活的距离阈值
    - IsWeaponsActive: bool

无人机命中判定:
  1. 武器命中：和普通武器一样（见射弹/射线判定）
  2. 撞击命中：Group 坐标进入目标 OBB → 触发撞击伤害
  3. 两者可以叠加（先被炮击打残，再撞击摧毁）
```

## 武器类型与战斗流程的对应关系

```

    - 监控 Group 状态：接舷战距离 → 终末阶段 → 命中/自毁

  3. 若 overheatCounter ≥ overheatThreshold → 进入过热状态

## 未来方向：无边界战斗的三层模拟 tier

无边界战斗的核心约束：**世界处处有战斗可能，但全精度模拟的成本不允许处处全精度**。解决方案是"精度分层"——全精度是成本，抽象是常态，玩家存在才升级精度。

### 三层模拟 tier（区域 LOD）

| Tier | 范围 | 精度 | 节律 |
|------|------|------|------|
| Tier 0 | 玩家视野内 | 部件 OBB、逐弹丸、逐 tick 物理 | 每 tick |
| Tier 1 | 附近区域 | Group AABB、武器级结算（DPS×命中率×相对速度窗口） | 每 N tick |
| Tier 2 | 远处 / 无玩家 | 统计抽象（期望损伤率、按事件结算） | 低频 / 事件驱动 |

**迁移规则**：实体在 tier 间**渐进迁移**（不瞬切，避免跳变）；玩家靠近时从抽象"着陆"到全精度。需要为每个实体维护一个"精度等级"字段。

**参照**：X4: Foundations 的 Zone 模拟 LOD——玩家所在 Zone 全精度、相邻降频、远处用粗粒度状态演进。本项目三层网格（1000km 战略格 / 20km 战斗细格 / 部件 OBB）已有空间 LOD，缺的是**时间 LOD**。

### 区域级时间膨胀（TiDi）

参照 EVE Online 的 Time Dilation：负载超过预算时，把**受影响区域**的模拟时间步按比例放慢（如 10% 速率），保证区域内各系统以同一比例减速、不产生系统间漂移。

- 落地位置：`TimeScaleManager` 增加"区域倍率"维度（现有物理 tick 体系可直接承载）。
- 与全局慢速模式的区别：只对高负载区域降速，远处区域保持正常节律。

### 相关集合（兴趣管理）

MMO/分布式系统的 Interest Management 思路：每个实体维护"它需要精确知道什么"（看到它的、攻击它的、它攻击的），其余只接收摘要。单机版的意义在于**决定哪些实体进全精度、哪些进抽象**：

- 只有**敌对且互相在武器射程内**的 Group 对，才进入逐弹模拟。
- CombatGrid 的 AABB 覆盖格已是"空间相关"的雏形，可叠加"交战相关集合"。

### 确定性

连续世界模拟的底线：伤害结算顺序、AI 决策顺序必须与 tick 绑定（随机数种子 = f(tick)），否则回放、存档、未来联机都会塌。参见 `ThreadSafety/` 目录的既有测试方向。

### 架构推论（对现有系统的要求）

1. 战斗不需要 StartBattle/EndBattle——**交战检测**（敌对进入射程）+ **结算调度**（按相关等级定精度）是两个常驻子系统。
2. **涌现式遭遇取代刷怪器**：faction AI 决定意图（劫掠/巡逻/封锁补给线），遭遇是意图冲突的自然结果——势力系统与战斗是同一套系统的两面。
3. 战斗结束不留"战场"，残骸留在世界里（残骸打捞、物流约束自然成立）。

## 战斗 AI 设计（基础）

### 行为状态机

```
Idle ──(进入交战距离)──→ Defensive
Defensive ──(目标锁定)──→ Aggressive
Aggressive ──(HP < 30%)──→ Evasive
Evasive ──(脱离/恢复)──→ Defensive
```

### 各状态行为

| 状态 | 行为 |
|------|------|
| Idle | 不做任何战斗动作，继续轨道运动 |
| Defensive | 面向目标，缓慢调整姿态，仅还击 |
| Aggressive | 全速接近目标，所有武器开火 |
| Evasive | 随机横向机动，停止开火，尝试拉远距离 |

### 目标优先级

```
1. 正在攻击自己的敌人
2. 血量最低的敌人
3. 距离最近的敌人
4. 部件最多的敌人（威胁最大）
```

## 未来扩展：电子战 GPU 计算（最低优先级）

**优先级说明**：电子战系统本身未在 MVP 阶段规划，此章节仅作为未来扩展的技术储备。

### 电子战为何适合 GPU

```
对比分析：

| 场景 | 计算量 | 并行性 | 串行依赖 | GPU 提升 | 值得性 |
|------|--------|--------|---------|---------|--------|
| 电子战信号矩阵 | 100,000+ | 高（完全独立） | 无 | 94-98x | 非常值得 |
| 电子战覆盖网格 | 600,000+ | 高（完全独立） | 无 | 98x | 非常值得 |
| 战斗碰撞检测 | 2,500 | 中 | 高（伤害应用串行） | 受串行限制 | 不值得 |

核心原因：
  1. 计算量巨大（信号源 × 目标矩阵 = 100,000+）
  2. 完全独立（信号A对目标X的强度不影响信号B对目标Y）
  3. 传输开销占比极低（30 μs / 50,000 μs = 0.06%）
  4. 可批量处理（每 N tick 计算一次，容忍延迟）
```

### 方案 A：信号强度矩阵计算

```
场景：100 信号源（雷达、通信节点） × 1000 目标（飞船、残骸）

数据结构（NativeArray，零 GC）：
  public struct SignalSourceData {
    public Vector3 position;
    public float basePower;       // 基础功率（MW）
    public float frequency;       // 频率
    public float bandwidth;       // 带宽
    public Vector3 direction;     // 信号方向（定向天线）
    public float beamWidth;       // 波束宽度（度）
    public int sourceId;
  }

  public struct TargetData {
    public Vector3 position;
    public float stealthFactor;   // 隐身系数（0-1）
    public float reflectivity;    // 反射率（雷达截面积）
    public int targetId;
  }

  public struct SignalStrengthMatrix {
    public int sourceId;
    public int targetId;
    public float strength;        // 信号强度（dB）
    public float detectionProb;   // 探测概率
  }

GPU Job（并行计算所有信号源对所有目标的强度）：
  [BurstCompile]
  public struct SignalCalculationJob : IJobParallelFor {
    [ReadOnly] public NativeArray<SignalSourceData> sources;  // 100 个
    [ReadOnly] public NativeArray<TargetData> targets;        // 1000 个
    public NativeArray<SignalStrengthMatrix> matrix;          // 100 × 1000 = 100,000 元素

    public void Execute(int index) {
      int sourceIndex = index / targets.Length;
      int targetIndex = index % targets.Length;

      var source = sources[sourceIndex];
      var target = targets[targetIndex];

      // 计算距离和方向
      Vector3 direction = target.position - source.position;
      float distance = direction.magnitude;

      // 信号强度计算（平方反比衰减）
      float distanceFactor = Pow(distance / 1000f, 2);
      float powerFactor = source.basePower / distanceFactor;

      // 波束指向性（定向天线增益）
      float angle = Angle(source.direction, direction);
      float beamFactor = Cos(angle / source.beamWidth * PI / 180);
      if (beamFactor < 0) beamFactor = 0;

      // 隐身影响
      float stealthFactor = target.stealthFactor;

      // 最终信号强度
      float strength = powerFactor * beamFactor * stealthFactor;

      // 转换为 dB（对数尺度）
      float strengthDb = Log10(strength) * 10;

      // 探测概率（基于信号强度阈值）
      float threshold = 50;
      float detectionProb = Clamp01((strengthDb - threshold) / 20);

      // 写入结果矩阵
      matrix[index] = new SignalStrengthMatrix {
        sourceId = source.sourceId,
        targetId = target.targetId,
        strength = strengthDb,
        detectionProb = detectionProb
      };
    }
  }

性能预估：
  - 100 信号源 × 1000 目标 = 100,000 次计算
  - CPU 单线程：约 50,000 μs（50 ms）
  - GPU 并行：约 500 μs
  - 传输开销：约 30 μs
  - GPU 总耗时：约 530 μs
  - 提升：约 94x

调用策略：
  - 每 5 tick 计算一次（信号强度变化慢，容忍延迟）
  - 目标数据常驻 GPU（只传输位置更新）
  - 信号源数据常驻 GPU（只传输功率/频率变化）
```

### 方案 B：电子战覆盖网格（实时可视化）

```
场景：(20+10+30) 信号源 × 10,000 网格点 = 600,000 次计算

用途：
  - 实时可视化电子战覆盖范围（雷达覆盖图、干扰区域）
  - UI 显示"当前区域的信号强度"
  - 决策辅助（舰队指挥官看覆盖热力图）

数据结构：
  public struct EWGridPoint {
    public Vector3 position;
    public float radarCoverage;    // 雷达覆盖强度（0-1）
    public float jamCoverage;      // 干扰强度（0-1）
    public float comCoverage;      // 通信覆盖强度（0-1）
  }

GPU Job（计算每个网格点的覆盖强度）：
  [BurstCompile]
  public struct EWGridCalculationJob : IJobParallelFor {
    [ReadOnly] public NativeArray<SignalSourceData> radarSources;  // 20 个
    [ReadOnly] public NativeArray<SignalSourceData> jamSources;    // 10 个
    [ReadOnly] public NativeArray<SignalSourceData> comSources;    // 30 个
    public NativeArray<EWGridPoint> grid;                          // 10,000 网格点

    public void Execute(int gridIndex) {
      var point = grid[gridIndex];

      // 雷达覆盖强度（叠加所有雷达）
      float radarCoverage = 0;
      foreach (var radar in radarSources) {
        float distance = Distance(point.position, radar.position);
        float strength = radar.basePower / Pow(distance / 1000f, 2);
        radarCoverage += strength;
      }
      radarCoverage = Clamp01(radarCoverage / 100);

      // 干扰强度（叠加所有干扰器）
      float jamCoverage = 0;
      foreach (var jam in jamSources) {
        float distance = Distance(point.position, jam.position);
        float strength = jam.basePower / Pow(distance / 1000f, 2);
        jamCoverage += strength;
      }
      jamCoverage = Clamp01(jamCoverage / 50);

      // 通信覆盖强度
      float comCoverage = 0;
      foreach (var com in comSources) {
        float distance = Distance(point.position, com.position);
        float strength = com.basePower / Pow(distance / 1000f, 2);
        comCoverage += strength;
      }
      comCoverage = Clamp01(comCoverage / 30);

      // 更新网格点
      point.radarCoverage = radarCoverage;
      point.jamCoverage = jamCoverage;
      point.comCoverage = comCoverage;
      grid[gridIndex] = point;
    }
  }

性能预估：
  - 600,000 次计算
  - CPU 单线程：约 300,000 μs（300 ms）
  - GPU 并行：约 3,000 μs
  - 传输开销：约 50 μs
  - GPU 总耗时：约 3,050 μs
  - 提升：约 98x

调用策略：
  - 每 10 tick 计算一次（可视化辅助，容忍延迟）
  - 网格数据常驻 GPU（只读取结果渲染热力图）
```

### 与战斗系统的对比

```
为什么电子战适合 GPU，而战斗系统不适合：

战斗系统：
  - 计算量小（500 射弹 × 5 船 = 2500）
  - 有串行依赖（命中后部件状态变化，射弹销毁）
  - GPU 传输开销占比高（30 μs / 100 μs = 30%）
  → 提升受限（串行依赖），不值得

电子战：
  - 计算量大（100 信号源 × 1000 目标 = 100,000）
  - 无串行依赖（信号强度计算完全独立）
  - GPU 传输开销占比低（30 μs / 50,000 μs = 0.06%）
  → 提升显著（94-98x），非常值得

优先级排序：
  1. 战斗子 Grid（已完成）
  2. 轨道动力学多线程（优先）
  3. 电子战 GPU（未来扩展，电子战系统实现后）
  4. 战斗系统多线程（不值得）
```
