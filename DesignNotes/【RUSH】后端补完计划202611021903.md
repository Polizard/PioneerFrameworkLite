## 1. 任务 1：一次抛多个 Group + 径向安装

### 1.1 现状（证据）

- `TrySeparateStage` 只支持**单实体组**：`entityCount > 1` 直接 `multi-entity` 拒绝
  （`SpaceGameComp.Staging.cs:157-158`）。
- 即使单实体，也只按 `stageId == max` 把所有被抛件收成**一个**新组
  （`SpaceGameComp.Staging.cs:179-223`）⇒ 四台助推器会粘成一个 Group，做不了科罗廖夫十字。
- 没有“分离簇 / booster root”概念；`SpacePart.parentId` 存在，但 `TrySeparateStage` 不用它做分组。
- 设计器：`DesignPartSpec` 已有 `parallelCount`（绕主推轴成环）、`useExplicitPose` /
  `localPosition` / `localRotation` / `parentIndex`，但 `DesignPartAssembler` 明写
  **“v1 无 3D 自由布局”**（`DesignPartAssembler.cs:23`）；`Window_RocketAssembler` 只编辑
  `stageId`/堆叠，没有径向/并联控件；`installPosition` 只保存、不消费。
- 分离核 `StageSeparationCore.Solve` 是**两半**解算（A/B），不是 N 子体
  （`StageSeparationCore.cs:105-166`）。

### 1.2 目标

- **一次 staging event 同时抛出 N 个 Group**（N ≥ 2；科罗廖夫十字 = 芯级 + 4 助推器）。
- 设计器支持**径向安装**：围绕芯级/主推轴，按角度、半径、数量、父件安装；
  可预览质量/质心/包围盒；旧设计默认零变化。
- 分离保持动量/角动量守恒、无互相穿插、确定性、可存档/读档。

### 1.3 设计要点（原始方案，2026-11-02）

- **数据模型（2026-11-02 用户方案）**
  - 在级序号后面加**块号**：`(stageId, blockId)`。`stageId` = 抛级批次；`blockId` = 同一级里的第几个刚体块。
  - 科罗廖夫十字 = **级 1 有 4 个块**（4 台助推器），芯级是级 0/块 0；一次级 1 抛级 → 4 个 Group。
  - `blockId` 默认 0；旧设计一 stage 一块，逐位不变。
  - 径向安装优先用结构化字段（`parentIndex` + 角度/半径/数量），
    `localPosition`/`localRotation` 保留为显式覆盖；`parallelCount` 只负责“同一站的环”。
- **设计器**
  - 径向安装控件：父件、角度（0–360°）、径向半径、件数、镜像/环；
  - cluster 分组：把若干径向 booster 标成同一分离簇；
  - 预览：质量/COM/AABB/是否穿插；至少一个芯级、每簇质量 > 0、总件数 ≤ 256；
  - 保存/读档：旧设计（无 cluster/无显式 pose）逐位不变。
- **组装器**
  - `DesignPartAssembler` 支持“父件 + 径向位姿”的部件；不要简单的“沿 −Z 堆叠”。
  - 级间空隙保留（2026-10-30 的 `stageGapMeters`），径向 booster 与芯级之间也要留缝隙。
- **分离核（N 子体）**
  - 对每个 cluster 求 `(mass, COM)`；父组刚体状态 `P, V, ω, R`：
    `P_i = P + R·c_i`、`V_i = V + ω×(R·c_i)`（与现有两半核同口径）。
  - 分离冲量：沿“簇质心相对芯级质心”的径向方向施加；对称 4 助推器时芯级反冲相消，
    非对称按动量守恒分配到芯级/其余簇。
  - 每簇原点 = 自身质心；母舰/其余簇做反向修正；角速度保持（中心冲量无力矩）。
  - `TrySeparateStage` 返回 `IReadOnlyList<SpaceEntityGroup>`（保留单组兼容包装）。
- **事务/出生**
  - 一次事件注册 N 个组，确定顺序；与 `GroupBirthKind` / `pendingBirths` 对齐；
    要么全抛、要么不抛（失败不留半组）。
  - 存档/读档：多组出生后重新加载，位置/速度/质量/簇关系一致。
- **碰撞/表现**
  - 径向/轴向 gap；分离瞬间宽相不接触；多组 AABB/SAP 正常；
  - 选中/通知/自动抛级 UI 支持多组；相机/轨道线不跳。

### 1.7 并行级（C-full）与自动抛级（**定稿 2026-11-03 00:21**，未落码）

> 用户 2026-11-02 裁定：**C-full**（每块独立油池，不是共享池）；自动抛级用**块罐占比**；
> 特殊规则：**子级不抛时父级也不抛**（只能从叶子往根抛）。

**激活口径（不是“挂着的级全开”）**

- 设计期仍有“并联点火”标签：`RocketDesignSpec.parallelIgnitionStageIds` → 装配时烘到 `SpacePart`。
- 活动集 = 最大级 + 标了并联的下级（可传递）。R-7：级 0 标并联 ⇒ 发射时 {1,0} 同时烧；
  抛掉助推器后 {0}。
- 否则三级串联火箭一发射就三级全开——C-full 不等于“所有附着级默认点火”。

**分池（C-full）**

- 池 = 最小可抛单元（**块**）：`PropulsionData` 加 `(stageId, blockId)` 键；
  `PartPropulsionBuilder` 按 (工质, 块) 建网；`FuelPlan` 键加块；
  `GroupPropulsionAggregator` 合并键加块；`SyncStageFeedValves` 按活动集开阀。
- 每步仍 O(引擎+罐)，网络数 1→N（典型 2–3）；判据用 R-7 在场同轮 A/B：Δstep ≤2% 或 ≤10 µs。

**自动抛级算法（块罐占比 + 叶子优先）**

1. 每块 `fraction = 块罐质量 / 块容量`；阈值沿用 `autoStageFuelFraction`（默认 2%），
   `minSeconds`（默认 20 s）、燃烧中不切（现有 `AutoStageCore.ShouldStageByFuel` 口径）。
2. 候选 = **叶子级**（没有任何在场子级的级）；父级被在场子级挡住。
3. 候选级**所有块** fraction ≤ 阈值 ⇒ 抛整级（一次事件，N 个碎片组，走 §1.6）。
4. 候选级是 `Keep` ⇒ 它与其祖先都不抛，计划停在它前面。
5. 现有 `StepAutoStagePlans` 的 `FirstEntityOf + propulsion[0]` 假设要拆
   （单实体/单网络 → 多块多网络）。
6. R-7 行为：助推器（级 1，芯级的子级）罐见底 ⇒ 抛级 1（4 块 → 4 个碎片组）；
   芯级（级 0）在助推器还在时**不能抛**；助推器若标 `Keep`，芯级永远不能抛。

**已确认（2026-11-03）**

- 池粒度 = **块**（每个可抛块自己的罐 + 引擎一张网；`PropulsionData` 键 = 工质 + 块）。
- 事件粒度 = **整级所有块一起抛**（候选级所有块低于阈值 ⇒ 一次事件 N 个碎片组）。
- 父/子 = 按 `parentIndex`（靠机头 = 父）；R-7 助推器 = 芯级的子级；**手动抛级也套**。

## 5. 出生协议 B/C：优化与准确性评估（只读勘察，未落码）

### 5.1 现状（两套机制并存）

- 契约层：`GroupBirthKind`（Instantiated / Continuation / Emitted）+ `GroupBirthPolicy` 已落地；
  `RegisterGroup(group, kind, source)` 在 DEBUG 只做自检，**行为仍然等于单参 `RegisterGroup`**；
  `Emitted` 直接 `Log.Error`“本树尚未接入”（`SpaceGameComp.cs:607-640`）。
- 旧机制：`AnchorGroupBirth` + `physicsBirthSourceId/OffsetShip/MuzzleSystem` + `ResolveGroupBirths`
  仍在用（`SpaceGameComp.Time.cs:46-90`）；`CombatManager.cs:4598` 直接调 `AnchorGroupBirth`。
- 旧机制的代价：
  - `ResolveGroupBirths` 每步 `foreach (groups.Values)` 找 pending——**O(全组)**，不是 O(pending)；
  - 每个组常驻 3 个出生字段，`GroupIsVisibleAt` 每查询都判 `physicsBirthSourceId`；
  - `pendingGroupBirthCount` + `invalidGroupBirths` 两个旁路状态，易与契约层分叉；
  - `Emitted` 实际没走 `pendingBirths`，导弹/弹丸仍是旧路径。

### 5.2 目标

**准确**：弹丸/导弹在母体状态提交前不进入 `groups`（碰撞/传感器/渲染/制导都看不见），
提交后用母体**已提交**位姿 + 局部偏移/相对速度反推，避免一帧瞬移/速度双计。
**优化**：解析只走 pending 列表（O(pending)），不扫全组；热路径没有每组的出生分支；
每步 0 新分配；存档只存 pending。

### 5.3 建议设计

- **数据**
  - 新增 `PendingBirth`（groupId、sourceId、birthTick、offsetShip、muzzleSystem、kind），
    存在 `List<PendingBirth>` 或 `Dictionary<int, PendingBirth>`（按 source 分组）；
  - **从 `SpaceEntityGroup` 移除** `physicsBirthSourceId/OffsetShip/MuzzleSystem` 三个字段；
    `groups` 只含已提交体 ⇒ `GroupIsVisibleAt` 不再需要出生分支。
- **入队（Emitted）**
  - `RegisterGroup(group, Emitted, source)`：
    - 只做 ID/实体/组对象的准备，**不进 `groups`、不进粗网格/战斗网格/天体登记**；
    - 捕获 `source` 的已提交 `position/rotation/velocity`；
    - 记录 `offsetShip = R⁻¹·(p_local − p_source)`、`muzzleSystem = v_local − v_source`、
      `birthTick = source` 的提交 tick；
    - 加入 pending；不调 `RegisterGroup` 的可见侧效应。
  - `CombatManager` 的导弹/弹丸出生改调这个入口；不再直接 `AnchorGroupBirth`。
- **解析（提交边界）**
  - 在 `AdvancePhysics` 提交后、消费者之前，遍历 pending（只 pending）：
    - `source` 存在且已提交 ⇒ `p = p_source + R_source·offsetShip`、
      `v = v_source + muzzleSystem`；写回 orbit；调可见注册（网格/天体/战斗）；
    - `source` 失效 / 超时 ⇒ 销毁 pending，`PhysicsLogWarning`；
  - 解析顺序按 `(birthTick, groupId)` 确定；同一批多个 pending 一次处理。
- **消亡对称**
  - `UnregisterGroup` / `DestroyGroup` 同样 `MarkPhysicsEvent()`（批次内延后到边界）；
    pending 的 source 死亡时，pending 直接失效，不等 2 区间。
- **超时**
  - 最多等 2 个物理区间（1×=4 s / 8×=32 s）；超时销毁 + 警告（带 groupId/birthTick/sourceId）。
- **存档**
  - pending 单独 Scribe（v+1）；`RestorePhysicsClockAnchor` 从 pending 重算；
  - 旧档：把旧的 `physicsBirthSourceId` 组迁移成 pending（或按已提交处理），保留旧档读取路径一个版本。

### 5.4 为什么这是“又优化又准确”

- 准确：解析用的是**提交态**，不是 mid-step 的活状态；pending 不在 `groups`，所有消费者天然看不到，
  不需要在碰撞/传感器/渲染里各加一道过滤。
- 优化：旧路径每步扫全组；新路径只扫 pending（通常 0–几个）。`GroupIsVisibleAt` 去掉每组的出生判断；
  存档/恢复只处理 pending。
- 一致性：契约层（`GroupBirthKind`）和实现层（pending）合成一条路径，不再有两套出生逻辑。

### 5.5 判据

- 运动/旋转母体发射：提交前 `groups` 不含弹丸；提交后位置误差 <1e-6，速度无双计；
- 母体在出生前死亡：弹丸销毁 + 警告；超时 2 区间销毁；
- 存档往返：pending 仍 pending、tick 不变；旧档可读；v+1 兼容；
- 性能：10k 组 + 10 pending，解析不出现 O(10k) 扫描；每步 0 新分配；
- 全量 gates/确定性。

### 5.6 风险

- 存档 v+1 与旧档迁移；`RegisterGroup` 的可见侧效应必须延迟到解析，不能提前入网格/天体；
- `CombatManager` 可能在出生后立刻用组做制导/碰撞——pending 期间它不可见，需确认调用方不假设“注册即可见”；
- 多 pending 同源/同 tick 的顺序与 ID 分配；确定性；
- 与多组抛级无关（抛级 = `Continuation`，立即入世界，不走 pending）。
